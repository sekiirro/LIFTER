## Why this feature, why now

P4 activation requires delivery of both initial plans (BRD-01 inv. 6). Both planners (F17, F18) need stable exercise and food identities that plan versions can snapshot (Constitution V). F16 is therefore the shared foundation of P3 and the first link of the critical path P3 -> P4. F13 and F15 explicitly leave catalogs to P3.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Govern the canonical global exercise library (Priority: P1)

The Platform Owner (PO) creates canonical Global Library entries with exactly the eight FR-003 fields. Supporting taxonomy/version metadata is not an additional Exercise Library detail field. The PO may edit an existing canonical exercise only in the explicit global admin scope (S36-PO-2, F16-MCQ-5 answered a). Every authorized edit creates a new immutable version; the exercise identity never changes.

**Independent Test**: As PO, create a global exercise and verify its stable identity/version and audit event; verify a global-admin edit appends a version and that a PO edit made in a personal workspace leaves canonical content unchanged. As WO/Trainer/Sales verify global create/edit is denied by both walls.

**Acceptance Scenarios**:

1. **Given** a PO, **When** they create a global exercise with an English name, optionally an Arabic name, a primary muscle group and metadata from the approved taxonomy, **Then** a stable exercise identity and version 1 exist and an audit event is recorded without free-text content.
2. **Given** a PO in the explicit global admin scope and an existing global exercise, **When** the PO edits it, **Then** a new version is appended, the previous version stays readable and unchanged, and the identity is preserved. **Given** a PO scoped to a personal workspace, **When** the PO edits the same exercise, **Then** only that workspace's override changes (see User Story 2, scenario 3).
3. **Given** a non-PO staff member, **When** they attempt to create, edit, remove, restore or merge a global exercise, **Then** the request is denied by app authorization and by RLS.
4. **Given** a PO creates or versions a Global exercise, **When** its optional Description is at most 2000 characters and its Alternatives omit the exercise itself, **Then** the version is accepted; **When** the Description exceeds 2000 characters or the exercise is included as its own Alternative, **Then** the write is refused with the existing validation error (FR-003, FR-025; S47-PO-8, S47-PO-9).

### User Story 2 - One global exercise catalog with workspace overrides (Priority: P1)

Coaching staff see one shared global exercise catalog in every authorized workspace. Each workspace has its own branded library and may independently edit all eight fields locally: Name, Description, Notes, Video, Alternatives, Default Rest Time, Default RIR and Default Reps. Local edits never change Global or another workspace. New global exercises appear automatically without overwriting local edits. Each overridden field resets to the canonical value independently (F16-MCQ-A). A workspace-private exercise created by a Trainer remains private to its workspace. This is one catalog with overlays, not duplicated global libraries.

**Independent Test**: Create one canonical global exercise and overrides in two synthetic workspaces. Verify both workspaces resolve the same canonical identity, each sees its own allowed override values, and neither workspace can read or infer the other's override or private exercise. Verify an edit made by the PO while operating in a personal workspace changes that workspace's override only.

**Acceptance Scenarios**:

1. **Given** a global exercise visible in workspace A and workspace B, **When** authorized staff open the workspace library, **Then** each sees the shared global entry together with only that workspace's override state.
2. **Given** a Trainer or WO with current `coaching_work` in workspace A, **When** they create or edit an override, **Then** only the eight FR-003 fields can be changed, and the canonical global identity and content remain unchanged.
3. **Given** the PO edits an exercise while scoped to the PO's personal workspace, **When** the change is saved, **Then** it writes to that workspace's override only and leaves canonical global content unchanged.
4. **Given** a Trainer creates a new exercise in workspace A, **When** the creation succeeds, **Then** it is a workspace-private exercise visible only in workspace A and does not become a global catalog entry.
5. **Given** a workspace is newly created, **When** it becomes available, **Then** no mapping row is created, and its exercise videos resolve to the global video fallback until a workspace edit creates an override (S36-PO-2, F16-MCQ-1 answered a; F16-MCQ-2 moot).
6. **Given** a workspace-A override or private exercise, **When** a caller without current workspace-A authorization reads from workspace B or through a client/plan path, **Then** the read is denied generically and reveals no foreign row, video, count, identifier existence or error distinction.
7. **Given** an exercise has optional Rest Time, RIR and Reps defaults, **When** an authorized planner adds it, **Then** those values are copied into editable planner entries and later library edits do not change them.
8. **Given** a new Global exercise is created while workspaces have local customizations, **When** workspace users open their libraries, **Then** the new exercise appears in every workspace and all existing local customizations are unchanged.
9. **Given** pre-F16 exercise data exists, **When** the F16 cutover runs, **Then** all pre-F16 exercise data is deleted rather than migrated (S40-PO-8): every legacy exercise row, including rows without Instructions, with its immutable legacy version history and legacy videos (S40-PO-7); every pre-F16 canonical and workspace-private exercise identity and version, with its videos; and mock plan snapshots that reference them are deleted or reset. No Instructions text is merged into Notes, legacy Notes are deleted with their rows (S40-R15), and the library contains no Instructions field (S40-PO-5).
10. **Given** a workspace exercise is created or versioned, **When** its Alternatives omit that exercise itself, **Then** the write is accepted; **When** it lists itself as an Alternative, **Then** the write is refused with the existing validation error (FR-025; S47-PO-9; workspace implementation is T075).

11. **Given** the workspace editor has selected Alternatives across multiple search pages, **When** staff search, paginate, or clear a query, **Then** each selected target remains selected and available even when it is outside the current result page; search is authorized and returns no more than 50 rows per keyset page (FR-025; S49-PO-3; implementation mapping S49-R9).
12. **Given** Notes or a stored Video text reference contains 2,000 characters, **When** an authorized editor saves it, **Then** it is accepted unchanged; **When** it contains 2,001 characters, **Then** editing, normalization, and database validation reject it without truncation. **Given** pre-existing stored values exceed the limit, **When** the cap migration runs, **Then** it raises with the count and leaves all rows unchanged (FR-003, FR-031; SC-020; S49-PO-3).

### User Story 3 - Add foods directly to the global food database (Priority: P1)

Any staff member with `coaching_work` adds a food to the global database immediately (no moderation queue), with structured nutrition per reference quantity and serving units. Validation and duplicate detection prevent invalid or duplicate entries without bureaucracy.

**Independent Test**: Add a valid food (immediately searchable by all coaching staff of all workspaces); attempt an invalid food with negative values (rejected with field errors) and an exact duplicate (blocked, pointing to the existing food); attempt a near-duplicate (warned, explicit confirm allowed); submit a 4/4/9 kcal discrepancy beyond the approved tolerance and verify a warning appears while the food saves.

**Acceptance Scenarios**:

1. **Given** a Trainer, **When** they add a food with AR and/or EN name, canonical product identity, preparation identity and weighing state, per-100 g (or per-100 ml) calories, protein, carbohydrate and fat, and at least one serving unit with a gram (or ml) equivalent, **Then** the food is immediately available globally as version 1.
2. **Given** negative values or macro grams exceeding the reference quantity, **When** submitted, **Then** it is rejected with field-level bilingual errors and nothing is written. **Given** calories inconsistent with 4/4/9 beyond `max(20 kcal, 10% of stated kcal)`, **When** submitted, **Then** a field-level warning appears and the food saves if all other validation passes (PO S20 Message B section 1, D16-5).
3. **Given** a food whose language, normalized name, basis, product identity, preparation identity and weighing state match an existing active food, **When** submitted, **Then** creation is blocked and the existing food is offered. **Given** the same normalized name in another language or a different product/preparation identity or raw/cooked state, **When** submitted, **Then** it remains a distinct food. **Given** a near match within the same identity dimensions (similar name and macros within tolerance), **Then** a warning lists candidates and creation proceeds only on explicit confirmation.
4. **Given** any global food, **When** viewed by non-PO staff, **Then** no creator identity or workspace of origin is disclosed (Invariant 1).

### User Story 4 - Version, remove, restore and merge catalog entries safely (Priority: P2)

Corrections never rewrite history: an edit creates a new version, Remove hides an entry from new selection, global catalog Restore is available to the PO through the backend/API and makes the same identity/current version selectable again, and a merge redirects a duplicate to a survivor. Workspace exercise Restore is not authorized. Existing plans keep their references and snapshots.

**Independent Test**: Remove a food and merge a duplicate into a survivor; verify search excludes the removed food for new selection, the survivor is suggested, existing version rows and client plans are unchanged, and frozen `ExerciseSnapshotV1`/`FoodSnapshotV1` fixtures still serialize exactly. (Rendering a stored plan snapshot is an F17/F18 acceptance criterion, not an F16 exit gate.)

**Acceptance Scenarios**:

1. **Given** an authorized actor per the approved edit/merge matrix, **When** they merge food X into food Y, **Then** X is marked superseded by Y (no delete), new selection of X is redirected to Y, and an audit event records both identities.
2. **Given** a removed or superseded entry, **When** a planner loads an existing draft containing it, **Then** the draft shows a non-blocking "removed/replaced" indicator and the stored values remain intact.
3. **Given** a PO restores a removed global catalog entry through the backend/API, **When** Restore succeeds, **Then** the same identity and current immutable version become selectable with one lifecycle/audit record; prior plan references and snapshots remain unchanged. Workspace exercise Restore is not authorized and no exercise Restore control is shown in the UI. **Given** X was merged into Y and Y is merged into Z, **Then** X is atomically redirected to Z; a later request targeting X resolves to active terminal Z, with no chain and no plan-reference rewrite.
4. **Given** an authorized actor viewing an exercise detail, **When** they choose Remove, **Then** removal requires explicit confirmation; cancel leaves the exercise unchanged. A PO may remove a global exercise and a PO may remove an explicitly scoped workspace exercise; a WO or Trainer may remove a workspace exercise only in their own workspace while current `coaching_work` membership is valid. Sales, Client, unauthenticated, foreign-workspace and revoked-membership actors are denied. Add/Edit has no lifecycle controls, and the exercise UI offers no Merge or Restore controls. Removal appends an inactive lifecycle marker and audit event, uses expected-revision compare-and-swap and an idempotency operation key, and does not delete or rewrite data, historical references, plans, or snapshots.

**Core removal rule**: Removing from the Catalog must never mean removing from clients' existing plans.

### User Story 5 - Bilingual, accessible catalog screens (Priority: P2)

Staff browse, search (Arabic and English, with Arabic normalization), filter and add catalog entries in the Design System, AR (RTL) and EN.

**Independent Test**: Playwright + axe on catalog list, search, add-food and add-exercise in AR/EN, light/dark, mobile/desktop; Arabic search finds entries regardless of alef/hamza/ta-marbuta/diacritic variants.

### User Story 6 - Resolve exercise video for a client viewing a global template (Priority: P1)

A global workout template keeps canonical exercise identity. Client access remains authorized and workspace-scoped. Published plans freeze names, descriptions, notes, alternatives and defaults; Video stays live and follows the authorized library resolution (S37-PO-1 Q2 = A; S36-PO-2).

**Independent Test**: Use synthetic global-template and client/workspace fixtures. Verify authorization and workspace isolation. After publication, change the authorized library Video and verify the next plan view resolves the current authorized workspace override or Global fallback.

**Acceptance Scenarios**:

1. **Given** a global template and a client in an authorized workspace, **When** the plan is viewed, **Then** only the current authorized workspace Video override or Global fallback is returned.
2. **Given** a workspace Video changes after publication, **When** the authorized client views the plan again, **Then** the current authorized library Video is returned while the other published values remain frozen.
3. **Given** a client-view request without the required plan/client workspace authorization, **When** video resolution is attempted, **Then** it is denied with generic security behavior and no foreign workspace information is disclosed.
4. **Given** a trainer adds an exercise whose default is copied into a planner entry, edits that entry, and publishes the plan, **When** the library default and exercise names change before or after publication and the plan is viewed, **Then** the published non-video values retain the planner-entry values captured at publication (including the trainer edit) and the name remains frozen, while Video follows the current authorized library resolution.
5. **Given** a published plan references an exercise identity that was later removed or merged, **When** the plan is viewed for the client, **Then** it never follows the merge survivor and the plan reference is unchanged (FR-028); Video resolves for the referenced identity using its current authorized library value.
6. **Given** any caller that is not the F19/P4 client boundary, **When** it attempts to call video resolution directly, **Then** the call is denied, because F16 exposes no client-callable function (FR-029).

### Edge Cases

- Same-language food with matching name and identity dimensions is an exact duplicate; the same normalized name in another language remains distinct. Test same-language blocking and cross-language distinction.
- Food measured in ml (liquids) vs g: no implicit g<->ml conversion unless the food defines a serving equivalence.
- Concurrent edit of the same entry by two actors: the second write against a stale version is rejected (optimistic concurrency), never silently overwritten.
- Merge chains: requests targeting a superseded entry resolve to its active terminal entry; when an active entry with inbound aliases is merged, all aliases are atomically repointed to the same terminal so chains never remain. Cycles are rejected.
- A PO restores a removed global catalog entry through the backend/API: the same identity becomes selectable again using its existing current immutable content version; no version or plan reference is rewritten. Workspace exercise Restore is not authorized.
- Video reference with a disallowed host, non-https URL, or embedded credentials: rejected.
- A global exercise has no workspace override: video resolution uses the canonical global video fallback.
- Workspace membership revoked mid-session: next request is denied (current-membership check per request).
- Very large catalog search on the Free tier: bounded page size, indexed search, no unbounded scans.
- A staff member with roles in several workspaces adds a workspace exercise: it belongs to exactly one chosen, authorized workspace.
- No client transfers between workspaces (S36-PO-2, FR-022): a client record and its plans stay in one workspace. Account deletion frees email/phone for fresh registration in another workspace, with no data transfer (S37-PO-10). The F11/F12 follow-up for this deletion behavior is pending (F11 and F12 exclude client closure/deletion); it is out of F16 scope and T069/F16-MCQ-D-R are removed from this feature.
- Per-field reset (S36-PO-3, F16-MCQ-A): resetting one overridden field returns only that field to the canonical value; the other overridden fields and the override version history are unchanged.
- Empty alternatives (S36-PO-3, F16-MCQ-B): a workspace may save an empty alternatives list, which means no alternatives for that exercise in that workspace. It is not a reset to the canonical list.
- Existing Notes are preserved for non-legacy data (S36-PO-3, F16-MCQ-C; S36-PO-5): no non-legacy note text is deleted or rewritten, and the legacy-data audit (T068) precedes any migration. Legacy exercise Notes are not preserved: they are deleted with their rows at cutover (S40-PO-5, S40-PO-8; architect ruling S40-R15, PDN-S40-F16-04 resolved).
- A published plan keeps the name, description, notes, alternatives and defaults from its planner entry frozen at publication; later library-default changes cannot replace planner-entry values, and later override edits/removals do not change the snapshot. Video remains live and follows the current authorized library resolution (F16-MCQ-O).

## Requirements _(mandatory)_

### Functional Requirements

- **FR-036** Given authorized WO/Trainers edit a workspace library, when they change any of the eight FR-003 fields, then the value is local to that workspace; when a new Global exercise appears, it is visible in every workspace without replacing local values.
- **FR-037** Given optional defaults are configured, when a planner adds the exercise, then Rest Time, RIR and Reps are copied into editable planner entries; subsequent library edits do not change those entries.
- **FR-038** Given pre-F16 exercise data exists, when the F16 cutover runs, then all pre-F16 exercise data is deleted rather than migrated (S40-PO-8): every legacy exercise row, including rows without Instructions (S40-PO-5), with its immutable legacy version history and legacy videos (S40-PO-7); every pre-F16 canonical and workspace-private exercise identity and version, with its videos; and mock plan snapshots that reference them are deleted or reset. None remains after cutover, no Instructions text is merged into Notes, legacy Notes are deleted with their rows (S40-R15), and the library has no Instructions field.

- **FR-001** Global exercises MUST have stable identities and append-only immutable versions. Taxonomy is exactly 18 muscles (Chest, Lats, Upper Back, Traps, Front Delts, Side Delts, Rear Delts, Biceps, Triceps, Forearms, Abs, Spinal Erectors, Quads, Hamstrings, Glutes, Adductors, Abductors, Calves) and 10 equipment values (Barbell, Dumbbell, Cable, Machine, Smith Machine, Bodyweight, Kettlebell, Resistance Band, Suspension Trainer, Other). For both canonical Global and Workspace exercise names, English is required and Arabic is optional (S37-PO-10); this supersedes the S20 Arabic-required rule for F16. Primary muscle and required equipment are required; secondary muscles are optional. Taxonomy is supporting version metadata, not a ninth Exercise Library detail field. The create/version form collects and validates it, and changing it appends a new version (FR-016a).
- **FR-002** PO exclusively creates global exercises; authorized staff manage workspace exercises. Only PO removes or merges global entries. The PO may edit an existing canonical global exercise only in the explicit global admin scope (S36-PO-2). Remove hides an entry from catalog search and prevents new selection; it does not change any existing client plan. (PO S20 Message B section 1; amended by PO S21-PO-4)
- **FR-003** Each global exercise has exactly these eight library fields: Name, Description, Notes, Video, Alternatives, Default Rest Time, Default RIR and Default Reps. Canonical Global and Workspace names require English and allow optional Arabic. Description is one optional value in any language, without an AR/EN pair; a canonical Global Description MUST contain at most 2000 characters, matching the workspace override cap, and a longer value is refused with the existing validation error (S47-PO-8). Notes and stored Video text references (URL or ID strings) MUST each contain at most 2,000 characters; media files are outside this limit. All editing, normalization, and database validation paths enforce the same maximum and reject over-limit values without truncation (S49-PO-3). Only the PO edits the Global Library. Each workspace has a branded, independently customizable library where authorized WO/Trainers may edit all eight fields locally without affecting Global or another workspace. New global exercises appear automatically in every workspace and do not overwrite local customizations. Instructions is not a field. Every legacy exercise row is deleted at cutover, not migrated (S40-PO-5), and no Instructions text is merged into Notes; existing Notes stay on rows that remain (S36-PO-5). Alternatives are limited to three unique targets per exercise. Defaults are optional. Rest Time is an integer from 0 through 600 seconds in 15-second increments; RIR is an integer from 0 through 5; Reps is an integer or inclusive range with each endpoint from 1 through 100. Defaults are copied into editable planner entries when an exercise is added and never remain live-linked.
- **FR-004** Staff with `coaching_work` in a workspace MUST be able to create workspace-only exercises in that workspace, versioned like workspace-owned entries; they are invisible to other workspaces and are not global catalog entries. Every workspace library MUST present its authorized shared global entries and that workspace's override state together with its workspace-private exercises, without exposing other workspaces' rows or counts.
- **FR-005** Global foods MUST have a stable identity and immutable versions holding: AR/EN names (at least one), basis (`g` or `ml`), canonical product identity, preparation identity, weighing state (`raw`, `cooked`, or `not_applicable`), per-100-basis energy (kcal) and protein/carbohydrate/fat grams, optional fiber, and one or more serving units each with an exact basis equivalent. Product identity, preparation identity and weighing state are non-null; use `not_applicable` when preparation/weighing distinction does not apply. These dimensions distinguish genuinely different products and raw/cooked forms; the PO-approved dataset audit supplies/approves catalog values before import.
- **FR-006** Any staff member with `coaching_work` in at least one workspace MUST be able to add a global food that is immediately usable (PRD-05: no moderation queue). A non-PO creator MUST explicitly select one current workspace where they have `coaching_work`; the selected workspace is stored as immutable origin provenance on the food identity and its creation record/first version. A PO may create directly without workspace context (origin is NULL) or select an authorized workspace. Origin is provenance only and never changes global catalog ownership. (PO S20 Message B section 1; D16-9)
- **FR-007** Negative nutritional values and non-positive serving equivalents are rejected. When the kcal discrepancy exceeds `max(20 kcal, 10% of stated kcal)`, the system warns; it MUST NOT block saving solely for this discrepancy. (PO S20 Message B section 1; supersedes v3 FR-007)
- **FR-008** Exact-duplicate identity MUST include language, normalized name, basis, canonical product identity, preparation identity and weighing state. Near-duplicate comparisons use normalized textual similarity of at least 90%, with no automatic synonym matching, and kcal proximity at most `max(10%, 10 kcal)`, standardized per 100 g or 100 ml; compare only within the same basis and product/preparation identity and weighing state, so raw/cooked states and genuinely different products remain distinct. Block genuine catalog duplicates, while repeated foods/meals inside client plans remain allowed through Duplicate Food/Meal actions. (PO S20 Message B section 1; supersedes v3 FR-008)
- **FR-009** The creator recorded on the stable food identity or PO may publish food edits without moderation; being the author of a later version alone grants no edit right. Only PO removes or merges global entries. (PO S20 Message B section 1; amended by PO S21-PO-4)
- **FR-010** Only PO may merge global entries. Merge MUST use an active source (never removed or superseded) and mark it superseded (no delete); resolve a requested target through its `superseded_by` chain to the active terminal before merging. Atomically repoint every direct inbound alias of a merged source to that terminal, so all chains are flattened and cycles cannot form. New selection of any alias resolves to the terminal; existing plan references and published snapshots remain unchanged.
- **FR-011** Catalog content versions and audit events are immutable and never updated or deleted, except the approved cutover deletion of pre-F16 exercise version history under FR-031 and FR-038 (S40-PO-7 and S40-PO-8); audit events are never deleted. Add creates an identity and its first version; every authorized Edit appends a content version; the single staff-facing lifecycle action, Remove, appends a non-destructive inactive marker without deleting content; Restore appends an active marker for the same identity and current content version, without creating or changing a content version. Removing a food or exercise hides it from catalog search and prevents new selections. Remove never cascades to a client plan and never changes, republishes, or removes an existing plan reference, snapshot, log, media availability, or historical data; only an explicit plan-editing action may remove an item from an existing plan. Global Remove and Restore are PO-only; Global Restore remains a backend/API capability only. Workspace exercise Remove is allowed to a PO for an explicitly scoped workspace and to a WO or Trainer with current `coaching_work` in that same workspace. Workspace exercise Restore is not authorized (S31-PO-1 Q3). The exercise UI exposes Remove on Exercise Detail only, requires confirmation, and has no Restore or Merge controls (S30-PO-9). (PO S20 Message B section 1; amended by PO S21-01, S30-PO-9 and S31-PO-1 Q3)
- **FR-012** Global catalog reads MUST be allowed to the PO directly (with or without workspace membership, BRD-02) or to authenticated staff holding `coaching_work` in at least one current workspace; the read function and RLS policy enforce the same rule; Sales, clients and unaffiliated staff are denied direct catalog access. F16 exposes no client-callable function. Only the internal, workspace-parameterized resolver of FR-029 may resolve the exercise videos referenced by a client's authorized published plan; the authenticated-client wrapper is owned by F19/P4. This does not grant clients catalog/table/search access, and the wrapper returns generic denial on missing or unauthorized plan/client scope. Clients never read catalogs directly; they see plan-version snapshots (F17/F18/P4).
- **FR-013** Global entries MUST NOT expose creator identity or workspace of origin to non-PO actors in lists, details, duplicate candidates, pagination/counts, RPC results, errors, or exports; the immutable creator and origin provenance is visible to PO governance only (D16-9). Global-catalog audit events set `workspace_id` NULL; workspace-catalog events use that workspace. Audit details are an allowlist (action, target/version ids, related id, changed-field codes such as `name_ar`, `kcal`, `video` - codes only, never values; the immutable version rows hold the content for PO review) with no names, notes, nutrition, URLs, origin workspace, raw operation key or free text. Operation keys MUST be client-generated UUIDv4, format-validated and bound to the RPC action name before use, stored only in the idempotency table, which keeps rows for 30 days and is purged by the existing cron (counted in D16-10 storage budgets).
- **FR-014** Exercise video URLs MUST use the approved HTTPS host rule in D16-3; `docs.google.com` is not an allowed host. Cutover deletes dummy `docs.google.com` values and provides no legacy support path. For pre-F16 exercise data, S40-PO-7 and S40-PO-8 delete the legacy and pre-F16 videos at cutover; no such video is carried over, so the earlier “no video lost” carry-over (S37-PO-10) does not apply to them. A single global identity may carry a canonical video and each workspace may override it. For library resolution the workspace video takes precedence, then the canonical video; removing a workspace video restores the global fallback (S36-PO-2). New workspaces have global video fallback and no automatic mapping rows. Video stays live in published plans and follows the current authorized library value (S37-PO-1 Q2 = A).
- **FR-015** Search MUST support AR and EN through a versioned, collation-independent `normalize_ar_en_v1` (Unicode NFC, explicit Arabic/Latin fold table: alef/hamza forms, ta marbuta/ha, alef maqsura/ya, diacritics and tatweel removal, locale-independent case mapping), filters (muscle group, equipment, basis), bounded pagination (max 50) and stable ordering. Algorithm changes require new columns/indexes via forward migration.
- **FR-016** Every mutating RPC MUST: authorize first; then lock all affected identity roots in deterministic UUID order (or acquire deterministic creation/key locks when a root does not yet exist); then look up `(actor_user_id, operation_key)` (same key + same request hash returns the original result; same key + different hash = conflict); re-read `current_version` and lifecycle state (stale expected version = conflict); recheck membership/capability and resource-specific ownership after lock waits and before disclosing an idempotent replay result; write exactly one audit event. Global food versioning additionally requires the actor to be the food's creator or PO, checked against the locked food identity before any write. Merge is PO-only: resolve a superseded target to its active terminal, atomically flatten direct inbound aliases to that terminal, and recheck all locked identities to prevent cycles or chains. Search is not audited per request.
- **FR-016a** Taxonomy (muscle groups, equipment) MUST be versioned: stable code, kind, AR/EN labels and lifecycle per term version; exercise versions reference term versions; PO taxonomy changes use audited RPCs and never rewrite existing exercise versions.
- **FR-017** Sales MUST have no catalog rights (deny by default; Sales coaching rights unconfirmed).
- **FR-018** The workspace exercise library MUST present Global entries together with the current workspace customizations. Its detail editor MUST expose the eight FR-003 fields to authorized WO/Trainers; the create/version form additionally collects the required taxonomy metadata of FR-001. The Global Library is editable only by the PO. A workspace edit, including a PO edit made in workspace scope, affects that workspace only.
- **FR-019** No YBS import and no seeded catalog content unless the PO supplies an approved starter list (BRD-06).
- **FR-020** Food snapshots retain their exact referenced immutable version and validated per-100 values. Published exercise plans retain frozen non-video values as required by S36-PO-5; Video stays live and follows the library (S37-PO-1 Q2 = A). Exercise defaults are copied into editable planner entries at addition and never live-linked. Exception (S40-PO-8, PDN-S40-F16-05 = A): at cutover, published exercise plan snapshots that reference pre-F16 exercise data are deleted or reset; no retention applies to them.
- **FR-021** Every role authorized by FR-006 (PO, Workspace Owner, or Trainer) is subject to at most 10 accepted new food identities per creator per rolling 24 hours, plus a platform-wide cap of 100 accepted new food identities per rolling 24 hours across all those roles; no more than 10,000 foods may be active. Exact idempotent replay consumes no additional quota. Remove/Merge decrease the active count; Restore must satisfy the active ceiling and does not consume an Add allowance. Enforce counters transactionally under concurrency-safe locks. Benchmark the catalog before production. (PO S20 Message B section 1; D16-10)
- **FR-022** No client transfers between workspaces (S36-PO-2). A client record and its plans belong to one workspace; the system MUST NOT move a client from one workspace to another.
