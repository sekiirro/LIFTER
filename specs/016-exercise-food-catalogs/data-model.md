# F16 Logical Data Model

This is a logical model for implementation planning, subordinate to the approved spec and plan. It defines no SQL syntax or migration implementation.

## Shared invariants

- Identity rows are stable. Every content edit appends an immutable, numbered version; current-version changes use compare-and-set under an identity-row lock.
- Use composite tenant keys and foreign keys for workspace-owned records. Every tenant read and write applies current membership checks plus forced RLS; callers cannot choose a foreign workspace by changing an ID.
- Lifecycle actions are append-only state transitions. `Add` creates identity/version 1; `Edit` appends a version; `Remove` appends a non-destructive inactive marker; `Restore` appends an active marker for the same identity and current content version. Remove is the only catalog-removal action. No lifecycle action deletes or rewrites a content version or breaks plan references. Global Remove/Restore and global merges are PO-only; workspace exercise Remove requires `coaching_work` in the explicitly selected owning workspace, and workspace exercise Restore is not authorized (S31-PO-1 Q3).
- Audit is immutable and transactional with a successful write. Audit details contain only allowlisted action/target/version/related IDs and changed-field codes. Global event `workspace_id` is NULL. Never write names, notes, nutrition, URLs, origin, raw operation keys, or free text to audit.
- Store audit-only governance fields (`created_by`, origin workspace where applicable) separately from non-PO read projections. Non-PO global food projections omit creator and origin in data, errors, counts, and search candidates.
- No exercise or food content is seeded. Seed only the approved taxonomy. No import occurs until the PO supplies and approves a dataset after the D16-4 audit.

## Nutrition and duplicate rules

- Nutrition basis is exactly per 100 g or per 100 ml. kcal and protein/carbs/fat are required; fiber is optional. Store decimal-safe values and reject negative values. Serving equivalents must be positive. The validator reports a warning when `abs(stated kcal - 4*protein - 4*carbs - 9*fat) > max(20 kcal, 10% of stated kcal)`; this discrepancy alone never blocks save.
- The full exact duplicate identity key is `(language, normalized name, basis, normalized product identity, normalized preparation identity, weighing state)`. Version duplicate checks reserve/check this full tuple for each localized name in the candidate version; the near-match candidate scope is same basis, normalized name similarity >=90%, kcal tolerance `max(10%, 10 kcal)`, and matching normalized product identity, normalized preparation identity and weighing state. Product/preparation/state dimensions are stored as identity fields rather than inferred only from localized names.
- Candidate comparison uses the versioned Arabic/English normalizer. Similarity threshold is at least 90%; no automatic alias/synonym expansion. Near-match kcal distance must be no more than `max(10%, 10 kcal)` per same basis and matching product/preparation identity and weighing state. Matching basis is required; g and ml are never compared as interchangeable.
- Block genuine catalog duplicates and offer the existing identity. Warn and require explicit confirmation for a near match. Different products/preparations and raw/cooked states remain distinct. Repeating the same food or meal within a plan remains allowed through plan duplicate actions.

## Lifecycle and version references

- Plan snapshots reference explicit `(identity_id, version)` pairs and retain their frozen values. Later catalog edits, Remove, Restore or merge never rewrite a plan snapshot. Round 3 (FR-027): an exercise reference in a published plan is an `ExerciseSnapshotV2` carrying exercise identity, canonical version, the override version reference (or null) and frozen non-video values captured from the planner entry at publication. Planner entries contain defaults copied when the exercise was added and any subsequent trainer edits; publication must not replace those values with a later effective library resolution (FR-026, FR-037). Video stays live and resolves from the current authorized library value (S37-PO-1 Q2 = A). A workspace-private exercise uses the same V2 type with `source = workspace_private`, carrying the workspace exercise identity and version, with no override reference (FR-027). Global and Workspace names require English and permit optional Arabic; Description is one optional value in any language (S37-PO-10).
- Remove hides the entry from new selection and appends a non-destructive marker; it never cascades to or modifies a client plan, snapshot, log, media reference or historical record. Restore appends an active marker for the same identity and current immutable content version. Food Restore re-reserves exact keys atomically and fails with a duplicate conflict if another active food owns any key.
- Merge is PO-only. It requires an active source, resolves a requested target through `superseded_by` to its active terminal, and atomically flattens direct inbound aliases so chains/cycles cannot form. Existing plan references and published snapshots remain unchanged; new selection resolves to the terminal. Remove and Merge do not refund the rolling food-add quota; they reduce only the active-food count.
- A food version freezes its default-alternative list after validating each target as active and current at write time. Later target Remove/version/Merge leaves the stored list untouched. At use time, F17/F18 planners and UI follow merge aliases to the terminal survivor's current version, skip removed targets while showing a visible `alternative unavailable` state, and never silently substitute another food.
- Effective resolution (FR-026): one internal contract returns, per field (Name, Description, Notes, Video, Alternatives, Default Rest Time, Default RIR, Default Reps), the value and its source (`override`, `canonical`, `none`) for an explicit workspace and canonical identity. The library view, the F17 picker and the snapshot builder all use it. Video precedence: workspace override video if set, else canonical current video, else `none`. Global-template authoring (F17) resolves canonical-only: no workspace is supplied or read, and no workspace override, private alternative or workspace metadata participates. Each field returns its canonical value with source `canonical`, or source `none` when no canonical value exists (optional fields may be absent without blocking); T068 records as an inventory blocker only a missing required or incompatible canonical value, with no fallback and no guessed value.
- Client-plan video (FR-029): F16 provides only an internal resolver executable by the Plan Core/P4 projection role. It takes the workspace from its caller, not from the client; any workspace-scoped reference that does not match the supplied workspace causes a whole-call generic denial. The authenticated-client wrapper (client ownership, plan-to-client relation, workspace derivation) belongs to F19/P4 and needs F19 persistence, which does not yet exist on main or on `origin/019-plan-core`. Client workspace equals plan workspace per FR-022 (no client transfers).
- Plan-view resolution for removed or merged identities (FR-028): the plan's own referenced identity is resolved, not the merge survivor; activity of the identity is not required; override rows are never rewritten by Remove or Merge.
- Library video resolution uses workspace override then Global fallback; removing a workspace video restores Global (S36-PO-2). Video stays live in published plans and follows that authorized library value (S37-PO-1 Q2 = A).

## Search and privacy

- `normalize_ar_en_v1` is collation-independent and versioned: Unicode NFC, explicit Arabic/Latin folding, alef/hamza forms, ta marbuta/ha, alef maqsura/ya, diacritic and tatweel removal, and locale-independent case mapping.
- Search filters support muscle group, equipment and food basis; stable ordering and bounded pagination cap page size at 50. Use indexed normalized columns; algorithm changes require forward migrations and new indexes.
- Global reads: PO directly, or authenticated coaching staff with current `coaching_work` in any workspace. Client, Sales, unknown and unaffiliated actors are denied direct catalog access. Workspace-owned search, detail/history, override writes, staff video resolution and joins require current `coaching_work` in that same workspace. The client-plan path is the internal resolver of FR-029, reachable only through the F19/P4 wrapper, which validates authenticated-client ownership and a same-workspace published plan/client relation, derives workspace from stored relations, and returns only video values for referenced exercises. It is not a staff catalog endpoint and exposes no direct table/search access. Every denial is generic and no read may expose another workspace's rows, videos, existence, counts or error distinctions. Global search never includes workspace-owned rows or inferable counts. Server-side projections, views, search, detail/history, RPC results, errors, pagination, duplicate candidates and exports null or omit `created_by` and `origin_workspace_id` for every non-PO caller. Only an explicit PO governance read returns provenance.

### S37 (S36-PO-5) field contract

Exercise library detail contains exactly Name, Description, Notes, Video, Alternatives, Default Rest Time, Default RIR and Default Reps. Global and Workspace names require English and permit optional Arabic. Description is one optional value in any language. Alternatives are limited to three unique targets. There is no Instructions field. Keep existing Notes; legacy Instructions are not merged into Notes (S40-PO-5). Optional defaults copy into editable planner entries when added and are never live-linked. Rest Time is 0–600 seconds in 15-second steps; RIR is an integer 0–5; Reps is an integer or range 1–100. Published plans freeze non-video values; Video stays live (S37-PO-1 Q2 = A).
