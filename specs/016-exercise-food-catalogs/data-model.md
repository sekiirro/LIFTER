# F16 Logical Data Model

This is a logical model for implementation planning, subordinate to the approved spec and plan. It defines no SQL syntax or migration implementation.

## Shared invariants

- Identity rows are stable. Every content edit appends an immutable, numbered version; current-version changes use compare-and-set under an identity-row lock.
- Use composite tenant keys and foreign keys for workspace-owned records. Every tenant read and write applies current membership checks plus forced RLS; callers cannot choose a foreign workspace by changing an ID.
- Lifecycle actions are append-only state transitions. `Add` creates identity/version 1; `Edit` appends a version; `Remove` appends a non-destructive inactive marker; `Restore` appends an active marker for the same identity and current content version. Remove is the only catalog-removal action. No lifecycle action deletes or rewrites a content version or breaks plan references. Global Remove/Restore and global merges are PO-only; workspace exercise/variation Remove/Restore require `coaching_work` in the explicitly selected owning workspace.
- Audit is immutable and transactional with a successful write. Audit details contain only allowlisted action/target/version/related IDs and changed-field codes. Global event `workspace_id` is NULL. Never write names, notes, nutrition, URLs, origin, raw operation keys, or free text to audit.
- Store audit-only governance fields (`created_by`, origin workspace where applicable) separately from non-PO read projections. Non-PO global food projections omit creator and origin in data, errors, counts, and search candidates.
- No exercise or food content is seeded. Seed only the approved taxonomy. No import occurs until the PO supplies and approves a dataset after the D16-4 audit.

## Nutrition and duplicate rules

- Nutrition basis is exactly per 100 g or per 100 ml. kcal and protein/carbs/fat are required; fiber is optional. Store decimal-safe values and reject negative values. Serving equivalents must be positive. The validator reports a warning when `abs(stated kcal - 4*protein - 4*carbs - 9*fat) > max(20 kcal, 10% of stated kcal)`; this discrepancy alone never blocks save.
- The full exact duplicate identity key is `(language, normalized name, basis, normalized product identity, normalized preparation identity, weighing state)`. Version duplicate checks reserve/check this full tuple for each localized name in the candidate version; the near-match candidate scope is same basis, normalized name similarity >=90%, kcal tolerance `max(10%, 10 kcal)`, and matching normalized product identity, normalized preparation identity and weighing state. Product/preparation/state dimensions are stored as identity fields rather than inferred only from localized names.
- Candidate comparison uses the versioned Arabic/English normalizer. Similarity threshold is at least 90%; no automatic alias/synonym expansion. Near-match kcal distance must be no more than `max(10%, 10 kcal)` per same basis and matching product/preparation identity and weighing state. Matching basis is required; g and ml are never compared as interchangeable.
- Block genuine catalog duplicates and offer the existing identity. Warn and require explicit confirmation for a near match. Different products/preparations and raw/cooked states remain distinct. Repeating the same food or meal within a plan remains allowed through plan duplicate actions.

## Lifecycle and version references

- Plan snapshots reference explicit `(identity_id, version)` pairs and retain their frozen values. Later catalog edits, Remove, Restore or merge never rewrite a plan snapshot.
- Remove hides the entry from new selection and appends a non-destructive marker; it never cascades to or modifies a client plan, snapshot, log, media reference or historical record. Restore appends an active marker for the same identity and current immutable content version. Food Restore re-reserves exact keys atomically and fails with a duplicate conflict if another active food owns any key.
- Merge is PO-only. It requires an active source, resolves a requested target through `superseded_by` to its active terminal, and atomically flattens direct inbound aliases so chains/cycles cannot form. Existing plan references and published snapshots remain unchanged; new selection resolves to the terminal. Remove and Merge do not refund the rolling food-add quota; they reduce only the active-food count.
- A food version freezes its default-alternative list after validating each target as active and current at write time. Later target Remove/version/Merge leaves the stored list untouched. At use time, F17/F18 planners and UI follow merge aliases to the terminal survivor's current version, skip removed targets while showing a visible `alternative unavailable` state, and never silently substitute another food.
- Exercise variations resolve for the explicitly selected workspace on each authorized read. Cross-workspace mappings are neither returned nor inferable, and workspace video URLs never enter plan snapshots.

## Search and privacy

- `normalize_ar_en_v1` is collation-independent and versioned: Unicode NFC, explicit Arabic/Latin folding, alef/hamza forms, ta marbuta/ha, alef maqsura/ya, diacritic and tatweel removal, and locale-independent case mapping.
- Search filters support muscle group, equipment and food basis; stable ordering and bounded pagination cap page size at 50. Use indexed normalized columns; algorithm changes require forward migrations and new indexes.
- Global reads: PO directly, or authenticated coaching staff with current `coaching_work` in any workspace. Client, Sales, unknown and unaffiliated actors are denied. Workspace-owned search, detail/history, variation, video resolution and planner/export joins require one explicitly selected workspace and current `coaching_work` in that workspace; global search never includes workspace-owned rows or inferable counts. Server-side projections, views, search, detail/history, RPC results, errors, pagination, duplicate candidates and exports null or omit `created_by` and `origin_workspace_id` for every non-PO caller. Only an explicit PO governance read returns provenance. No read may expose another workspace's rows, videos, existence, counts or error distinctions.


## Manual exercise distribution (S35-PO-1, S35-PO-2; FR-022 to FR-032)

Logical model only; no SQL and no migration is created by this specification.

- **Copy = workspace exercise with source provenance.** A copy is an ordinary `workspace_exercises` identity (composite `(workspace_id, id)` key, own versions, own lifecycle) extended with immutable source fields: `source_exercise_id` (global exercise identity) and `source_exercise_version` (the global version copied). Both are NULL for workspace-only exercises (FR-004) and set only by the send RPC. They are written once and never updated. A copy never shares an identity, version row or lifecycle marker with the global exercise or with another workspace's copy.
- **Independence.** Version 1 of the copy is created at send time from the source's current immutable version and the FR-024 relations; later global versions, Remove, Restore or merge never touch it, and copy versions never touch global rows. No foreign key from a global row to a copy exists.
- **Carried content (FR-024).** (a) Exercise data: the source's current `exercise_versions` content, except alternatives. (b) Media link and variation: the target workspace's own non-removed `exercise_variations` mapping for the source identity (URL and/or note), copied as the copy's own media link; the storage form is MCQ-F16-16. (c) Alternatives: the source version's `alternativeExerciseIds`, carried only when valid (active target, not the source, no duplicate); the target form is MCQ-F16-8 and invalid-relation reporting is MCQ-F16-10. No other workspace's mapping is ever read.
- **Active-copy rule.** At most one active (not Removed) copy per `(workspace_id, source_exercise_id)`; enforced under a deterministic creation lock plus a partial unique guard keyed on active state, so concurrent sends produce one copy and the other pair outcome is `skipped_existing`. Removed copies are excluded from the guard; any number of Removed copies may precede the active one. This depends on the workspace-exercise lifecycle revision and Remove marker of PR #43 (T042/T043). Only active sources are eligible (FR-026, S35-PO-2 decision 4); superseded-source redirect: MCQ-F16-9.
- **Fresh resend.** Resending after Remove inserts a new identity with new version 1 from the current global version. The Removed copy, its versions and markers are not modified, restored, merged or aliased to the new copy; plan references to the Removed copy keep resolving to it (FR-027, FR-028).
- **No automation.** No trigger, cron, policy or function other than the send RPC creates copy identities or copy version 1 (FR-025). Authorized manual edits of a copy (FR-004: workspace exercise versioning and lifecycle, including the current-version advance performed by `catalog_write_workspace_exercise`) are ordinary workspace operations and are not copy creation or propagation. The no-seed rule (FR-019) is unchanged.
- **Operation key and ledger.** One client-generated UUIDv4 key per send, bound to the action and the canonical request hash. The ledger result stores every per-pair outcome, including `skipped_existing` and `rejected_inactive_source` (FR-016 replay rule).
- **Audit.** One allowlisted send event per send (FR-029, SC-010): `workspace_id` per MCQ-F16-11, `send_outcomes` detail (UUIDs and outcome codes only). No names, content, URLs or notes. Event name `catalog.exercise_sent` is provisional.
- **Reads.** Copies are visible only through workspace reads with explicit `workspace_id` and current `coaching_work` (FR-030). Global reads are unchanged (FR-012). Planner selection of global identities (S35-PO-2 decision 6) is a register item, not a requirement, until MCQ-F16-13 and MCQ-F16-14 are answered (FR-031 reserved).
