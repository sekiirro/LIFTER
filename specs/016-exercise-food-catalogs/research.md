## F16-specific decisions applied

- Global exercise identity is shared across all workspaces. Workspace video mappings and workspace-only exercises are separate tenant rows; selected-workspace video URLs resolve at read time under authorization.
  - *Superseded in part (S36 round 3, critique F3, F5, F9):* the video value is an override field (FR-003, FR-023, FR-024); canonical video is a new field; the legacy mapping rows are migration history whose write path is retired (FR-031). The identity-sharing rule above still holds.
- Global food identity is shared. New food creation is immediately usable by authorized coaching staff. Food content requires kcal, protein, carbs, and fat per 100 g or 100 ml; fiber is optional; at least one of Arabic or English name is required.
- Versions are immutable and snapshots pin exact versions. Lifecycle actions are Add, Edit, Remove and Restore, represented by append-only content versions and lifecycle markers. Remove is the only staff-facing removal action; existing plan references remain valid.
- Exact duplicate identity includes language, normalized name, basis, canonical product identity, preparation identity and weighing state. Near-duplicate detection uses normalized textual similarity >=90%, no automatic synonym matching, and kcal proximity <= `max(10%, 10 kcal)` per matching 100 g/ml basis, product/preparation identity and weighing state. Genuine duplicates are blocked; different products/preparations and raw/cooked states remain distinct. Kcal-vs-4/4/9 discrepancies over `max(20 kcal, 10% of stated kcal)` warn but do not block saving by themselves.
- D16-10 limits apply to every authorized food creator role: at most 10 new food identities per creator per rolling 24 hours, 100 across all authorized creators per rolling 24 hours, and 10,000 active foods. Enforce counters transactionally under concurrency-safe locks and make exact replay quota-neutral. Benchmark before production; do not claim benchmark evidence in this design phase.
- Global creator and origin workspace metadata are available only to PO governance reads. Every non-PO server-side projection, including errors, duplicate candidates, counts, search, detail/history and exports, must omit or null both fields. Global audit events carry no workspace origin.
- For the final exercise library contract, defaults are optional and consist of Default Rest Time, Default RIR and Default Reps; approved ranges are recorded in the S37 architecture audit below. Food alternatives/default rules remain separate.

### Read-only origin/main evidence

- `supabase/migrations/20261106092000_catalog_workspace_exercises.sql:31-50` defines workspace-scoped `exercise_variations` and append-only `exercise_variation_versions`, each keyed by workspace plus global exercise. This is an explicit per-workspace mapping row, not a copy of the canonical identity.
- `supabase/migrations/20261106112000_catalog_variation_operations.sql:49-52` accepts only `video_url` and legacy `note`, checks those values, and stores a variation payload; lines 75-77 audit changed fields as video/note. It does not implement the new eight-field library. `catalog_write_variation` and `catalog_transition_variation` are granted to authenticated users at lines 82 and 146 (authorization is checked in the function).
- `supabase/migrations/20261106105000_catalog_video_resolution.sql:2-15` defines the shared host validator; the migration and variation write currently accept YouTube, Google Drive, and `docs.google.com` hosts. This is read-only evidence for F16-MCQ-P; no host policy is inferred from the code.
- `supabase/migrations/20261031121000_client_accounts_model.sql:62-69` defines clients with globally unique `email_normalized` and `phone_e164`; lines 83-104 define private identifier claims and restrictive client foreign keys. This confirms identifier release and history retention require an explicit lifecycle mechanism.
- `lib/auth/capabilities.ts:18` lists the `delete_client` capability. The origin/main tracked-code search for `deleteClient`, `delete_client`, “delete client”, `removeClient`, and `archiveClient` found no client-delete action, UI flow, or RPC implementation; matching non-policy references are capability declarations/matrices only. Thus the repository contains authorization vocabulary but no current Delete implementation to verify for identifier release. S36-PO-3 already decides the desired outcome (release email/phone and retain required history); the mechanism stays in residual F16-MCQ-D-R. No new MCQ is raised because the outcome is decided. No production database was accessed.


### Architecture recommendation

Recommend virtual fallback with sparse workspace customization rows. It satisfies each approved behavior above and directly supports automatic appearance of new Global exercises without fan-out or overwriting local values. The existing main schema shares canonical exercise identity and has workspace-scoped variation rows. Its current video resolver returns active matching variation rows and does not fall back to canonical video when no variation exists. A future design can retain the shared-identity/isolation pattern while adding an explicit virtual Global fallback and broadening local customization to exactly the eight fields. This is a technical recommendation only. The video-freeze conflict is not resolved by architecture.
