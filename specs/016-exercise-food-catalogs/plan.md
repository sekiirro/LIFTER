# Implementation Plan: F16 Exercise & Food Catalogs

**Spec**: spec.md (same folder) | **Status**: S38 round 7 spec-only reconciliation of the Sol Medium critique (S37-PO-11). No code, SQL, migration or fixture is part of this round. All F16 product decisions are closed; F16-MCQ-D-R has a pending F11/F12 follow-up (F11 and F12 exclude client deletion) and is out of F16 scope. A7 is dispositioned by this round under S37-PO-11.

## Summary

Keep a PO-only canonical Global Library and expose it in every workspace through independently customizable local values for exactly eight fields. Authorized WO/Trainers edit all eight fields locally. New global exercises appear automatically without overwriting local customizations. Keep global and workspace writes behind both authorization walls and preserve existing food catalog contracts. UI requirements are specified in `spec.md`; this remains a spec-only round, so implementation requires Spec Kit and architect authorization. The formerly open PO decisions are historical: F16 product decisions are closed by S37-PO-1 Q2 and S37-PO-10, and the A7 critique gate by S37-PO-11.

## Technical Context

Next.js App Router on Cloudflare Workers (OpenNext), Supabase Postgres + FORCE RLS, supabase-js with user JWT, the established F12-F15 privilege pattern for writes (SECURITY DEFINER RPCs in `app_private`/`public`, owned exactly like the existing F12-F15 definer functions (no new owner role), with table policies denying all direct client DML and integration tests proving authorized RPC writes succeed and unauthorized ones fail under that owner, `set search_path = ''` with fully qualified objects, EXECUTE revoked from public/anon/service_role and granted only to `authenticated` — except the FR-029 client-plan video resolver, which has no EXECUTE grant in F16; F19/P4 adds the single grant to the principal its wrapper runs as. Every RPC rechecks `auth.uid()`, current membership, capability and expected version; no direct table DML grants; reads through hardened read functions or security-barrier views). `docs/02-architecture.md` now distinguishes invoker-rights reads from the F12-F15 SECURITY DEFINER mutation RPC pattern. Existing `authorize()` + `app_private.role_has_capability` + `has_workspace_access(ws, cap)`, append-only `audit_events`, next-intl AR/EN, Design System, Vitest, Playwright + axe. Free-tier limits: 500 MB DB, 10 ms Worker CPU per request.

## Design

### Database

#### Exercise override data model (design only)

- Add a logical `exercise_overrides` entity keyed by `(workspace_id, exercise_id)` and linked to the one canonical global `exercises.id`; workspace ID is part of all keys, constraints and references. It is a versioned entity with a current-version pointer and append-only `exercise_override_versions` content.
- The workspace customization contains only local values for exactly Name, Description, Notes, Video, Alternatives, Default Rest Time, Default RIR and Default Reps. Global and Workspace names require English and allow optional Arabic; Description is one optional value in any language. Alternatives are limited to three unique targets per exercise. Instructions is removed; legacy exercise rows are deleted at cutover, not migrated, and Instructions is not merged into Notes (S40-PO-5); existing Notes are retained. No field may shadow/change canonical IDs, global taxonomy identity, canonical version history or food data. Preserve the separately defined `workspace_exercises` identities for Trainer-created private exercises.
- Add a nullable canonical `video_url` to immutable global exercise version content (FR-023). No canonical video exists on main (verified 2026-11-06), so this is a new field, not a rename. Workspace video overrides take precedence when configured; otherwise the resolver returns the canonical current video; otherwise explicit absence. The resolver result includes its source (`workspace_override`, `global` or `none`) for authorized presentation. URL validation follows D16-3; `docs.google.com` is disallowed, dummy values are deleted at cutover and have no legacy support path (F16-MCQ-P). Video stays live in published plans and follows the library (F16-MCQ-O).
- Workspace-private exercise versions carry their own nullable `video_url` (FR-024), written only through the workspace exercise write operation.
- No automatic workspace mapping rows are materialized (F16-MCQ-1 answered a; F16-MCQ-2 moot). A workspace alternatives override replaces the global list and may reference workspace-private exercises (F16-MCQ-4 answered c). Global and Workspace names require English and allow optional Arabic; Description is one optional value in any language; Alternatives are capped at three unique targets (S37-PO-10). Do not seed content in this design.
- Mapping creation is virtual (F16-MCQ-1 answered a). Canonical edits are PO-only in the explicit global admin scope (F16-MCQ-5 answered a). Removing a workspace video restores the global fallback (F16-MCQ-6 answered a).

#### Client/plan-workspace read path

- Global templates retain canonical global exercise IDs. The client request supplies the plan and published-version context, not a workspace ID. The F19/P4 client wrapper, not F16, verifies authenticated-client ownership, that the plan belongs to that client in one workspace, and that the published plan/version is viewable. It derives workspace from the persisted plan/client relation and passes only the exercise references of that authorized published plan to the F16 internal resolver (FR-029). The persisted relation does not exist yet (verified: no persisted plan table on main; `origin/019-plan-core` adds no migrations), so the wrapper and its tests are blocked until F19 persistence lands. Because clients never transfer between workspaces (FR-022), that derived workspace is the client's only workspace. This client self-ownership check is separate from staff `coaching_work`; the client path does not grant direct access to override rows, catalog tables or staff search/RPCs.
- Workspace override is the highest-precedence video source; global video is fallback. Include the resolved source in the authorized resolver result. A later workspace video update is reflected on the next view without modifying/re-publishing the global template.
- Apply current tenant membership/access checks and forced RLS at each staff workspace-scoped step. The narrowly scoped client projection uses the authenticated client's Plan Core/P4 ownership check and a same-workspace relation derived from stored plan/client records. Missing, unauthorized, foreign, stale or malformed client/plan scope returns one generic denial shape with no existence, count, identifier or media distinction. Cross-tenant reads must return no partial catalog or media rows.
- The client read path is separate from staff catalog reads. It must not grant clients direct access to catalog tables or staff search RPCs; clients consume plan/template view data only.
- Historical plan identity/content remains preserved. Published plans freeze non-video values (S36-PO-5); Video stays live and follows the authorized library resolution (S37-PO-1 Q2 = A). Video removal restores global fallback for library resolution.

- Tables (global, no `workspace_id`): `exercises(id, created_by, created_at, lifecycle_state, superseded_by)`, `exercise_versions(exercise_id, version, payload columns..., created_by, created_at, unique(exercise_id, version))`, `foods(id, created_by, created_at, lifecycle_state, superseded_by)`, `food_versions(..., product_identity_norm, preparation_identity_norm, weighing_state, ...)`, `food_serving_units(food_version_id, unit_key, label_ar, label_en, basis_qty)`, append-only `catalog_lifecycle_events` for Remove/Restore/merge transitions, versioned taxonomy `taxonomy_terms(id, kind 'muscle_group'|'equipment', code unique)` + immutable `taxonomy_term_versions(term_id, version, label_ar, label_en, lifecycle)`; exercise versions reference term versions (FR-016a).
- Tables (workspace-scoped, `workspace_id` + composite FKs `(workspace_id, id)`): `workspace_exercises` + versions, `exercise_variations(workspace_id, exercise_id, ...)` + versions.
- Forward logical addition (no SQL in this spec task): `exercise_overrides(workspace_id, exercise_id, current_version, lifecycle/revision metadata)` plus immutable `exercise_override_versions(workspace_id, exercise_id, version, Name, Description, Notes, Video, Alternatives, Default Rest Time, Default RIR and Reps customization fields, plus audit metadata)`, and child rows `exercise_override_alternatives` for alternatives of each version (FR-025: one target per row, at most three unique targets, composite key `(workspace_id, workspace_exercise_id)` for private targets, global FK for global targets, targets active at write, frozen with the version). Composite foreign keys bind both workspace and canonical exercise identity. Per-field reset is answered: each customized field returns to Global independently. An empty alternatives list is allowed (F16-MCQ-B, answered a). Description and Alternatives are included in the eight editable fields.
- Current-version pointer: `current_version` on the identity row with composite FK `(id, current_version) -> versions(identity_id, version)`; advanced only by the versioning RPC after `FOR UPDATE` and an expected-version check. Version rows append-only (trigger + revoked grants); identity lifecycle changes use append-only lifecycle markers, including Restore to the same active identity/current version; content versions are never edited or deleted.
- Nutrition storage and validation: per 100 g or 100 ml, store kcal as `numeric(7,1)` (0–999,999.9) and protein/carbohydrate/fat/optional fiber grams as `numeric(7,2)` (0–99,999.99). Require kcal, protein, carbohydrate, and fat; allow fiber to be absent. Reject non-finite, negative, or out-of-range values with field errors and write nothing. Reject when protein + carbohydrate + fat exceeds the 100 g/100 ml reference quantity; equality at 100 is valid, and no tolerance or epsilon applies. Every food has at least one serving unit with a positive exact gram equivalent for a `g` food or ml equivalent for an `ml` food; reject cross-basis conversions. Per-food defaults allow at most THREE validated alternatives. For the separate 4/4/9 kcal discrepancy, warn only above `max(20 kcal, 10% of stated kcal)`; that discrepancy alone never blocks saving (D16-5). Snapshot transport per FR-020 uses decimal strings.
- Search: `app_private.normalize_ar_en_v1(text)` IMMUTABLE, NFC + explicit fold table (FR-015); generated columns `name_norm_ar_v1`, `name_norm_en_v1` on version rows; `pg_trgm` GIN indexes; page size max 50; read via a hardened `catalog_search` function (not audited per call). Workspace name search (F16-MCQ-I(1)(b)) matches canonical and workspace names and returns the effective workspace name; Description search follows the exact eight-field contract. No separate override storage budget (F16-MCQ-I(2)(b)); database size is monitored against the 70% exit trigger.
- Duplicate detection: `catalog_food_name_keys` contains one active exact-key reservation per localized food name and identity: `(lang, name_norm, basis, product_identity_norm, preparation_identity_norm, weighing_state)` is NOT NULL and UNIQUE; `food_id` is the payload, not part of the key. These dimensions implement D16-7b/7c and FR-008: raw/cooked state and genuinely different products/preparations remain distinct. Create inserts all localized keys atomically; a version with unchanged identity dimensions retains them; changed dimensions atomically releases old keys and reserves the new ones, with collision against another active food returning an exact-duplicate conflict. Remove and merge release the source food's active keys. Restore derives keys from the same identity's current immutable version and atomically reserves them with the active lifecycle marker; if another active food owns any key, return an exact-duplicate conflict and leave the food removed. Key locks use a deterministic ordering. Near-duplicate candidates are compared only when language, basis, product/preparation identity, and weighing state match; normalized name similarity is >=90%, with no automatic synonym matching and kcal proximity <=max(10%, 10 kcal) per 100g/100ml. Plan repeats remain allowed through Duplicate actions.
- Lifecycle and merge: Remove is the only catalog removal action; it appends a non-destructive inactive marker, hides the food or exercise from catalog search and prevents new selection. It never cascades to or modifies a client plan, snapshot, log, media reference, or historical record; removal from an existing plan requires an explicit plan-editing action. Restore appends an active marker for the same identity and current immutable content version. Food Restore re-reserves its exact-key rows atomically as described above; a collision leaves it removed. Restore RPCs are `catalog_restore_food` and `catalog_restore_exercise`; global Remove/Restore is PO-only (Restore is a backend/API capability only), while workspace exercise Remove requires `coaching_work` in the explicitly selected owning workspace; workspace exercise Restore is not authorized (S31-PO-1 Q3; T047). Only PO merges global entries. Food versioning additionally checks creator-or-PO on the locked identity. For merge, a superseded target resolves to its active terminal; source must be active; merging a source atomically repoints its direct inbound aliases to that terminal and releases the source's active food keys. Lock every affected identity in UUID order and recheck state; lifecycle operations never rewrite plan references or published snapshots.
- Catalog addition limits: `catalog_addition_limits` keeps transactionally updated usage state for a per-creator limit of 10 new food identities per rolling 24 hours for every authorized creator role (PO, Workspace Owner, Trainer), a platform-wide limit of 100 new identities per rolling 24 hours across those roles, and the 10,000-active-food ceiling. A non-PO Add explicitly selects one current workspace where that creator has `coaching_work`; persist it as immutable `origin_workspace_id` provenance on the food identity and first-version creation record. PO may create directly with NULL origin or select an authorized workspace. Each Add locks the applicable creator and platform usage rows and active-food counter in deterministic order, checks limits after the operation-key replay check, and increments counters only in the same transaction that commits the new identity, key reservations, receipt, and audit event. Concurrent adds therefore cannot pass a stale count; exact idempotent replay consumes no additional quota. Remove and merge decrement active-food usage; Restore checks and increments the active-food ceiling but does not consume an Add allowance. A rejected over-limit request returns a quota-specific failure and writes no food identity/version, key, counter increment, or success audit event. Benchmark before production (D16-10).
- Operation keys: use shared `app_private.operation_keys(actor_user_id, action, operation_key uuid, request_hash, result jsonb, created_at, unique(actor_user_id, operation_key))`; bind each UUIDv4 key to one action and canonical request hash. Same actor/key/action/hash returns the original result; a different action/hash conflicts. Look up after authorization and the ordered resource locks; recheck current authorization after lock waits before returning a replay. Successful mutation, key reservations/counter changes, receipt, and one audit event commit atomically. Rows older than 30 days are purged by the existing cron job.
- Snapshots and export reads: builders use explicit canonical global/workspace exercise identity versions. Published-plan Video is resolved live from the current authorized library value; the other published values remain frozen (F16-MCQ-O, S37-PO-1 Q2 = A). Authorization remains scoped to the plan's workspace (FR-020).
- Audit: existing `audit_events`, two-segment action names (`catalog.food_created`, `catalog.food_versioned`, `catalog.food_merged`, `catalog.exercise_versioned`, `catalog.taxonomy_versioned`, ...), `workspace_id` NULL for global, allowlisted details only (FR-013).

### Authorization (two walls)

- No new capability (round 3, FR-033). PO-only checks use `app_private.is_platform_owner()`; workspace checks use `app_private.has_workspace_access(workspace_id, 'coaching_work')`. The earlier proposal to add `govern_global_catalog` through a fifth redefinition of `app_private.role_has_capability` is withdrawn: it would have been a PO-only check that already exists, and no capability named `govern_global_catalog` exists on main (verified 2026-11-06).
- New SECURITY DEFINER helper `app_private.can_read_global_coaching_content()` = caller is PO (direct, regardless of membership; F14 FR-001 global-access precedent) OR holds `coaching_work` in at least one current workspace membership. RLS on global tables: SELECT if helper; no direct INSERT/UPDATE/DELETE grants (RPC only). F17/F18 reuse this helper for global templates.
- Workspace tables: RLS `has_workspace_access(workspace_id, 'coaching_work')`. Override reads and writes use the same forced-RLS workspace predicate; a global exercise ID never bypasses workspace scope. Client-plan resolution derives the client's workspace from a trusted relationship and rechecks current authorization; generic denial must not distinguish missing from foreign IDs. Never allow direct client DML or client access to staff catalog search.
- Override reads and writes use the same forced-RLS predicate for the same explicit workspace (consolidated with the workspace-table rule above; round 3 removes the duplicate paragraph).
- Global food creator and origin provenance (`created_by`, `origin_workspace_id`) is returned only by an explicit PO-only governance read. Every other server-side read path MUST null or omit both fields for every non-PO caller, including RPC projections, views, search, detail/history, duplicate candidates, pagination/counts, errors and any exports; base tables are not granted to `authenticated` directly. Security-barrier views and RPC projection builders enforce the mask, not client code. Name the negative test `global_food_provenance_masking_non_po` and verify each read path returns neither value; name the positive test `global_food_provenance_po_governance_read` and verify PO governance can see both values.
- Every mutation RPC has an explicit authorization scope. The action identifiers below are documentation labels mapped to the existing checks of FR-033: `catalog_create_food` -> `catalog.food.create` (PO directly, or WO/Trainer with current `coaching_work` in one explicitly selected workspace; persist that workspace as immutable food-origin provenance); `catalog_version_food` -> `catalog.food.version` (PO or the recorded creator of the locked identity); food Remove/Restore/Merge -> `catalog.food.govern` (PO only); global exercise create/Remove/Restore/Merge -> `catalog.exercise.govern` (PO only); canonical exercise versioning -> `catalog.exercise.govern` (PO only, explicit global admin scope; F16-MCQ-5 answered a); workspace exercise create/version/Remove -> `catalog.workspace_exercise.write` (PO, WO, or Trainer with current `coaching_work` in the explicitly supplied workspace; workspace Restore is not authorized, S31-PO-1 Q3); override create/version/Remove -> `catalog.workspace_override.write` with explicit workspace, CAS and the same scope; taxonomy versioning -> `catalog.taxonomy.version` (PO only). Reads are explicit too: global search/detail/history -> `catalog.read.global` (PO directly, or current `coaching_work` in at least one workspace); workspace exercise/override detail/history -> `catalog.read.workspace` plus a required `workspace_id` and current `coaching_work` in that workspace; staff video resolution -> `catalog.read.workspace_video` plus the explicitly selected, currently authorized workspace. Client plan video projection uses a separate authenticated-client self-ownership check through the Plan Core/P4 boundary, derives workspace from stored plan/client relations, and limits results to exercises referenced by the authorized published plan. Sales, unaffiliated staff, and unauthenticated actors are denied; clients receive no staff catalog operation or direct table access. Every service/RPC MUST authorize before validation and recheck current role, membership, plan ownership and scope after lock waits.

Mutation ordering is canonical across F16 writers: authorize action and explicit scope -> lock affected identity roots in UUID order (or deterministic identity/key creation locks when the root does not yet exist) -> lock exact-food-key hashes and any applicable addition-limit rows in deterministic order -> look up the shared idempotency ledger -> on an exact replay, recheck current authorization after lock waits before returning the stored result; otherwise re-read expected version, lifecycle, key ownership, membership, and creator rights -> validate input and quota -> atomically write immutable version/lifecycle changes, active key reservations, quota counters, idempotency result, and one audit event.
