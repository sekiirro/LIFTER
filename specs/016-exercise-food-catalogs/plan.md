# Implementation Plan: F16 Exercise & Food Catalogs

**Spec**: spec.md (same folder) | **Status**: Spec-only redesign plan. Existing F16 catalog implementation is historical context; this document designs the forward-compatible shared-global-catalog/workspace-override changes. No implementation or migration file is part of this plan-only change. The eight open decisions in `decision-register.md` constrain implementation details and are not answered here.

## Summary

Retain the global exercise identity and food catalog, expose the shared exercise catalog in each workspace through an independent versioned override, retain workspace-private exercises, and resolve exercise video for client views using the client's workspace at read time. Keep global and workspace writes behind both authorization walls and preserve existing food catalog contracts. UI requirements are specified in `spec.md`; implementation remains blocked by the open PO decisions.

## Technical Context

Next.js App Router on Cloudflare Workers (OpenNext), Supabase Postgres + FORCE RLS, supabase-js with user JWT, the established F12-F15 privilege pattern for writes (SECURITY DEFINER RPCs in `app_private`/`public`, owned exactly like the existing F12-F15 definer functions (no new owner role), with table policies denying all direct client DML and integration tests proving authorized RPC writes succeed and unauthorized ones fail under that owner, `set search_path = ''` with fully qualified objects, EXECUTE revoked from public/anon/service_role and granted only to `authenticated`, every RPC rechecking `auth.uid()`, current membership, capability and expected version; no direct table DML grants; reads through hardened read functions or security-barrier views). `docs/02-architecture.md` now distinguishes invoker-rights reads from the F12-F15 SECURITY DEFINER mutation RPC pattern. Existing `authorize()` + `app_private.role_has_capability` + `has_workspace_access(ws, cap)`, append-only `audit_events`, next-intl AR/EN, Design System, Vitest, Playwright + axe. Free-tier limits: 500 MB DB, 10 ms Worker CPU per request.

## Design

### Database

#### Exercise override data model (design only)

- Add a logical `exercise_overrides` entity keyed by `(workspace_id, exercise_id)` and linked to the one canonical global `exercises.id`; workspace ID is part of all keys, constraints and references. It is a versioned entity with a current-version pointer and append-only `exercise_override_versions` content.
- The logical version payload contains only the allowlisted override attributes: optional workspace name, description, instructions, video URL and alternatives. No field may shadow/change canonical IDs, global taxonomy identity, canonical version history or food data. Preserve the separately defined `workspace_exercises` identities for Trainer-created private exercises.
- Model the global exercise video as a canonical global value available to fallback resolution. Workspace video overrides take precedence when configured; otherwise resolution returns the global video. The resolver result includes its source (`workspace_override` or `global`) for authorized presentation. URL validation follows the current HTTPS YouTube/Drive allowlist.
- Exact materialization and initial value of auto-created workspace mappings, and how alternatives combine with global alternatives, remain blocked by F16-MCQ-1, -2 and -4. Do not select a physical default or seed content in this design.
- Mapping creation/removal and PO canonical edit questions remain blocked by F16-MCQ-1/-2/-5/-6. No implementation default is implied by the logical model.

#### Client/plan-workspace read path

- Global templates retain canonical global exercise IDs. The client request supplies the plan and published-version context, not a workspace ID. The Plan Core/P4 client boundary verifies authenticated-client ownership, that the plan belongs to that client in one workspace, and that the published plan/version is viewable. The projection derives workspace from the persisted plan/client relation, then resolves only exercises referenced by that authorized published plan. This client self-ownership check is separate from staff `coaching_work`; the client path does not grant direct access to override rows, catalog tables or staff search/RPCs.
- Workspace override is the highest-precedence video source; global video is fallback. Include the resolved source in the authorized resolver result. A later workspace video update is reflected on the next view without modifying/re-publishing the global template.
- Apply current tenant membership/access checks and forced RLS at each staff workspace-scoped step. The narrowly scoped client projection uses the authenticated client's Plan Core/P4 ownership check and a same-workspace relation derived from stored plan/client records. Missing, unauthorized, foreign, stale or malformed client/plan scope returns one generic denial shape with no existence, count, identifier or media distinction. Cross-tenant reads must return no partial catalog or media rows.
- The client read path is separate from staff catalog reads. It must not grant clients direct access to catalog tables or staff search RPCs; clients consume plan/template view data only.
- Historical plan identity/content remains preserved. Do not decide historical rendering of non-video override values (F16-MCQ-3) or behavior after explicit override removal (F16-MCQ-6).

- Tables (global, no `workspace_id`): `exercises(id, created_by, created_at, lifecycle_state, superseded_by)`, `exercise_versions(exercise_id, version, payload columns..., created_by, created_at, unique(exercise_id, version))`, `foods(id, created_by, created_at, lifecycle_state, superseded_by)`, `food_versions(..., product_identity_norm, preparation_identity_norm, weighing_state, ...)`, `food_serving_units(food_version_id, unit_key, label_ar, label_en, basis_qty)`, append-only `catalog_lifecycle_events` for Remove/Restore/merge transitions, versioned taxonomy `taxonomy_terms(id, kind 'muscle_group'|'equipment', code unique)` + immutable `taxonomy_term_versions(term_id, version, label_ar, label_en, lifecycle)`; exercise versions reference term versions (FR-016a).
- Tables (workspace-scoped, `workspace_id` + composite FKs `(workspace_id, id)`): `workspace_exercises` + versions, `exercise_variations(workspace_id, exercise_id, ...)` + versions.
- Forward logical addition (no SQL in this spec task): `exercise_overrides(workspace_id, exercise_id, current_version, lifecycle/revision metadata)` plus immutable `exercise_override_versions(workspace_id, exercise_id, version, name override, description override, instructions override, video override, alternatives override, audit metadata)`. Composite foreign keys bind both workspace and canonical exercise identity. Exact null/clear/materialization and alternative-composition semantics are blocked by the MCQs above.
- Current-version pointer: `current_version` on the identity row with composite FK `(id, current_version) -> versions(identity_id, version)`; advanced only by the versioning RPC after `FOR UPDATE` and an expected-version check. Version rows append-only (trigger + revoked grants); identity lifecycle changes use append-only lifecycle markers, including Restore to the same active identity/current version; content versions are never edited or deleted.
- Nutrition storage and validation: per 100 g or 100 ml, store kcal as `numeric(7,1)` (0–999,999.9) and protein/carbohydrate/fat/optional fiber grams as `numeric(7,2)` (0–99,999.99). Require kcal, protein, carbohydrate, and fat; allow fiber to be absent. Reject non-finite, negative, or out-of-range values with field errors and write nothing. Reject when protein + carbohydrate + fat exceeds the 100 g/100 ml reference quantity; equality at 100 is valid, and no tolerance or epsilon applies. Every food has at least one serving unit with a positive exact gram equivalent for a `g` food or ml equivalent for an `ml` food; reject cross-basis conversions. Per-food defaults allow at most THREE validated alternatives. For the separate 4/4/9 kcal discrepancy, warn only above `max(20 kcal, 10% of stated kcal)`; that discrepancy alone never blocks saving (D16-5). Snapshot transport per FR-020 uses decimal strings.
- Search: `app_private.normalize_ar_en_v1(text)` IMMUTABLE, NFC + explicit fold table (FR-015); generated columns `name_norm_ar_v1`, `name_norm_en_v1` on version rows; `pg_trgm` GIN indexes; page size max 50; read via a hardened `catalog_search` function (not audited per call).
- Duplicate detection: `catalog_food_name_keys` contains one active exact-key reservation per localized food name and identity: `(lang, name_norm, basis, product_identity_norm, preparation_identity_norm, weighing_state)` is NOT NULL and UNIQUE; `food_id` is the payload, not part of the key. These dimensions implement D16-7b/7c and FR-008: raw/cooked state and genuinely different products/preparations remain distinct. Create inserts all localized keys atomically; a version with unchanged identity dimensions retains them; changed dimensions atomically releases old keys and reserves the new ones, with collision against another active food returning an exact-duplicate conflict. Remove and merge release the source food's active keys. Restore derives keys from the same identity's current immutable version and atomically reserves them with the active lifecycle marker; if another active food owns any key, return an exact-duplicate conflict and leave the food removed. Key locks use a deterministic ordering. Near-duplicate candidates are compared only when language, basis, product/preparation identity, and weighing state match; normalized name similarity is >=90%, with no automatic synonym matching and kcal proximity <=max(10%, 10 kcal) per 100g/100ml. Plan repeats remain allowed through Duplicate actions.
- Lifecycle and merge: Remove is the only catalog removal action; it appends a non-destructive inactive marker, hides the food or exercise from catalog search and prevents new selection. It never cascades to or modifies a client plan, snapshot, log, media reference, or historical record; removal from an existing plan requires an explicit plan-editing action. Restore appends an active marker for the same identity and current immutable content version. Food Restore re-reserves its exact-key rows atomically as described above; a collision leaves it removed. Restore RPCs are `catalog_restore_food`, `catalog_restore_exercise`, and `catalog_restore_workspace_exercise`; global Remove/Restore is PO-only, while workspace exercise Remove/Restore requires `coaching_work` in the explicitly selected owning workspace. Only PO merges global entries. Food versioning additionally checks creator-or-PO on the locked identity. For merge, a superseded target resolves to its active terminal; source must be active; merging a source atomically repoints its direct inbound aliases to that terminal and releases the source's active food keys. Lock every affected identity in UUID order and recheck state; lifecycle operations never rewrite plan references or published snapshots.
- Catalog addition limits: `catalog_addition_limits` keeps transactionally updated usage state for a per-creator limit of 10 new food identities per rolling 24 hours for every authorized creator role (PO, Workspace Owner, Trainer), a platform-wide limit of 100 new identities per rolling 24 hours across those roles, and the 10,000-active-food ceiling. A non-PO Add explicitly selects one current workspace where that creator has `coaching_work`; persist it as immutable `origin_workspace_id` provenance on the food identity and first-version creation record. PO may create directly with NULL origin or select an authorized workspace. Each Add locks the applicable creator and platform usage rows and active-food counter in deterministic order, checks limits after the operation-key replay check, and increments counters only in the same transaction that commits the new identity, key reservations, receipt, and audit event. Concurrent adds therefore cannot pass a stale count; exact idempotent replay consumes no additional quota. Remove and merge decrement active-food usage; Restore checks and increments the active-food ceiling but does not consume an Add allowance. A rejected over-limit request returns a quota-specific failure and writes no food identity/version, key, counter increment, or success audit event. Benchmark before production (D16-10).
- Operation keys: use shared `app_private.operation_keys(actor_user_id, action, operation_key uuid, request_hash, result jsonb, created_at, unique(actor_user_id, operation_key))`; bind each UUIDv4 key to one action and canonical request hash. Same actor/key/action/hash returns the original result; a different action/hash conflicts. Look up after authorization and the ordered resource locks; recheck current authorization after lock waits before returning a replay. Successful mutation, key reservations/counter changes, receipt, and one audit event commit atomically. Rows older than 30 days are purged by the existing cron job.
- Snapshots and export reads: builders use explicit canonical global/workspace exercise identity versions. Workspace video mappings are resolved dynamically for the plan's explicitly authorized workspace and never enter plan-version snapshots or stored exports (FR-020).
- Audit: existing `audit_events`, two-segment action names (`catalog.food_created`, `catalog.food_versioned`, `catalog.food_merged`, `catalog.exercise_versioned`, `catalog.taxonomy_versioned`, ...), `workspace_id` NULL for global, allowlisted details only (FR-013).

### Authorization (two walls)

- New capability `govern_global_catalog` -> PO only (extend `app_private.role_has_capability`; forward migration, never edit pushed ones).
- New SECURITY DEFINER helper `app_private.can_read_global_coaching_content()` = caller is PO (direct, regardless of membership; F14 FR-001 global-access precedent) OR holds `coaching_work` in at least one current workspace membership. RLS on global tables: SELECT if helper; no direct INSERT/UPDATE/DELETE grants (RPC only). F17/F18 reuse this helper for global templates.
- Workspace tables: RLS `has_workspace_access(workspace_id, 'coaching_work')`. Override reads and writes use the same forced-RLS workspace predicate; a global exercise ID never bypasses workspace scope. Client-plan resolution derives the client's workspace from a trusted relationship and rechecks current authorization; generic denial must not distinguish missing from foreign IDs. Never allow direct client DML or client access to staff catalog search.
- Overrides: forced RLS and every read/write predicate require `has_workspace_access(workspace_id, 'coaching_work')` for the same explicit workspace. A global exercise ID never bypasses workspace scope. Client-plan resolution derives the client's workspace and rechecks authorization in the client/plan read contract; generic denial must not distinguish missing from foreign IDs. Never allow direct client DML or client access to staff catalog search.
- Global food creator and origin provenance (`created_by`, `origin_workspace_id`) is returned only by an explicit PO-only governance read. Every other server-side read path MUST null or omit both fields for every non-PO caller, including RPC projections, views, search, detail/history, duplicate candidates, pagination/counts, errors and any exports; base tables are not granted to `authenticated` directly. Security-barrier views and RPC projection builders enforce the mask, not client code. Name the negative test `global_food_provenance_masking_non_po` and verify each read path returns neither value; name the positive test `global_food_provenance_po_governance_read` and verify PO governance can see both values.
- Every mutation RPC has an explicit authorization action and scope: `catalog_create_food` -> `catalog.food.create` (PO directly, or WO/Trainer with current `coaching_work` in one explicitly selected workspace; persist that workspace as immutable food-origin provenance); `catalog_version_food` -> `catalog.food.version` (PO or the recorded creator of the locked identity); food Remove/Restore/Merge -> `catalog.food.govern` (PO only); global exercise create/Remove/Restore/Merge -> `catalog.exercise.govern` (PO only); canonical exercise versioning remains PO-DECISION-NEEDED F16-MCQ-5; workspace exercise create/version/Remove/Restore -> `catalog.workspace_exercise.write` (PO, WO, or Trainer with current `coaching_work` in the explicitly supplied workspace); override create/version/Remove -> `catalog.workspace_override.write` with explicit workspace, CAS and the same scope; taxonomy versioning -> `catalog.taxonomy.version` (PO only). Reads are explicit too: global search/detail/history -> `catalog.read.global` (PO directly, or current `coaching_work` in at least one workspace); workspace exercise/override detail/history -> `catalog.read.workspace` plus a required `workspace_id` and current `coaching_work` in that workspace; staff video resolution -> `catalog.read.workspace_video` plus the explicitly selected, currently authorized workspace. Client plan video projection uses a separate authenticated-client self-ownership check through the Plan Core/P4 boundary, derives workspace from stored plan/client relations, and limits results to exercises referenced by the authorized published plan. Sales, unaffiliated staff, and unauthenticated actors are denied; clients receive no staff catalog operation or direct table access. Every service/RPC MUST authorize before validation and recheck current role, membership, plan ownership and scope after lock waits.

### RPCs (SECURITY DEFINER per the established pattern above)

Mutation RPCs: `catalog_create_food`, `catalog_version_food`, `catalog_remove_food`, `catalog_restore_food`, `catalog_merge_food`, `catalog_create_exercise`, `catalog_version_exercise`, `catalog_remove_exercise`, `catalog_restore_exercise`, `catalog_merge_exercise`, `catalog_write_workspace_exercise`, `catalog_remove_workspace_exercise`, `catalog_restore_workspace_exercise`, `catalog_write_variation`, and `catalog_version_taxonomy_term`. Reads: `catalog_search(kind, query, filters, cursor, workspace_id)`, hardened detail/history reads, and workspace-scoped video resolution. For global food/exercise search, authorize by global role and do not return workspace-owned rows. Any workspace exercise, override or variation search requires one explicit `workspace_id` and current `has_workspace_access(workspace_id, 'coaching_work')`; missing/unauthorized scope returns no workspace rows or inferable counts. Never combine unscoped workspace results into global search.

All workspace-owned reads carry the same explicit workspace through search, detail/history, override reads, video resolution and planner/export joins. Staff cannot substitute another workspace ID: current membership and FORCE RLS are checked on every read. Export reads use the authorized plan's `workspace_id`; global catalog fields use the global role rule, while workspace exercise/video data is joined only from that workspace. Clients do not receive staff catalog access; an authorized client-plan view resolves exercise video through the separate client/plan read path above while retaining plan snapshot content. No read returns or signals another workspace's exercise, override, video URL/note, row existence, candidate, count or error distinction. Workspace video URLs remain dynamic and are never stored in plan snapshots or exports.

#### Override write/remove contracts (design only)

- Add an override write RPC contract for create/update and a separate remove/clear RPC contract, using the repository's existing CAS, actor/action-bound idempotency, deterministic lock ordering, post-lock authorization recheck, transactionally appended audit event, and generic error conventions described above and in `contracts/catalog-api.md`.
- Writes require the explicit workspace and canonical exercise identity, expected current override revision/version where applicable, allowlisted fields only, and a UUIDv4 operation key. WO/Trainer may act only in their current authorized workspace. PO workspace-scoped writes affect that workspace's override only. Canonical edits require a distinct global governance operation and remain PO-DECISION-NEEDED F16-MCQ-5.
- Removal does not decide whether a workspace video returns to global fallback or no video (F16-MCQ-6); that externally observable behavior is blocked. The API contract may define generic authorization and concurrency behavior without defining the unresolved product outcome.
- Exact RPC names/argument shapes are reserved for implementation planning after MCQ resolution; do not freeze a speculative signature in this spec-only change.

#### Migration plan (design only; no files)

1. After MCQ resolution, inventory existing global exercise canonical video payload and workspace variation rows; write an explicit forward-only compatibility map from current variation/note state into the new override model. Do not edit any pushed migration.
2. Introduce versioned workspace override storage with composite workspace/canonical-identity constraints, current-version CAS, immutable versions, audit allowlist and forced RLS.
3. Add/extend global video representation and an authorized resolver returning `{video, source}` under workspace-override-then-global precedence. Backfill/automatic mapping behavior must wait for MCQ-1/-2; no backfill default is selected here.
4. Add the staff override RPCs and separate client/plan-workspace resolver/read path with generic denial, keeping the existing staff API boundary intact.
5. Rehearse an upgrade from every supported deployed schema state, then fresh replay, policy/privilege audit, tenant mutation tests and snapshot/history compatibility before any implementation merge. Version number and migration files are implementation-time work; none are created in this feature-spec task.

Mutation ordering is canonical across F16 writers: authorize action and explicit scope -> lock affected identity roots in UUID order (or deterministic identity/key creation locks when the root does not yet exist) -> lock exact-food-key hashes and any applicable addition-limit rows in deterministic order -> look up the shared idempotency ledger -> on an exact replay, recheck current authorization after lock waits before returning the stored result; otherwise re-read expected version, lifecycle, key ownership, membership, and creator rights -> validate input and quota -> atomically write immutable version/lifecycle changes, active key reservations, quota counters, idempotency result, and one audit event. A reused key with a different action/hash conflicts. Stale versions and duplicate/quota conflicts write no partial state. Merge locks all affected identity roots and key rows in deterministic order, resolves the target to its active terminal, and rejects cycles/chains.
