## 1. Scope and non-goals

- In scope: the mechanism, controls and test plan for deleting **verified synthetic legacy mock package rows** (rows of `packages` together with their offers in `package_offers` and terms in `package_versions`) on a named stack, by an operator, outside `supabase/migrations`.
- Out of scope: the four-category initialization subtask of T065 (a separate forward migration with its own review — never entangled with the teardown script); T064/T064a (already implemented: read-only preflight `app_private.package_c5_preflight(uuid[])`, migrations `20261121100000`/`20261121110000_v2`); T070 (post-implementation acceptance review, unchanged); retirement of future real packages (FR-023, T076).
- This document authorizes nothing by itself. Execution additionally requires: the independent review PASS (section 8), a recorded preflight output with `deletable = true`, and the run-record procedure of control A4.

## 2. Requirements this design must satisfy

- **FR-006** (spec.md:301): every published version rejects update/delete/truncate for every role including PO, `service_role` and `postgres` under installed guards; all term changes are new versions; the only carve-out is the PO-approved C5 operator teardown of verified synthetic mock rows (S61-PO-2 Q3=A: transient owner-only single-transaction trigger disablement under the T064b controls is not a guard exception); no application role, migration or standing code path may delete a published version.
- **FR-028** (spec.md:323): preflight-verified synthetic-only status and complete dependency enumeration; refuse/escalate on unknown dependency state, non-synthetic data, or required financial/audit dependency **before writes**; deletion only after the preflight reports the explicit allow-list `deletable = true` (status `clean` or `refused`, never `escalate`; only refusal code `attached_offers_or_versions`; NULL/empty input never deletable); preserve required client, financial and audit history; partial completion not accepted; the path MUST NOT disable or weaken general immutability, audit, RLS or restrictive-reference protections, nor cascade into protected dependencies; explicit and limited to the verified mock target set.
- **S61-PO-2** (docs/04-changes-and-questions.md:1629, verbatim `Teardown Q1=A, Q2=A, Q3=A`): Q1=A audit rows that merely name a mock do not block; only client, registration-link and financial references block. Q2=A the offer update guard may be disabled for the single `current_version_id := NULL` statement under the T064b controls. Q3=A transient owner-only, single-transaction trigger disablement by the operator script is not a "guard exception".
- **SC-019** (spec.md:376): 100% of unsafe preflight cases refuse with zero writes; the complete deletable synthetic-only case deletes obsolete mocks preserving required history.
- **Constitution 1.19.0**: published package versions and catalog entries are immutable; audit history is append-only and tamper-resistant; encrypted backups with periodic restore test (D-14); high-risk work (security, RLS, migrations, financial logic) requires independent review and executed mutation tests; development uses synthetic data only; pushed migrations are never edited (S32-R1).

## 3. Installed protections the design must leave intact

Verified in `supabase/migrations/20261029120000_packages.sql`, `20261111170857_packages_tier_rank.sql`, `20261118000000_f9_package_markets_types_currency.sql`:

- Guards: `packages_no_delete`, `package_offers_no_delete`, `package_versions_no_delete` (BEFORE DELETE → `app_private.forbid_delete()`, raises 23514); `packages_no_truncate`, `package_offers_no_truncate`, `package_versions_no_truncate` (BEFORE TRUNCATE); `packages_no_update`, `package_versions_no_update` (BEFORE UPDATE → `audit_events_immutable()`); `package_offers_guard` (BEFORE UPDATE, live definition redefined by the tier-rank migration: identity/duration/tier_rank immutable + `set_package_pricing` authorization); `package_versions_insert_guard`, `package_versions_market_guard`, `package_offers_z_category_guard`; audit triggers `audit_packages`, `audit_package_versions`, `audit_package_offers` → `audit_row_change()`.
- RLS: all three tables are `ENABLE`/`FORCE ROW LEVEL SECURITY` with all privileges revoked from `public`, `anon`, `authenticated`, `service_role`; only a `BYPASSRLS`/superuser owner role can write.
- Restrictive references: every FK into the package tables is `ON DELETE RESTRICT` (none cascade); the `package_offers.current_version_id` → `package_versions` cycle is two composite, non-deferrable FKs. Downstream restrictive dependents: `registration_links`, `clients`, `subscriptions`, `subscription_renewals`, `subscription_upgrades`, and installments/payment events/activations/renewal-date revisions transitively through subscriptions.
- Audit: `audit_events` is append-only (`audit_events_immutable`, `audit_events_no_truncate`), references packages by soft `(target_table, target_id)` with no FK.
- Precedent: `supabase/cleanup/20261111_t077_legacy_package_offers.sql` (operator script, one trigger disabled inside one transaction) — shape precedent only, not a dependency check.

## 4. Mechanism decision

| Id | Mechanism | Verdict |
| --- | --- | --- |
| M1 | Bypass flag/branch inside `forbid_delete()` or the immutability guards | REJECTED — a standing guard exception; unauthorized (FR-006/FR-028), widens every caller's surface |
| M2 | SECURITY DEFINER RPC or any API/job-reachable delete path | REJECTED — a runtime delete path for application roles violates FR-006 ("no application role … may delete a published version") |
| M3 | One-shot operator script, executed by hand as the database owner on a named stack, in ONE transaction, transiently disabling only the three named per-table delete triggers (and, for the single `current_version_id := NULL` statement only, `package_offers_guard`), deleting in FK order by explicit allow-list, re-enabling and asserting guard state before COMMIT | SELECTED — exactly the shape PO Q2=A/Q3=A authorize; no migration runs on `db reset`/deploy; no standing code path; no API surface |
| M4 | Fail-closed refusal (no deletion unless everything is provably clean) | MANDATORY DEFAULT at every decision point, nested inside M3 — refusal is the default outcome; deletion happens only when every control in section 5 passes |

Migration is forbidden for the teardown (a migration would run on every reset/deploy); the script lives outside `supabase/migrations` (like `supabase/cleanup/`).

## 5. Normative controls

### A. Actor authority
- A1. Executed only by the database owner (`postgres` on LIFTER stacks) running the reviewed script file by hand with `psql --single-transaction -v ON_ERROR_STOP=1`. The role must have `BYPASSRLS` (or superuser) because the tables are FORCE RLS — asserted, fail-closed, before any write.
- A2. Not callable by `anon`, `authenticated`, `service_role`, PO, WO or any job/API: no `SECURITY DEFINER`, no new function, no new grant, no RPC. Verified by catalog diff before/after in tests.
- A3. Only the owner can disable a trigger or reach the tables at all; the script never creates any persistent capability.
- A4. **Run record (out-of-band, recorded BEFORE execution)**: UTC timestamp; operator identity; reviewer identity and `review_ref` pointing at the recorded independent-review PASS of this design; the script artifact's content hash (the operator runs exactly the reviewed artifact); stack identity; the preflight allow-list output (`deletable = true`) with its capture timestamp; per-table before-counts. The script refuses without a valid `run_id`/`review_ref` (format-pinned); binding `review_ref` → allow-list → run record is verified by the procedure and re-checked by the reviewer, not left to script comments.
- A5. Stack identity: cluster-unique `pg_control_system().system_identifier`, captured on the target stack and passed as `expected_stack_id`; mismatch refuses. `current_database()` is never an identity signal. Where the owner genuinely cannot call `pg_control_system()`, an owner-maintained `lifter.stack_id` database setting is acceptable **only if the run record states which mechanism was used**; silent fallback is a divergence (section 9, D3).
- A6. Any non-local stack additionally requires explicit PO approval and a backup **with a verified restore test** (D-14) recorded in the run record before the run. Local stack A–D runs still record the run record; no teardown is authorized to run against production data ever, and development uses synthetic data only.

### B. Workspace scope and target selection
- B1. Input is an explicit allow-list of `packages.id` values taken from a captured preflight output that reports `deletable = true`. No pattern, name or wildcard selection at delete time; NULL/empty input refuses.
- B2. Scope key is the package id. Legacy mocks have `workspace_id IS NULL` and one legacy package may hold offers in several workspaces: offers and versions are enumerated across ALL workspaces by composite `(workspace_id, id)`; the package DELETE additionally asserts `workspace_id IS NULL` on every deleted row.
- B3. Because the schema has no synthetic marker, every workspace holding an offer/version of a target (the preflight `workspace_ids`) must be independently verified synthetic and recorded in the run record; the operator's verified workspace list must EQUAL the preflight set exactly (superset and subset both refuse).
- B4. Real catalog rows are structurally excluded: `workspace_id` set, any version with `market` set, or any offer with `available = true` is refused by the preflight (`real_catalog_row`) and re-asserted under the lock.
- B5. A shared package across ≥2 workspaces is deletable only when EVERY such workspace is verified; otherwise refuse — no partial teardown of a shared package's rows.

### C. Dependency completeness and restrictive references — without weakening the guards
- C1. The only deletable configuration is the preflight contract itself: `deletable = true`, i.e. every dependent row in the whole FK graph is one of the targets' own offers/versions (refusal code `attached_offers_or_versions`). Any registration link, client, subscription, renewal, upgrade, installment, payment-event, or other FK-dependent row refuses (`required_financial_dependency` / required categories). Any audit row belonging to a client/financial dependent refuses (`required_audit_dependency`, Q1=A); audit rows merely naming a mock are reported and do not block.
- C2. Dependents are enumerated catalog-driven from `pg_constraint` (transitive walk from the three package tables), so a table added later is detected. Package-id-shaped columns with no FK edge, and target package/offer/version ids found inside `json`/`jsonb`/`uuid[]`/`text` columns, escalate (`unknown_dependency_state`) — never guessed safe. A caller that cannot see the rows refuses (`caller_cannot_see_rows`).
- C3. FKs stay enabled, validated, and `RESTRICT`/`NO ACTION`: no `CASCADE`, no `TRUNCATE`, no deferrability changes, no FK dropped/recreated. Constraint definitions are hash-compared before/after; any change refuses.
- C4. Transient trigger disablement is bounded exactly by PO Q2=A/Q3=A: only the three per-table `*_no_delete` row triggers, each disabled only around its own table's single DELETE statement and re-enabled immediately after; and only `package_offers_guard`, only for the single `UPDATE package_offers SET current_version_id = NULL` on target offers, re-enabled **before the first DELETE**. `DISABLE TRIGGER ALL/USER`, `session_replication_role = 'replica'`, and disabling any truncate, update-immutability, insert/market/category or audit trigger are forbidden. Trigger DDL is transactional and rolls back with the transaction.
- C5. The current-version UPDATE asserts: row-count equality, `available = false` on every target offer, and that **no column other than `current_version_id` changed** (row-json comparison against a before-snapshot).
- C6. Before any change: `session_replication_role` must be `origin` (refuse otherwise; the script itself issues only `SET LOCAL … = 'origin'`); every non-internal trigger on the four tables must match the expected allow-list at `tgenabled = 'O'` — any extra, missing or pre-disabled trigger refuses (never "repair"); every internal trigger must belong to a validated FK constraint with an `RI_FKey_*` function; no rewrite rules on the four tables; no unvalidated FK on/onto them; every FK into the package tables is `RESTRICT`/`NO ACTION`.
- C7. The expected trigger allow-list is re-derived from the target stack's current migration state before each run, pinned in the run record, and asserted exactly — a trigger added by a later feature blocks the run until the list and script are re-reviewed.
- C8. Guard function bodies are hash-compared before/after (`forbid_delete`, `audit_events_immutable`, all package guard functions, `audit_row_change`, preflight): nothing may be altered mid-run; any change refuses.
- C9. Locking: `LOCK TABLE packages, package_offers, package_versions IN EXCLUSIVE MODE` in fixed order with a positive `lock_timeout`, then the preflight is re-run under the lock and must equal the reviewed allow-list exactly (set-equality, deletable, synthetic-only). EXCLUSIVE conflicts with the ROW SHARE lock of FK checks, so racing dependent inserts block and then abort on the RESTRICT FKs.

### D. Atomicity
- D1. The whole procedure is one transaction (`--single-transaction` plus an in-transaction assertion that refuses autocommit execution). Trigger DDL, deletes and audit inserts commit together or not at all.
- D2. Every DELETE uses `RETURNING` and must satisfy exact set-equality (identity and count) with the enumerated target rows; any mismatch raises.
- D3. `lock_timeout` and `statement_timeout` are set (positive) before the block — unset/zero refuses — so a hung run cannot hold EXCLUSIVE locks indefinitely. Values are recorded run-record parameters (the reviewed script may pin them).
- D4. Post-conditions before COMMIT: trigger set back to the expected state; function and constraint hashes unchanged; non-target package/offer/version counts unchanged; zero target rows remain; teardown events (by `run_id`) equal the deleted package count.
- D5. Any failed assertion raises a distinct SQLSTATE with a machine-readable reason code → full rollback → the stack is byte-identical, proven by test (content-level, not just counts).

### E. Audit preservation
- E1. `audit_events` is never updated or deleted; its immutability and no-truncate triggers are asserted enabled (C6). Pre-existing audit rows naming the mocks are retained — Q1=A means they do not *block*, never that they are erased (FR-028: required audit history preserved).
- E2. New audit: exactly one teardown event per deleted package — `actor_user_id` NULL (no operator identity in the database; the operator lives in the run record), an action of the `word.word` shape naming the teardown, `target_table = 'packages'`, `target_id` = package id, `workspace_id` NULL for legacy rows, `details` allow-listed to run id, review reference, offer count and version count — no PII, no commercial values, no row data.
- E3. The teardown event inserts roll back with the transaction; a failed insert aborts the run.

### F. FR-006 immutability
- F1. No guard body, RLS policy, grant or FK changes — hash-asserted (C8, C3) and catalog-diff tested.
- F2. The carve-out is bounded: transient, owner-only, single-transaction, per-statement scope, PO-authorized (Q3=A) — and only ever reachable by the operator procedure on a named stack. No migration, no standing code path, no application role gains delete ability (A2, tested).
- F3. Non-mock rows are unreachable: real categories refuse upstream (B4), deletes are keyed by the exact allow-list with `workspace_id IS NULL` re-assertion, and post-conditions prove non-target rows unchanged (D4). Real published version rows can therefore never enter the delete set.
- F4. After any run (successful or refused), attempted UPDATE/DELETE/TRUNCATE of remaining published versions by every role must still be refused by the installed guards (regression-tested).

### G. Refusal / escalation semantics
- G1. Refusal is the default (M4). Acceptable preflight state is only `deletable = true` with every refusal code exactly `attached_offers_or_versions`. Everything else refuses the run: `non_synthetic`, `real_catalog_row`, `required_financial_dependency`, `required_audit_dependency`, `unknown_dependency_state`, `caller_cannot_see_rows`, any `escalate` status, NULL/empty/all-mode input.
- G2. Runtime/harness refusals (write nothing): not inside one transaction; caller not the owner; `BYPASSRLS` missing; stack identity mismatch; missing/malformed `run_id`/`review_ref`; unpinned `search_path`; unset timeouts; replication role ≠ `origin`; trigger set/state unexpected (including a pre-disabled guard — never repaired); internal-FK trigger unexpected; unvalidated FK; rewrite rule present; non-restrictive FK; malformed allow-list; preflight not deletable / target set differs / not synthetic / workspace mismatch; lock timeout; any count mismatch; any failed post-condition.
- G3. On refusal: raise the distinct SQLSTATE with the machine-readable reason code and refusal-code summary only (no row data, no commercial values, no PII), exit non-zero, leave the stack byte-identical (D5), record the refusal in the run record, and **escalate to the PO and the security reviewer**. The operator never edits data to make a run pass; a changed stack requires a fresh preflight capture and a fresh recorded review reference.

## 6. Out of scope / unchanged

No migration for the teardown; no edit to any pushed migration (S32-R1); no new grants; no change to any guard function body, RLS or audit mechanism; the four-category initialization is a separate T065 subtask delivered as a new forward migration with its own review (S34-PO-6 identity, S35-PO-1 F9=A literals, no fabricated commercial values); T070 remains the post-implementation acceptance review and neither gates implementation nor substitutes this gate.

## 7. Test plan (T065 implements; T070 verifies)

Integration tests against the real database on the lane's own stack, executing the operator script as the owner; every case asserts stack state afterwards. Constitution requires **executed mutation tests** for the critical controls — a mutant script variant must be *run* and observed to refuse/roll back, not merely grepped.

1. **Happy path**: verified synthetic mock with offers + published versions + audit rows naming it deletes atomically; exactly one teardown event per package with the allow-listed details (E2); all guards `tgenabled = 'O'` after; pre-existing audit rows preserved; non-target rows unchanged.
2. **Childless mock** (no offers/versions, `clean`) deletes with the same assertions.
3. **Shared legacy package** across ≥2 workspaces: refuses unless every workspace is verified; verified case removes its offers/versions in all workspaces; a foreign (non-target) package/offer/version is untouched.
4. **Per-refusal-code zero-write cases**: `non_synthetic`; `real_catalog_row` (workspace_id set; version with market; available offer); `required_financial_dependency` via subscription, renewal, upgrade, installment, payment event; `required_audit_dependency` (financial audit row on a dependent); registration link; client; `unknown_dependency_state` (unknown table with a package-id column; target id inside a jsonb column; unknown/missing id); `caller_cannot_see_rows`; empty/NULL/all-mode input; `escalate` status never deletes.
5. **Harness refusals**: outside one transaction; non-owner; stack identity mismatch; missing/malformed run id or review ref; unpinned search_path; unset timeouts; owner without BYPASSRLS; replication role ≠ origin (mutation-prove the branch is reachable); pre-disabled guard trigger refuses and is never repaired.
6. **Ordering and scope (executed mutants)**: `package_offers_guard` re-enabled before the first DELETE (probe between UPDATE and DELETE — dynamic mutant, not a text check); each `*_no_delete` disabled only around its own DELETE; version/offer/package delete-count and other-column mismatches fire; target-set ≠ allow-list fires; `non_target_rows_changed` fires; `targets_remain` fires; teardown-event-count mismatch fires; a mid-run failure rolls back everything and leaves every guard enabled.
7. **Concurrency**: a dependent insert for a target blocks while the lock is held and then aborts; a no-LOCK mutant is NOT blocked (mutation proving the lock matters).
8. **Authority**: anon/authenticated/service_role/PO session cannot reach any delete path; catalog diff shows no new function or grant after a run.
9. **FR-006 regression after the run**: attempted UPDATE/DELETE/TRUNCATE of remaining published versions by every role is still refused; guard hashes unchanged.
10. **Audit**: `audit_events` count equals before + run-id-scoped teardown events; zero pre-existing rows mutated or deleted (count **and** content check of the rows naming the targets); teardown `details` contain exactly the allow-listed keys.
11. **Refusal leaves the stack byte-identical**: content-level comparison (row counts plus targeted row content/dump hash) before vs after a refused run.
12. **Uncovered refusal branches** (each proven by an executed mutant or forced state): constraint definition changed; guard function body changed; unvalidated FK; rewrite rule present; non-restrictive FK; internal-FK trigger unexpected.
13. **Malformed allow-list input** produces the machine-readable refusal code, not a raw cast error (see divergence D8).

## 9. Draft T065 divergences

Draft under review: `supabase/cleanup/20261121_t065_c5_mock_package_teardown.sql` (+ companion `tests/integration/packages-c5-teardown.test.ts`), authored before the T064b PASS (recorded ordering exception, tasks.md). Per S65-R8 the draft is an unaccepted draft; each divergence below names the design clause it departs from. Convergences are summarized at the end.

- **D1 — run-record binding is comment-only (A4)**: the draft's header *says* "Record operator, reviewer, stack identity and before-counts in the out-of-band run record FIRST", but nothing in the script contract or tests binds `run_id`/`review_ref` to a recorded PASS for this allow-list: `review_ref` is validated syntactically only (draft lines 105–110). Design A4 requires the procedure (and reviewer check) to bind run record ↔ `review_ref` ↔ allow-list ↔ script-artifact hash before execution; the draft records no script hash at all.
- **D2 — no backup / PO-approval prerequisite (A6)**: the draft never mentions a backup with restore test or explicit PO approval for a non-local stack. Design A6 makes both recorded prerequisites before any non-local run (constitution D-14 + deployment rules).
- **D3 — silent stack-identity fallback (A5)**: on `insufficient_privilege` the draft silently falls back to `lifter.stack_id` (lines 97–101) without recording which mechanism decided the identity. Design A5 permits the fallback only when the run record states the mechanism used.
- **D4 — audit preservation is not asserted (E1, D4, test 10/11)**: the draft never touches `audit_events` and counts teardown events by `run_id`, but it captures no before/after count of the **pre-existing audit rows naming the targets**, so "audit preserved" is asserted only indirectly (trigger-state gate). Design E1/D4 requires the explicit before/after audit-count assertion and a content-level refusal-identical proof (D5); the draft's refusal tests check row counts, not content identity.
- **D5 — missing FK/constraint-state refusal coverage (C3, C6, test 12)**: the draft asserts restrictive delete actions (`fk_not_restrictive`), unvalidated FKs, rewrite rules and internal-FK trigger state (lines 152–185) — good — but its **tests never execute any of these refusal branches** (no mutant or forced state), and the `constraint_changed` / `guard_function_changed` post-condition branches (lines 329–334) likewise have no executed-mutant test. Design section 7 item 12 requires each to be proven by an executed mutant or forced state.
- **D6 — static text checks stand in for executed mutants (section 7 preamble, test 6)**: several draft "mutation checks" are `script.split(needle)` text assertions (e.g. test file lines 393–435: guard re-enabled before first DELETE; rollback after deletes; set-equality checks). Text presence is not behavior. Design section 7 requires dynamic mutants that are run and observed to refuse/roll back for the re-enable ordering, rollback, and count-mismatch controls (some draft checks — replica refusal, no-LOCK concurrency, delete-scoping, `non_target_rows_changed`, `targets_remain`, event-count mismatch, current-version verification — are executed and satisfy this).
- **D7 — owner check pins the role name (A1)**: the draft refuses unless `current_user = 'postgres'` (line 94) rather than testing database ownership; on a stack whose owner role is not literally `postgres` (but holds `BYPASSRLS`) the draft refuses what design A1 permits, and conversely it never asserts the role *owns* the database. Design A1 states the requirement as "database owner role with BYPASSRLS"; the reviewer should rule whether the pinned name is acceptable on LIFTER stacks (it is on A–D) or the check must test ownership.
- **D8 — malformed allow-list is a raw cast error (G2, test 13)**: a non-UUID token in `c5.package_ids` raises a raw `invalid input syntax for type uuid` cast failure (lines 122–123), not the machine-readable `c5_refused:*` contract of G2. Fail-closed, but the error surface violates the uniform refusal semantics.
- **D9 — timeouts are hard-pinned, not recorded parameters (D3)**: the draft fixes `lock_timeout = '5s'` / `statement_timeout = '120s'` (lines 42–43). Design D3 makes the values recorded run-record parameters (positive, refuse unset). The draft's pinning is fail-closed and acceptable; recorded as a parameterization divergence for the reviewer to accept as-is.
- **D10 — T065's initialization subtask is absent (section 1/6)**: the draft script implements teardown only; the four-category initialization (forward migration, S34-PO-6/S35-PO-1 literals, no fabricated commercial values) exists nowhere in the draft. Not a script defect — the script correctly stays teardown-only — but T065's draft claim covers an unimplemented subtask; T065 remains partial regardless of the teardown verdict.
- **D11 — `expected_triggers` allow-list is hard-coded (C7)**: the draft pins one fixed trigger array (lines 67–86). Design C7 requires the list to be re-derived from the target stack's migration state per run and pinned in the run record. The hard-coded list is fail-closed (an unexpected trigger refuses), so the divergence is process-level: the run record must carry the re-derived list, and any migration addition re-gates the script.

**Convergence summary (for the reviewer)**: the draft already matches this design on — mechanism shape M3/M4 (operator script, outside `supabase/migrations`, one transaction, refusal default); per-name-only trigger disablement bounded to the three `*_no_delete` guards plus the Q2=A-narrowed single `package_offers_guard` disablement for `current_version_id := NULL`, re-enabled before the first DELETE with count/other-column/`available` assertions; truncate and update-immutability triggers never disabled; `session_replication_role = 'origin'` asserted, never set to replica; EXCLUSIVE lock in fixed order with the preflight re-run under the lock requiring exact allow-list equality, `deletable`, and synthetic-only; structural real-catalog exclusions (`workspace_id IS NULL` re-asserted at delete time); composite `(workspace_id, id)` deletion with exact workspace-list equality; catalog-driven preflight with the Q1=A audit semantics; set-equality deletes with `RETURNING`; post-condition trigger/function/constraint re-assertion and non-target count checks; teardown events with NULL actor and allow-listed details; machine-readable refusal codes on a single SQLSTATE; and the `deletable`-only acceptance rule with NULL/empty/all-mode refusals.
