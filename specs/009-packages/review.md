## 1. Facts from the installed schema (verified in the repository)

- Protected rows and guards (`supabase/migrations/20261029120000_packages.sql`): `packages_no_delete` / `packages_no_truncate`, `package_offers_no_delete` / `package_offers_no_truncate`, `package_versions_no_delete` / `package_versions_no_truncate`, all `app_private.forbid_delete()` (raises 23514). `packages_no_update` and `package_versions_no_update` use `audit_events_immutable()`. `package_offers_guard` (BEFORE UPDATE) is SECURITY DEFINER and raises `not_permitted` unless `auth.uid()` is set and has `set_package_pricing` workspace access.
- Restrictive references, all `ON DELETE RESTRICT`: offers -> packages, versions -> offers (composite), offers.current_version_id -> versions (two composite FKs, not deferrable). The current-version FKs form a cycle: a published offer cannot be deleted before its versions, and its versions cannot be deleted while `current_version_id` points at them.
- Downstream restrictive references to versions: `registration_links`, `clients` (`package_version_id`), `subscriptions`, `subscription_renewals.package_offer_id`. Audit events reference packages, versions and offers by soft `target_id` (no FK) and are immutable.
- Every package created through `create_package_category` / `create_package` and every published version writes an audit event (`audit_package_created`, `audit_row_change`). So a mock that went through the RPCs always has audit rows naming it.
- Precedent: `supabase/cleanup/20261111_t077_legacy_package_offers.sql` runs as an operator script, disables `package_offers_no_delete` inside one transaction and re-enables it. That precedent treats any audit, link, client, subscription or renewal reference as disqualifying.
- No retirement or teardown RPC exists. Application roles (`anon`, `authenticated`, `service_role`) have no DELETE or TRUNCATE grant on these tables; only `postgres` can run the guard DDL.

## 2. Requirements this design must meet

Constraints from FR-028, T065 and T070: no guard exception authorized; no weakening of FR-006 immutability, restrictive references, audit or RLS; no cascade into protected dependencies; limited to the verified mock target set; refuse and escalate before any write on unknown, non-synthetic or required financial/audit dependency; all-or-nothing; preserve client, financial and audit history.

## 4. Controls (apply to M3; M4 uses the refusal rules only)

1. **Actor authority**: executed only by the database owner (`postgres`) via an operator procedure run on a named target stack, with operator and reviewer identities, stack and before-counts recorded first (as T077). Not callable by `anon`, `authenticated`, `service_role`, PO, WO or any API/job. No `SECURITY DEFINER` function, no grant, no new RPC, no `service_role` path. The procedure ships outside `supabase/migrations` (like `supabase/cleanup/`), so it never runs on `db reset` or in production by accident.
2. **Workspace scope**: the target set is an explicit allow-list of `packages.id` values captured by the T064a preflight, each with its `workspace_id`; every statement filters on `(workspace_id, id)` composite keys. Nothing is selected by pattern at delete time, so a foreign-workspace row can never be swept in. A foreign-workspace negative test is required.
3. **Synthetic-only proof (T064a output, read-only, zero writes)**: package code matches the test/fixture/mock convention, every `created_by`/`published_by` is a known synthetic staff profile, and the workspace is a verified synthetic workspace. Any non-synthetic signal, unknown classification or unreadable dependency state refuses with no writes.
4. **Dependency completeness**: enumerate dependents from the catalog (`pg_constraint` FK graph from `packages`, `package_offers`, `package_versions`, plus the named tables in section 1), not from a hand-written list, so a table added later is detected. Any row in `registration_links`, `clients`, `subscriptions`, `subscription_renewals`, payments/installments, assignments, or any other referencing table refuses the whole run. FKs stay enabled and restrictive; no `CASCADE`, no `session_replication_role`, no `ALTER ... DISABLE TRIGGER ALL`/`USER`, no `TRUNCATE` (the truncate guards stay installed and untouched).
5. **Audit preservation**: `audit_events` is never modified or deleted (immutable). Open question Q1 decides whether existing creation/publication audit events block deletion. Regardless, the procedure writes one new teardown audit event per deleted package (actor = operator identity string, target ids, counts, reviewer reference) inside the same transaction, in the existing allow-listed audit details style (no PII, no commercial values), so removal itself is auditable. If the audit write fails, the transaction rolls back.
6. **Atomicity**: one transaction; all trigger DDL, deletions and the audit write commit together or not at all. `ALTER TABLE ... DISABLE TRIGGER` is transactional in PostgreSQL, so a rollback restores the triggers. Lock the target tables (SHARE ROW EXCLUSIVE or stronger) before the preflight re-check, then re-run the dependency check, so no concurrent publish, link or registration can add a dependency between check and delete. Partial completion is a failure: assert deleted count equals the allow-list count.
7. **Immutability (FR-006)**: published versions of anything that is not a verified mock are never touched. For mocks, deleting a published version contradicts the FR-006 literal text and is admissible only through the FR-028 carve-out, and only when control 4 shows zero dependents. The current-version cycle is broken by one controlled update of `offers.current_version_id` to NULL, which also requires disabling `package_offers_guard` and its audit trigger for that statement. The reviewer must explicitly approve or reject this extra disablement (Q2).
8. **Post-conditions asserted before COMMIT**: every touched guard trigger has `tgenabled='O'`; guard function definitions are unchanged (compare to pre-run hashes); row counts of every non-target package/offer/version equal the before-counts; the `audit_events` count equals before-count plus the teardown events only; no FK/constraint changed. Any failed assertion raises and rolls back.
9. **Refusal/escalation semantics**: refusal is the default. On any unsafe or unknown row: write nothing, print a machine-readable refusal reason code and the blocking dependency category (no row data), exit non-zero, and escalate to the PO and the security reviewer. The output never lists commercial values. A refused run leaves the stack byte-identical.
10. **Out of scope / unchanged**: no migration, no edit to a pushed migration, no new grants, no change to `forbid_delete()`, `audit_events_immutable()`, RLS or any guard function body. T070 still reviews the implemented path afterward and does not replace this gate.

## 5. Open questions for the reviewer / PO (not decided here)

- **Q1 (audit rows)**: does an immutable audit event that merely names a mock package as `target_id` count as a "required audit dependency" under FR-028? A) No: audit rows are preserved untouched and do not block; only financial/client references block (recommended; otherwise every RPC-created mock is undeletable). B) Yes: any audit reference blocks, matching the T077 precedent, and RPC-created mocks are retained (M4).
- **Q2 (current-version cycle)**: may the procedure also disable `package_offers_guard` (update) for the single `current_version_id := NULL` statement? A) Yes, under controls 1-9 (recommended if M3 is accepted). B) No: only mocks whose offers have no versions are deletable.
- **Q3 (ruling)**: is transient owner-only per-table trigger disablement in a single reviewed transaction a "guard exception"? A) No, with the controls above (M3). B) Yes, so only M4 is allowed.
