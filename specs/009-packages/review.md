## 1. Facts from the installed schema (verified in the repository; corrected after independent review #1)

- Protected rows and guards (`supabase/migrations/20261029120000_packages.sql`): `packages_no_delete` / `packages_no_truncate`, `package_offers_no_delete` / `package_offers_no_truncate`, `package_versions_no_delete` / `package_versions_no_truncate`, all `app_private.forbid_delete()` (raises 23514). `packages_no_update` and `package_versions_no_update` use `audit_events_immutable()`. The LIVE `package_offers_guard` (BEFORE UPDATE, SECURITY DEFINER) is the one redefined in `20261111170857_packages_tier_rank.sql` (lines 19-32): it raises `immutable` for identity, duration and `tier_rank` changes and `not_permitted` unless `auth.uid()` is set and has `set_package_pricing` workspace access. The `20261029120000` definition is stale.
- Restrictive references, all `ON DELETE RESTRICT`: offers -> packages, versions -> offers (composite), offers.current_version_id -> versions (two composite FKs, not deferrable). The current-version FKs form a cycle: a published offer cannot be deleted before its versions, and its versions cannot be deleted while `current_version_id` points at them.
- Downstream restrictive references (every FK to the package tables is `ON DELETE RESTRICT`, so a racing dependent insert aborts the teardown): `registration_links` (version), `clients` (`package_version_id`, plus the link triple), `subscriptions` (a DIRECT version FK `f13_renewal:11-13` plus the link triple), `subscription_renewals` (offer FK AND version FK, `f13_renewal:45-47`), `subscription_upgrades` (offer FK and version FK, `20261111233600:49-50`); installments, payment events, activations and renewal-date revisions reach packages transitively through subscriptions. Audit events reference packages, versions and offers by soft `target_id` (no FK) and are immutable. Package ids can also sit in json/jsonb without an FK (`subscription_upgrade_operations.result_receipt`, audit `details.package_version_id`, job payloads).
- Legacy mock rows have `packages.workspace_id/market/type` all NULL (`20261118000000`), `code` is globally unique, and one legacy package may have offers in several workspaces. Post-F9 real categories are `packages` rows with `workspace_id` set (`create_package_category`) and versions carrying `market/type`; `code` is nullable there. The schema has no synthetic marker for a workspace or staff profile, so the code convention (`^(test|fixture)-...`) is necessary but NOT sufficient: real rows are excluded structurally (control 3).
- Every package created through `create_package` / `create_package_category` and every published version writes an audit event, so a mock that went through the RPCs always has audit rows naming it (PO Q1=A: these do not block).
- Precedent: `supabase/cleanup/20261111_t077_legacy_package_offers.sql` runs as an operator script, disables `package_offers_no_delete` inside one transaction and re-enables it. It is a shape precedent only and is NOT a complete dependency check (it omits `subscription_upgrades`).
- No retirement or teardown RPC exists. Application roles (`anon`, `authenticated`, `service_role`) have no DELETE or TRUNCATE grant; only `postgres` can run guard DDL, and the package tables are `FORCE ROW LEVEL SECURITY`, so deletes rely on the `postgres` role's BYPASSRLS (asserted by control 8).

## 2. Requirements this design must meet

Constraints from FR-028, T065 and T070: no guard exception authorized; no weakening of FR-006 immutability, restrictive references, audit or RLS; no cascade into protected dependencies; limited to the verified mock target set; refuse and escalate before any write on unknown, non-synthetic or required financial/audit dependency; all-or-nothing; preserve client, financial and audit history.

## 3. Candidate mechanisms evaluated

| Id  | Mechanism                                                                                                                                                                                                                                                                                                                       | Verdict                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1  | A bypass flag, role check or `IF current_setting(...)` branch added inside `forbid_delete()` or the immutability guards                                                                                                                                                                                                         | REJECTED. Standing guard exception; explicitly unauthorized; widens the attack surface of every caller.                                                                                                                                                                                                                                                                                         |
| M2  | A SECURITY DEFINER teardown RPC callable by PO                                                                                                                                                                                                                                                                                  | REJECTED. A runtime path to delete protected rows from the API surface; PO is not an authority over FR-006; it would still need M1 or M3 inside.                                                                                                                                                                                                                                                |
| M3  | One-shot operator-run script executed as `postgres` (not a migration, not an API, not a function), in a single transaction, that disables only the named per-table delete triggers (and the offer update guard for the current-version cycle) for the verified target set, deletes in FK order, re-enables, and asserts each trigger is `tgenabled='O'` before COMMIT | CONDITIONAL. Same shape as the T077 precedent. No standing code path and no API exposure. Still a transient disablement; whether that counts as a "guard exception" is exactly the ruling the independent reviewer must make.                                                                                                                                                                  |
| M4  | No physical deletion of anything with attached offers/versions: fail-closed refuse/escalate; deletion only of rows with no protected children and no audit rows                                                                                                                                                                 | FALLBACK. Zero weakening for protected history. `packages_no_delete` still blocks even childless package rows, so it needs the same ruling for the package row itself. Mocks with attached history stay (hidden from sale via `available=false`); they do not conflict with the four categories because the unique key is on `(workspace_id, market, type)` over non-null categories. |

**Recommendation (for the reviewer to accept or overrule)**: M3 under the controls below, with M4 as the mandatory default whenever preflight finds anything not provably clean. If the reviewer rules that even transient owner-only trigger disablement violates "no guard exception", the only compliant outcome is M4 and T065 shrinks to four-category initialization plus refusal.

## 4. Controls (apply to M3; M4 uses the refusal rules only)

M3 is an operator cleanup script run as the database owner, shipped outside `supabase/migrations` (like `supabase/cleanup/`), NOT a migration: a migration would run on every `db reset` and on production deploys. Rulings applied: PO S61-PO-1 Q1=A, Q2=A (narrowed to `package_offers_guard` only), Q3=A, plus independent review #1 findings 1-3 and 5-13.

1. **Actor authority**: executed only by `postgres` via an operator procedure on a named target stack, with operator and reviewer identities, stack identity and before-counts recorded first in an out-of-band run record (as T077). Not callable by `anon`, `authenticated`, `service_role`, PO, WO or any API/job. No `SECURITY DEFINER` function, no grant, no new RPC, no `service_role` path. Any non-local stack needs explicit PO approval (Constitution deployment rules) and a backup plus restore test before production.
2. **Harness**: the whole procedure runs in one `DO` block or `psql --single-transaction -v ON_ERROR_STOP=1`, and refuses to run if it is not inside a transaction or the stack identity check fails.
3. **Target set (review findings 2, 3)**: the input is an explicit allow-list of `packages.id` values produced by the T064a preflight. A package is never targeted if `workspace_id IS NOT NULL`, any of its versions has `market IS NOT NULL`, or any of its offers has `available = true` (real catalog rows); the preflight reports these as `real_catalog_row`. The run-time target set (re-derived under the lock) must EXACTLY equal the reviewed allow-list or the run refuses. Because legacy mocks have a NULL `workspace_id`, scope is by package id: enumerate offers and versions across ALL workspaces; every such workspace must be verified synthetic (a named allow-list in the run record, since no marker exists in the schema) or the run refuses. Offers and versions are deleted by composite `(workspace_id, id)`; packages by `id AND workspace_id IS NULL`. Nothing is selected by pattern at delete time. The code convention is necessary but not sufficient.
4. **Dependency completeness (findings 5, 9)**: dependents are enumerated from the catalog (`pg_constraint` FK graph from the three package tables, transitively), so a table added later is detected; this covers `subscription_upgrades`, the version FK on `subscription_renewals`, the direct version FK on `subscriptions`, registration links, clients, installments and payment events. Any row in any dependent refuses the whole run. A package-id column without an FK edge (column-name oracle), or a target id found in any json/jsonb column, refuses (escalates). Audit rows that merely name a mock do NOT block (Q1=A); audit rows of client/financial dependents do. FKs stay enabled and restrictive; no `CASCADE`, no `TRUNCATE`; the truncate guards stay installed.
5. **Replication role and trigger state (finding 1)**: assert `current_setting('session_replication_role') = 'origin'` and `SET LOCAL session_replication_role = 'origin'`; never set `replica`. Before any change assert that every trigger on `packages`, `package_offers`, `package_versions` and `audit_events` has `tgenabled = 'O'`, that the trigger set equals the expected list, that all FKs are validated and that no `pg_rewrite` rules exist on these tables; otherwise REFUSE (do not "repair"). Forbidden: `DISABLE TRIGGER ALL/USER`, `session_replication_role`, CASCADE, TRUNCATE.
6. **Lock (finding 7)**: `LOCK TABLE packages, package_offers, package_versions IN EXCLUSIVE MODE` in that fixed order with `lock_timeout`, then re-run the preflight and compare to the allow-list. (`SHARE ROW EXCLUSIVE` does not conflict with the ROW SHARE FK-check lock of dependent inserts.) SERIALIZABLE is not required. Dependent inserts that race the lock abort on the restrictive FKs.
7. **Offer guard (Q2=A, finding 6)**: disable ONLY `package_offers_guard`, run a single `UPDATE public.package_offers SET current_version_id = NULL` over the allow-listed `(workspace_id, id)` offers, assert the row count, that no other column changed and `available = false`, then re-enable `package_offers_guard` IMMEDIATELY, before the first DELETE. The offer audit trigger is NOT disabled (it writes nothing when `available` is unchanged). Optional (finding 14): adopt deleting versions and offers in one writable-CTE statement instead only if a test proves it satisfies the RESTRICT cycle without this disablement.
8. **Delete order and set checks (findings 12, 13)**: order is null current version, versions, offers, packages, each as `DELETE ... USING <allow-list> ... RETURNING` with set-equality against the allow-list; assert zero targets remain and the delete triggers (`*_no_delete`) are disabled only for their own table's delete statement and re-enabled right after it. Assert `rolbypassrls` for the executing role (FORCE RLS on the package tables). Assert guard function body hashes unchanged.
9. **Audit (findings 8, 10)**: `audit_events` is never modified or deleted; `audit_events_immutable` and `audit_events_no_truncate` are asserted `tgenabled = 'O'`. One teardown event per deleted package: `actor_user_id` NULL, `action` matching `^[a-z_]+\.[a-z_]+$`, `target_table = 'packages'`, `workspace_id` NULL for legacy rows, `details` allow-list only (run id, review reference, offer count, version count; no PII, no operator identity, no commercial values); the operator identity lives in the out-of-band run record. The insert by `postgres` under FORCE RLS is tested. The post-condition counts teardown events BY RUN ID, not total audit count (which races).
10. **Atomicity and post-conditions**: one transaction; trigger DDL, deletions and the audit insert commit together or not at all (`ALTER TABLE ... DISABLE TRIGGER` is transactional). Before COMMIT assert: every touched trigger `tgenabled = 'O'` again; guard function definitions unchanged; counts of every non-target package/offer/version equal the before-counts; teardown events equal the deleted package count; no FK or constraint changed. Any failed assertion raises and rolls back.
11. **Refusal/escalation semantics**: refusal is the default (M4). On any unsafe or unknown row: write nothing, print a machine-readable reason code and blocking dependency category (no row data, no commercial values), exit non-zero, escalate to the PO and security reviewer. A refused run leaves the stack byte-identical.
12. **Out of scope / unchanged**: no migration for the teardown, no edit to a pushed migration, no new grants, no change to `forbid_delete()`, `audit_events_immutable()`, RLS or any guard function body. T070 still reviews the implemented path afterward and does not replace this gate.

PO words, verbatim: `Teardown Q1=A, Q2=A, Q3=A` (recorded in `docs/04-changes-and-questions.md` as S61-PO-1).
