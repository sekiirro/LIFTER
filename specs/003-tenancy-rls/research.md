Findings carried to the architect (no new mechanism is proposed in this round):

1. **F-A1 (existing pending task):** the last-PO guard is not implemented on `origin/main`. Pending tasks T015, T021, T022 and T024 cover it. Evidence: table row above.
2. **F-A2 (open decision):** a Platform Owner's membership revocation does not remove PO access, because PO access is role-based. This conflicts with the S36-PO-2 clause that membership revocation must remove PO access, and the atomic demotion that answered it is removed by S37-PO-3/4. Open: S37-Q5.
3. **F-A3 (open decision):** the S37-PO-4 deletion step has no existing path, and the no-delete guards and G1=A keep it blocked. Open: S37-Q4.
4. **F-A4 (open decision, S37-Q6):** `authorize()` is pure (FR-007), so it cannot detect that an actor object loaded before a change is stale. The only existing guard is the per-request reload in `getActor()` (`lib/auth/actor.ts:42-51`). The database clause (FR-016(c)) is enforced by the per-request re-read in the helper functions. Open: S37-Q6.

Stale-session enforcement (S37-Q1) is resolved as "existing DB/RLS per-request authorization; no new mechanism", because the audit shows no gap in the role and membership re-read paths. The F-A1 gap is pending work, not a stale-session gap. The app-layer stale-actor clause is a separate open question (F-A4, S37-Q6).
