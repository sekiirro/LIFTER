# Research: P0-F3

| Topic | Decision | Rationale | Alternatives |
|---|---|---|---|
| Helper location | Schema `app_private`, not exposed by the API (not in the PostgREST `schemas` list). Functions are `SECURITY DEFINER`, `STABLE`, `SET search_path = ''`, fully qualified names. `EXECUTE` is granted to `authenticated` only. | Policies can call them, but clients can't call them as RPCs. An empty search_path prevents hijacking. | `public` helpers (exposed as RPC) |
| Identity | `auth.uid()` from the signed JWT, always written as `(select auth.uid())` in policies (initplan caching) | Architecture v3 threat model. Supabase RLS performance guidance. | `SET LOCAL` context (rejected in review log #1) |
| PO access | `is_platform_owner()` = the caller's staff role is `platform_owner`. It grants every workspace without needing membership rows. | BRD: "full platform-level authority" | Auto-membership rows for the PO (drift-prone) |
| Role storage | `staff_profiles.role` (enum `staff_role`), exactly one per auth user | BRD-02 consistent role; AT-ISO-07 holds by construction | Role on the membership (could diverge) |
| Membership history | `revoked_at`/`revoked_by`. Unique active membership via a partial unique index `(workspace_id, user_id) WHERE revoked_at IS NULL`. A trigger allows only the null→value transition of `revoked_at`/`revoked_by` (with `revoked_by = auth.uid()`) and blocks every other column change. No DELETE policy or grant. | Constitution VI: history is preserved | Hard delete |
| Composite keys | `workspace_memberships` has `UNIQUE (workspace_id, id)`. Later tenant tables reference `(workspace_id, membership_id)` and similar keys through composite FKs. | Constitution I | — |
| Capabilities | Text identifiers validated against a fixed list in `app_private.role_has_capability(role, cap)` (an immutable CASE). Unknown → false. | Easy parity testing; deny-by-default | A capabilities table (mutable, so it needs its own governance) |
| Matrix | `set_package_pricing`: PO. `generate_registration_link`: PO, WO, Sales, Trainer. `configure_installment_schedule`, `approve_registration`, `record_payment`, `manage_freeze`: PO, WO, Sales. `record_refund`, `delete_client`, `export_client_dataset`, `manage_workspaces`, `manage_staff_access`: PO (12 capabilities total). `coaching_work`: PO, WO, Trainer. | D-09, D-10, Architecture matrix, Constitution III | — |
| Grants | Revoke all from `anon` and `public` on the 3 tables. `authenticated` gets SELECT, INSERT, UPDATE (RLS filters). No DELETE. | Defense in depth | — |
| Test DB access | supabase-js clients per user (password sign-in after admin `createUser`), plus `postgres` over `DB_URL` for catalog and parity queries. Fixtures are created with the service-role client (bypasses RLS). Each test file uses unique slugs and emails (random suffix). | Exercises the real PostgREST + RLS path | pg-tap (needs SQL test tooling in CI; a later option) |
| Env for tests | The harness reads `API_URL`, `ANON_KEY`, `SERVICE_ROLE_KEY` and `DB_URL` from `process.env`, as written by `supabase status -o env`. If they are missing, it fails with a clear "run supabase start" message. | No secrets in the repo; the local demo keys are generated | Hard-coded demo keys |
| CI | A new `integration` job: setup-cli v1 (2.122.0) → `supabase start -x studio,imgproxy,inbucket,edge-runtime,logflare,vector,supavisor,realtime,storage-api,postgres-meta` → `supabase status -o env >> $GITHUB_ENV` (variable names normalized by the harness) → `npm run test:integration` → `supabase stop`. | Roadmap QG-2. $0. | Remote Supabase (needs secrets) |
| PO bootstrap | The README documents an operator SQL snippet run with the local or staging SQL editor: insert `staff_profiles(user_id, 'platform_owner')`. Not a migration (no PII or user ids in git). | ND-F3-3 | Seed file with a real email (PII) |
