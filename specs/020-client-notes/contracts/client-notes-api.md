# Client Notes Application Contract (proposed)

This is a behavioral contract for later implementation, not an API endpoint naming decision. Route/RPC names, request envelope and error copy remain unspecified.

## Operations

| Operation | Allowed actor | Required scope | Result |
| --- | --- | --- | --- |
| List notes | Trainer, Workspace Owner, Platform Owner | Current active workspace membership and role capability. A Trainer's client assignment is not a restriction (CN-MCQ-04, S37-PO-7). PO uses current platform-wide workspace policy. | Notes only for the requested client/workspace, newest-created first with `id` tie-break (FR-008). |
| Create note | Trainer, Workspace Owner, Platform Owner | Same current scope; author is derived from server-verified identity | One independent plain-text note: leading and trailing whitespace removed, then 1 to 5,000 Unicode code points, not blank after trimming (FR-002, CN-MCQ-14; S37-PO-16); the trimmed text is stored; server creation timestamp; one metadata-only audit event in the same transaction (FR-010). The request carries a client-generated idempotency key, generated once per create and re-sent unchanged with the same body on retry; body equality is checked after trimming (FR-011). A duplicate create in the same workspace/client scope with the same key and trimmed body returns the existing note row instead of creating a second note (FR-011, CN-MCQ-18; S39-PO-9). A same-key retry carrying a different trimmed body is rejected as a key/body mismatch: no second note, no body change and no create audit event (CN-MCQ-22; S40-R9). After the note is hard-deleted, a same-key retry returns a deleted/not-found outcome and never recreates the note; the content-free create-idempotency record survives the delete with no note body (CN-MCQ-20; S40-PO-6). The note row is unique on `(workspace_id, client_id, idempotency_key)` while it exists, and the key record and note are written atomically by a hardened boundary; a direct or concurrent duplicate is refused (FR-011). |
| Edit note | Original author with current authorization (active membership and a role still authorized), or Platform Owner | Current workspace/client scope; current authorization required | Replace current body in place; last save wins, the winner being the write the database commits last (FR-009); set `edited_at`; keep author, creation timestamp and all immutable columns; no version history; one metadata-only audit event in the same transaction (FR-010). |
| Hard-delete note | Platform Owner only | Existing Platform Owner workspace scope | Permanently remove row; one metadata-only audit event in the same transaction (FR-010). Audit retention is the existing `public.audit_events` policy (CN-MCQ-13); confirmation copy is CN-MCQ-08 rows 11–13. |

## Display

- Timestamps are shown in the viewer's local time zone in the CN-MCQ-08 row 29 format (FR-009, CN-MCQ-12).
- A note with an unavailable author shows the CN-MCQ-08 row 26 label “Unavailable author” / “صاحب الملاحظة غير متاح” (FR-002, CN-MCQ-06).
- Edited marker: CN-MCQ-08 row 25. Byline: row 28. Exit-protection warning copy (title, body, Stay and Discard): CN-MCQ-16 rows 30–33 in spec.md (S38-PO-11). All other strings: CN-MCQ-08 table rows 1–29 in spec.md; no other copy is approved.
- The in-flight warning body (a save already sent) is CN-MCQ-19, spec.md row 34, i18n key `clientNotes.exitWarning.bodyInFlight`, approved byte-exact by S40-PO-3 (option Variant 1 (Recommended)): EN “Your note is being saved. Leaving now won't cancel the save.” / AR “ملاحظتك بتتحفظ. لو خرجت دلوقتي، الحفظ مش هيتلغي.”. Rows 30–33 are unchanged and row 31 covers only text that has not been submitted. While a create or edit save is in flight the note field is read-only, so only row 34 applies in that state (CN-MCQ-21; S40-PO-6 option A).
- Leaving the editor or choosing Discard does not cancel a create or edit request already submitted; its outcome is the server result (committed or refused), and a committed save keeps its row and its one audit event (CN-MCQ-17; S39-PO-8). Only text that has not been submitted is discarded.
- If a save outcome is unknown (no response), the editor retains the text, keeps the field read-only, never indicates success, and shows the existing save-error state (row 18) with the existing Retry action (row 17); a create Retry reuses the same key and original body, and no duplicate create starts until the outcome is resolved (DESIGN.md Q51; CN-MCQ-21; S40-PO-6). While the save outcome is unknown, exit protection uses the approved CN-MCQ-16 title, Stay and Discard rows 30, 32 and 33 with the approved generic save-error body CN-MCQ-08 row 18; rows 34 and 31 MUST NOT be reused for that state. Leaving cancels nothing, and the unresolved create keeps its key for Retry; no new string is introduced (CN-MCQ-23; S40-PO-10 option A, architect mapping). A Retry the server refuses (for example after membership revocation) does not resolve the original attempt; the same state stays in place and no new create starts.
- A same-key create whose trimmed body differs from the original submission is a failed create (key/body mismatch); a same-key retry after the note was hard-deleted is also a failed create (deleted/not-found). Both use the existing generic save-error state, CN-MCQ-08 row 18; no new string is introduced (CN-MCQ-22; S40-R9; CN-MCQ-20; S40-PO-6).

## Denials

- Deny Sales, Client and anonymous actors for every operation.
- Deny unauthorized actors, non-PO actors with revoked membership, and all foreign client/workspace scope. A non-PO revoked membership grants zero access; the Platform Owner follows the existing PO rule.
- Do not trust actor, client, workspace or role fields supplied by a caller. An idempotency key is not an authorization factor and never widens scope; it only identifies one create attempt for duplicate prevention.
- Application checks and database RLS must independently enforce the matrix.
- Failure response shape is not specified here. Where a denial message is shown, its copy is CN-MCQ-08 row 27 (“You don't have permission to do this.” / “ليست لديك صلاحية للقيام بذلك.”), a generic message that discloses no note, client or workspace existence.
- A denied or rejected operation emits no successful note-mutation event (specs/005-audit-log US1 scenario 2).
