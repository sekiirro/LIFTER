## User Scenarios & Testing

### Story 1 — View notes for an authorized client (P1)

An authorized Trainer, Workspace Owner, or Platform Owner views independent notes in the Client Details tab for a client within their authorized scope. Any Trainer in the workspace may view notes for any client in that workspace, regardless of assigned Trainer (S37-PO-6, S37-PO-7).

**Independent test**: Authenticate synthetic role fixtures and request notes for clients in workspace A and workspace B through both application and database boundaries.

**Acceptance scenarios**

1. **Given** a Trainer or Workspace Owner with active membership in workspace A, regardless of which Trainer is assigned to client A1, **When** they open the Client Notes tab for A1, **Then** only notes associated with A1 in A are returned, newest-created first (FR-001, FR-004, FR-008).
2. **Given** a Platform Owner requesting an authorized Client Details record, **When** they open Client Notes, **Then** its workspace-scoped notes are returned under the existing Platform Owner access model (FR-004).
3. **Given** a Sales identity, a Client identity, an anonymous caller, or a staff identity without current authorization, **When** they read notes directly or through the application, **Then** access is denied by both authorization boundaries (FR-004, FR-005).

### Story 2 — Create a plain-text note (P1)

An authorized Trainer, Workspace Owner, or Platform Owner creates a separate plain-text note from Client Details using Add New Note.

**Independent test**: Create synthetic notes under each permitted role, check exact saved content (trimmed)/author/server timestamp, reject blank-after-trim and over-limit payloads, and attempt direct unauthorized inserts.

**Acceptance scenarios**

1. **Given** a Trainer (for any client in their workspace), Workspace Owner, or Platform Owner in its authorized scope and a body that does not contain U+0000 and has 1 to 5,000 Unicode code points after its leading and trailing whitespace is removed, **When** they submit it through Add New Note, **Then** one independent note is created with the trimmed text as its body, attributed to the verified actor and a server-assigned creation timestamp (FR-001, FR-002, FR-004; CN-MCQ-14).
2. **Given** a caller submits a body that has more than 5,000 Unicode code points after trimming, or a body that is blank after trimming, **When** the request reaches the application or database write boundary, **Then** creation is refused and no note is persisted (FR-002; CN-MCQ-02).
3. **Given** a caller submits a body of 5,000 Unicode code points followed or preceded by whitespace, **When** the request is accepted, **Then** the stored body is the 5,000 code points without that whitespace (FR-002; CN-MCQ-14; S37-PO-16).
4. **Given** a caller supplies a forged author, client, or workspace identity, **When** the write is attempted, **Then** those supplied identities cannot widen access or replace verified identity/scope (FR-004).
5. **Given** an authorized actor has unsaved text in the Add New Note field that has not been submitted, **When** they try to leave the editor (navigate away, close it or cancel), **Then** the exit-protection warning with Stay and Discard is shown, using the CN-MCQ-16 strings (rows 30–33) and no Save Draft; **Stay** keeps the text and creates nothing, and **Discard** discards only that unsubmitted text, so no row is created from it and no audit event is emitted (FR-007, FR-010; CN-MCQ-16).
6. **Given** a create save has already been submitted and is in flight, **When** the actor chooses Discard or otherwise leaves the editor, **Then** Discard leaves the editor and does not cancel the submitted save; the outcome is the server result — the note is committed or the save is refused — and a committed note keeps its row and its one audit event. While the save is in flight the note field is read-only, so no later unsaved text can exist in that state and editing resumes only after the server result (CN-MCQ-21; S40-PO-6 option A, architect mapping). The exit warning body in that state is only CN-MCQ-19 row 34, i18n key `clientNotes.exitWarning.bodyInFlight` (S40-PO-3); row 31 does not apply. If the save outcome is unknown (no response), the editor retains the text, keeps the field read-only, shows the existing save-error state and Retry (CN-MCQ-08 rows 17-18), never indicates success, and a Retry reuses the same idempotency key and original body; no duplicate create starts until the outcome is resolved (DESIGN.md Q51; CN-MCQ-21). The unresolved create's text, key and original body are kept in that tab's browser `sessionStorage` until the server result is known, then cleared; the record is written before the create request is dispatched when `sessionStorage` is available, so a same-tab reload while the request is in flight retains it; the state survives a same-tab reload only, no server-side pending note body is stored, closing the tab clears it, and no new copy is added (CN-MCQ-24; S40-PO-12 option A, architect mapping; Principle VII). A definite refusal of the original create request resolves the attempt only when no retry of that create was ever sent; if a retry could have committed (for example a retry whose response was lost), the key must be reconciled with the server first (see FR-007); when no content-free key record exists because that retry never reached the server, the same-key reconciliation retry follows the normal create path and creates the first note with its one create audit event, and that confirmation resolves the attempt. A refused Retry does not clear it. A record copied into an opener-created tab is ignored and removed, and cannot overwrite or resolve this tab's state. The record is bound to the signed-in actor and is cleared on sign-out or an account switch, so another actor cannot read or retry it. A Retry refused by the server (for example after membership revocation) does not resolve that attempt: the state above stays in place and no new create starts (CN-MCQ-23; S40-PO-10, architect mapping). Exit protection in that unknown-result state uses the approved CN-MCQ-16 title, Stay and Discard rows 30, 32 and 33 with the approved generic save-error body CN-MCQ-08 row 18; rows 31 and 34 are not reused for that state. Leaving cancels nothing, and the unresolved create keeps its idempotency key so Retry can resolve it (CN-MCQ-23; S40-PO-10 option A, architect mapping). The spec makes no cancellation claim for an in-flight save (FR-007, FR-010; CN-MCQ-17; S39-PO-8; CN-MCQ-19; S40-PO-3; CN-MCQ-21; S40-PO-6).
7. **Given** an authorized create whose result is not observable (no confirmed response), **When** the actor retries that create with the same client-generated idempotency key and the same body, **Then** the retry never creates a second note; if the original note is live and the trimmed retry body matches the original submission fingerprint for that key (not the note's current body, which may have been edited), the retried request returns that existing note; if the note was hard-deleted, the retry returns a deleted/not-found outcome regardless of the retry body and does not recreate it; if no content-free key record exists because that earlier retry never reached the server, the same-key retry follows the normal create path and creates the first note with its one create audit event, which resolves the attempt (FR-011, FR-007; CN-MCQ-18; CN-MCQ-20; S39-PO-9; S40-PO-6).
8. **Given** a create request reuses an idempotency key already used for a note in the same workspace/client scope, **When** it reaches the database, **Then** if the note is live and the retry body equals the original submitted body after trimming, the request returns the existing note row unchanged, no second note is created and, under FR-010, no second create audit event is emitted; if the note is live and the retry body differs after trimming, the request is refused as a key/body mismatch with no second note, no body change and no create audit event; if the note was hard-deleted, the request returns a deleted/not-found outcome regardless of its body (that outcome takes precedence over the mismatch refusal) and does not recreate it (FR-011, FR-010; CN-MCQ-18; CN-MCQ-20; CN-MCQ-22; S39-PO-9; S40-PO-6; S40-R9).

### Story 3 — Edit and permanently delete (P1)

The note author or Platform Owner edits a note. Only the Platform Owner permanently hard-deletes a note. Notes do not have version history.

**Independent test**: Use synthetic author, other Trainer, Workspace Owner, Platform Owner, Sales, Client, and anonymous fixtures to exercise edit and delete through both walls; verify deleted rows are absent.

**Acceptance scenarios**

1. **Given** a note whose author still holds current authorization in that workspace (an active membership and a role still authorized under FR-004; CN-MCQ-05), **When** the author submits a valid edit, **Then** the current body is replaced in place, the edited timestamp is set, the original author and creation timestamp are kept, and no version history is created (FR-003, FR-004). **Given** two saves to the same note, **When** both are valid, **Then** the last save is the note content (FR-009).
2. **Given** a Platform Owner and a note in a workspace within the PO's existing authorized scope, **When** the PO edits the note, **Then** the current content changes, the edited timestamp is set, and no version history is created (FR-003, FR-004).
3. **Given** any non-PO actor, including the note author, **When** they attempt a hard delete, **Then** the operation is denied. **Given** a Platform Owner with current scope, **When** they hard-delete, **Then** the note row is permanently removed (FR-003, FR-004).
4. **Given** a non-PO actor with a revoked membership, or a Sales, Client, anonymous, or foreign-workspace actor, **When** a direct database or application request attempts a read or write, **Then** it is denied (FR-004, FR-005). A Platform Owner is governed by the existing PO rule, not by a membership row. **Given** an author whose membership was revoked and later restored, **When** they edit their note, **Then** author edit rights have resumed (CN-MCQ-05).
5. **Given** two valid saves to one note by the author or the Platform Owner that overlap in time, **When** the database commits them, **Then** the later committed body is the note content, `created_at` and `author_user_id` are unchanged, no version row exists, and each successful save emits exactly one audit event (FR-003, FR-009, FR-010).
6. **Given** a direct UPDATE that changes `id`, `workspace_id`, `client_id`, `author_user_id`, `created_at` or `idempotency_key` of an existing note, **When** it is attempted by the author (including an author authorized in two workspaces), a Trainer, a Workspace Owner or a Platform Owner, **Then** the database refuses it and the row is unchanged (FR-003, FR-005).
7. **Given** an author or Platform Owner has unsaved changes to an existing note's body that have not been submitted, **When** they try to leave the editor, **Then** the same exit-protection warning is shown, using the CN-MCQ-16 strings (rows 30–33) and no Save Draft; **Stay** keeps the change in the editor, and **Discard** discards only the unsubmitted change, leaving the stored body unchanged, with no edited timestamp change and no audit event (FR-003, FR-007, FR-010; CN-MCQ-16).
8. **Given** an edit save has already been submitted and is in flight, **When** the author or Platform Owner chooses Discard or otherwise leaves the editor, **Then** Discard leaves the editor and does not cancel the submitted save; the outcome is the server result — the edit is committed or refused — and a committed edit sets the edited timestamp, keeps the original author and creation timestamp, and emits its one audit event. While the save is in flight the note field is read-only, so no later unsaved text can exist in that state and editing resumes only after the server result (CN-MCQ-21; S40-PO-6 option A, architect mapping). The exit warning body in that state is only CN-MCQ-19 row 34, i18n key `clientNotes.exitWarning.bodyInFlight` (S40-PO-3); row 31 does not apply. If the edit outcome is unknown (no response), the editor retains the text, keeps the field read-only, shows the existing save-error state and Retry (CN-MCQ-08 rows 17-18), never indicates success, and a Retry re-sends the edit until the server result is known (DESIGN.md Q51; CN-MCQ-21). The unresolved edit state is held only in page memory for the current editor page; it does not survive navigation or reload. After a reload the note is read from the server at its last committed body, no success is indicated, and no Retry state for the prior edit attempt is restored (CN-MCQ-24 applies to creates; no new copy). An edit retry is a new save, not an idempotent replay: creates alone carry an idempotency key (FR-011), so an edit retry has no stored original outcome; if a later edit committed in the meantime, the retry follows last save wins (CN-MCQ-11; FR-009) and each successful write emits its own audit event (FR-010). Exit protection in that unknown-result state uses the approved CN-MCQ-16 title, Stay and Discard rows 30, 32 and 33 with the approved generic save-error body CN-MCQ-08 row 18; rows 31 and 34 are not reused for that state. Leaving cancels nothing, and, while the editor page remains open, the unresolved edit keeps its Retry path so the server result can still be resolved; a reload or navigation does not restore it (CN-MCQ-23; S40-PO-10 option A, architect mapping). The spec makes no cancellation claim for an in-flight save (FR-003, FR-007, FR-009, FR-010; CN-MCQ-17; S39-PO-8; CN-MCQ-19; S40-PO-3; CN-MCQ-21; S40-PO-6).

## Functional Requirements

- **FR-001**: The product MUST expose a separate Client Notes tab within Client Details, placed as a horizontal tab alongside the existing client profile tabs (DESIGN.md §6). Notes MUST be independent of Exercise Library and Workout Planner records.
- **FR-002**: Each note MUST be an independent plain-text entry with a maximum length of 5,000 Unicode code points, an author, and a server-assigned creation timestamp. Leading and trailing whitespace MUST be removed from the submitted body, then the result is counted in Unicode code points against the 5,000 limit and stored as the trimmed text (CN-MCQ-14; S37-PO-16). Whitespace means characters with the Unicode White_Space property. A body that is blank after trimming (in other words, whitespace-only) MUST be rejected and no row persisted (CN-MCQ-02). Interior formatting is preserved (S37-PO-16); no other normalization is defined. A body containing the NUL character U+0000 MUST be rejected at both the application and database boundaries, with no row persisted; the refusal uses the existing generic save-error state (CN-MCQ-08 row 18) and no new copy is added. An authorized creation action MUST be labeled “Add New Note” (CN-MCQ-08 row 2). When a note's author is unavailable, the note MUST be kept and MUST show the neutral unavailable-author label “Unavailable author” / “صاحب الملاحظة غير متاح” (CN-MCQ-06; CN-MCQ-08 row 26). No user-visible copy is approved outside the CN-MCQ-08 table (rows 1–29), the CN-MCQ-16 table (rows 30–33) and the CN-MCQ-19 row 34 in Clarifications.
- **FR-003**: A note MUST have no version history. Only its author or a Platform Owner MAY edit it, and an author MAY edit only while holding current authorization in the note's workspace: an active membership and a role still authorized for Client Notes under FR-004 (CN-MCQ-05). A successful edit MUST replace the current body in place, set an “edited” timestamp, and keep the original author and creation timestamp (CN-MCQ-03). The database MUST refuse any UPDATE that changes `id`, `workspace_id`, `client_id`, `author_user_id`, `created_at` or `idempotency_key`; an edit changes only `body` and `edited_at`. Only a Platform Owner MAY permanently hard-delete a note.
- **FR-004**: Authorized Trainers, Workspace Owners, and Platform Owners MAY view and create notes within their authorized workspace scope. A Trainer MAY view and create notes for any client in their workspace, regardless of assigned Trainer (S37-PO-6, S37-PO-7; CN-MCQ-04). Platform Owner scope MUST follow the existing merged F3 platform-wide PO rule of `app_private.has_workspace_access`, which grants Platform Owner access without a membership row; this is the existing PO rule, recorded in plan.md Complexity tracking, and no constitution change is made (CN-MCQ-25; S40-PO-12 option A, architect mapping). Application authorization MUST use the existing verified-actor and role/membership model. A Client or Sales actor MUST be denied. UI visibility MUST NOT act as a security boundary.
- **FR-005**: Notes MUST be workspace-scoped. Backend authorization and database RLS MUST enforce the same deny-by-default access policy for read, create, edit, and hard delete. Every note request MUST be bound to its client and workspace; a caller-supplied foreign workspace/client/author MUST NOT widen access. Cross-workspace and per-role denial coverage MUST be specified.
- **FR-006**: The behavior answered by the PO (CN-MCQ-01..14, CN-MCQ-18 and CN-MCQ-19) is encoded in FR-001..FR-011 and the scenarios above. Copy governed by CN-MCQ-08 is encoded from the approved S38-PO-2 table, by row number; copy governed by CN-MCQ-16 is encoded from rows 30–33 (S38-PO-11); copy governed by CN-MCQ-19 is encoded from row 34 (S40-PO-3, option Variant 1 (Recommended)). The Client Notes UI MUST reuse existing Design System components and their existing values (S38-R9): the DESIGN.md §6 tabs pattern, the existing textarea, button, dialog, toast and States components, and the existing tokens and breakpoints. It MUST NOT introduce a new breakpoint, touch-size, focus or token value. If implementation later needs a value that exists neither in DESIGN.md nor in an existing component, that becomes a PO question at that time under the frontend design gate and MUST NOT be implemented as a guess.
- **FR-007**: The tab MUST follow DESIGN.md and the existing Design System for EN LTR / AR RTL, typography, keyboard access, visible focus, accessible labels/roles, contrast, and loading/empty/error/success/disabled/pending/interaction states. The tab and its actions MUST be text-only with no icon (CN-MCQ-10). The tab label, state messages, action labels, “edited” and byline labels, and the “Unavailable author” and permission messages MUST use the exact CN-MCQ-08 table strings (rows 1–29). Mixed-direction user text MUST be wrapped in the existing `Bidi` component (README.md, mixed-direction data; `components/ui/Bidi`) and MUST NOT be machine-translated. Exit protection (DESIGN.md §5, Q54, PO-approved session 14): while a note create or edit field holds unsaved changes, leaving the editor (navigating away, closing it or cancelling) MUST show a warning with Stay and Discard choices; Stay keeps the unsaved text and Discard leaves the editor, discarding only text that has not been submitted. A save already submitted is not cancelled: the server either commits or refuses it, and a committed save keeps its row, its edit metadata and its one audit event (CN-MCQ-17; S39-PO-8). The spec MUST NOT promise cancellation, or "no row persisted", for an in-flight save. Save Draft MUST NOT be offered (S38-PO-10). For text that has not been submitted, the warning title, body, Stay label and Discard label MUST be the exact CN-MCQ-16 strings in Clarifications rows 30-33 (S38-PO-11). While a create or edit save is in flight, the warning body MUST use the separate in-flight body from CN-MCQ-19 row 34, i18n key `clientNotes.exitWarning.bodyInFlight`, approved byte-exact by S40-PO-3 (option Variant 1 (Recommended)): leaving cannot cancel a save already sent. Rows 30-33 are unchanged: row 31 (body) applies only to text that has not been submitted, while rows 30, 32 and 33 (title, Stay, Discard) also label the in-flight warning; row 34 replaces only the body while a save is in flight. While a create or edit save is in flight, the note field MUST be read-only until the server result is known; editing resumes only after the save is committed or refused. Because the field cannot accept text in that state, only row 34 applies while a save is in flight and no combined warning state exists (CN-MCQ-21; S40-PO-6 option A, architect mapping). If the save outcome is unknown (the request never reached the server or its response was lost), the editor MUST retain the text, keep the field read-only, never indicate that the save succeeded, and show the existing generic save-error state (CN-MCQ-08 row 18) with the existing Retry action (CN-MCQ-08 row 17). A create Retry MUST reuse the same client-generated idempotency key and the original submission body; an edit Retry re-sends the edit. The actor MUST NOT start a duplicate create while the outcome is unresolved, and editing MUST NOT resume until the attempt is resolved: the note is created or returned, the key's note is deleted/not-found, the key's outcome is known after reconciliation, or (when no retry of that create was ever sent) the original request receives a definite refusal. A refusal of a Retry after an unknown outcome is distinct and does not resolve the original attempt (the refused-Retry rule below). The actor may still leave via the existing exit-protection Discard, which does not cancel or resolve the submitted create. This applies DESIGN.md Q51 (Persistent Warning + Recovery for failed saves/network loss; PO-approved session 14) using only the approved CN-MCQ-08 strings; no new copy is added (CN-MCQ-21; S40-PO-6). While the save outcome is unknown, exit protection MUST use the approved CN-MCQ-16 title, Stay and Discard rows 30, 32 and 33 with the approved generic save-error body CN-MCQ-08 row 18; the in-flight body row 34 and the unsaved body row 31 MUST NOT be reused for that state. Leaving cancels nothing, and the unresolved create keeps its idempotency key so Retry can resolve it; no new copy is added (CN-MCQ-23; S40-PO-10 option A, architect mapping, not PO words). A Retry that the server refuses (for example after membership revocation) does not resolve the original create attempt: the text, the read-only field and the idempotency key stay as they are, and no new create starts until the original outcome is reconciled (CN-MCQ-23; S40-PO-10, architect mapping; no new copy). The unresolved create's recovery state MUST be kept in that tab's browser `sessionStorage`: the note text, the client-generated idempotency key and the original submission body. When `sessionStorage` is available, the record MUST be written before the create request is dispatched, so a same-tab reload while the request is in flight retains the key and original body and a later create cannot duplicate the note. It is held only on that device in that tab until the server result for that attempt is known, then cleared. It survives a same-tab reload only; a new tab, another device or another browser does not receive it, and closing the tab clears it under browser `sessionStorage` semantics, so the spec makes no reload or duplicate-prevention promise after a tab close. No server-side pending note body is stored (the content-free create-idempotency record in FR-011 holds only the key, scope and body fingerprint), and no new user-visible copy is added (CN-MCQ-24; S40-PO-12 option A, architect mapping). Clearing occurs only when the attempt is resolved: the server confirms the note was created (including a same-key/same-body retry returning the existing note, or a same-key reconciliation retry creating the first note when no key record exists), the server confirms the key's note was deleted/not-found, or the key's outcome is otherwise known. A definite refusal of the original create request alone does not clear the record when a retry of that create could have committed (for example a retry whose response was lost): the application MUST first reconcile the key with the server. The reconciliation outcomes are the existing note, deleted/not-found, or, when no content-free key record exists because the earlier retry never reached the server, the normal create path creating the first note with its one create audit event; an existing key record is never used to create a new note. The application MUST clear the record and resume editing only once no retry of that create could have committed or the key's outcome is known, so a later create with a new key cannot duplicate the note. When no retry of that create was ever sent, a definite refusal of the original request resolves the attempt (it was not accepted) and editing resumes. A refusal of a Retry after an unknown outcome is distinct: it does not resolve the original attempt and does not clear the record (the refused-Retry rule above). An explicit Discard in the unknown-result state leaves the editor but does not clear that record, because the submitted create is not cancelled and is not resolved; only a known resolution or tab close clears it. The record is scoped to its workspace/client and create key, so it is not shared with, or overwritten by, another client's editor. It is also bound to the originating browsing context with a per-tab identifier that survives a same-tab reload but is not inherited by a new tab opened with an opener; a copied record whose identifier does not match the current context MUST NOT be treated as the current tab's state and MUST NOT overwrite or resolve the originating tab's record, and the application MUST ignore and remove such a copied record. The record MUST be bound to the signed-in actor (the verified author) and MUST be readable and retryable only by that actor. On sign-out or an account switch, the record MUST be cleared and MUST NOT be readable or retryable by the new actor, including through direct `sessionStorage` access. Same-actor recovery and duplicate prevention are preserved. Privacy (constitution Principle VII): this state is device-local, is never written to application logs or audit, and is cleared when the create is resolved. If the browser does not provide `sessionStorage` (for example storage is disabled), the same state is held in page memory only for the current page and the same-tab reload guarantee does not apply. For an edit whose outcome is unknown, the retained text and Retry state are held only in page memory for the current editor page; the tab-local `sessionStorage` recovery above applies to creates (CN-MCQ-24). The spec makes no promise that an unresolved edit survives navigation or reload: after a reload the note is read from the server at its last committed body, no success is indicated, and no Retry state for the prior edit attempt is restored. No new copy is added. The recovery safeguards above (retain the text, Retry, no duplicate create) remain specified. Browser close/reload: the browser's built-in warning is used (its text cannot be customized), as recorded in CN-MCQ-16. No new motion is required. Breakpoints, touch sizes, focus styling and tokens MUST be the existing values of DESIGN.md and the reused components (S38-R9; FR-006).
- **FR-008**: The note list MUST show notes newest-created first, ordered by server creation timestamp with a deterministic tie-break. An edit MUST NOT change a note's position in the list (CN-MCQ-01).
- **FR-009**: Concurrent edits to one note MUST resolve as last save wins (CN-MCQ-11): each save that satisfies FR-002 and FR-003 replaces the current body, and the winner is the write the database commits last (client clocks are not used). No stale-write rejection, merge or conflict prompt is defined. An edit retry after an unknown result is a new save of the same body, not an idempotent operation: Client Notes defines an idempotency key for creates only (FR-011), so an edit retry has no key and no stored original outcome to return. If the original edit committed and a later edit intervened, the retry follows last save wins and may replace that later body; each successful write emits its own audit event (FR-010). This is the existing last-save-wins and one-event-per-successful-save behaviour (CN-MCQ-11), not a new decision. Timestamps MUST be displayed in the viewer's local time zone (CN-MCQ-12) in the CN-MCQ-08 row 29 format: day, month name, year, then 12-hour time with AM/PM, with Western digits 0–9 (for example “8 Nov 2026, 10:15 PM” / “8 نوفمبر 2026، 10:15 م”).
- **FR-010**: Each successful note create, edit, and hard delete MUST emit exactly one audit event. Its note-specific content MUST be limited to the actor, workspace, client ID, note ID, action, and timestamp. In the existing `public.audit_events` table these map to `actor_user_id`, `workspace_id`, `details` (client ID), `target_id` (note ID), `action`, and `occurred_at`. The table's structural fields (its generated `id`, the required `target_table` naming the note relation, and the `details` object that carries the client ID) are not note content. An audit event MUST NEVER contain note text, and no generic row-snapshot capture may store note body content in audit (CN-MCQ-07). Note text MUST NOT be written to application logs (constitution Principle VII). Client Notes audit events MUST follow the app's existing audit retention unchanged: no Client Notes retention setting, purge, or override is added (CN-MCQ-13). The existing policy is defined by the immutable `public.audit_events` table (`supabase/migrations/20261027150000_audit_log.sql`, update, delete and truncate blocked by triggers); its period is an open pre-production decision (DP-02 / ND-F5-1 / B4, `docs/13-production-readiness.md`), which Client Notes inherits and does not decide. The note mutation and its audit event MUST be written in the same database transaction: if the audit write fails, the mutation MUST roll back and no successful audit event remains. A rejected or denied operation MUST NOT produce a successful note-mutation event; this follows the existing audit rule in `specs/005-audit-log/spec.md` User Story 1, scenario 2 (a write the database rejects produces no event), and Client Notes adds no denial-audit event type.
- **FR-011**: Every note create MUST carry a client-generated idempotency key, generated once per create attempt and re-sent unchanged on every retry of that create; a retry MUST re-send the same body as the original submission. Body equality is checked after leading and trailing whitespace is trimmed (the FR-002 trim), so a body that differs only by surrounding whitespace is the same retry body and a materially different trimmed body is a mismatch. The database MUST enforce uniqueness of the key within the note's workspace/client scope through a content-free create-idempotency record that survives a note hard delete and never retains the note body or note text (CN-MCQ-20; S40-PO-6 option A, architect mapping). The note row MUST also be unique on `(workspace_id, client_id, idempotency_key)` while it exists, so at most one live note can reference a key; the key record and the note MUST be written atomically by a hardened database write boundary, and a direct or concurrent write that would create a second live note for the same triple MUST be refused. A hard delete MUST set the surviving key record's deleted state, remove the note row and write its one delete audit event in the same transaction; a failure of any step rolls back all of them, so no key is left in the created state without a live note and a retry always sees a consistent deleted/not-found outcome (CN-MCQ-20; S40-PO-6). A duplicate create that reuses a key already used in that scope and re-sends the same trimmed body MUST return the existing note row instead of creating a second note; under FR-010 no second create audit event is emitted. A create whose result is not observable MUST be retryable without producing a duplicate note (CN-MCQ-18; S39-PO-9; architect mapping, not PO words). A same-key create that carries a different trimmed body MUST be rejected as a key/body mismatch while the note is live: no second note, no change to the existing note's body, and no create audit event (CN-MCQ-22; architect ruling S40-R9, option A). After the note is hard-deleted, the deleted/not-found outcome takes precedence over the body-mismatch rule: a same-key retry MUST return a deleted/not-found outcome regardless of its body and MUST NOT recreate the note or emit a create audit event; the hard delete still removes all note content, and the surviving idempotency record holds only workspace/client scope, key and a content-free body fingerprint of the original trimmed body used to detect a mismatch — never the note body (CN-MCQ-20; S40-PO-6 option A, architect mapping). The key MUST NOT substitute for verified actor, role or workspace/client scope (FR-004, FR-005). No new user-visible copy is introduced: the mismatch and deleted/not-found outcomes use the existing generic save-error state (CN-MCQ-08 row 18) (CN-MCQ-22; S40-R9; copy reuse for CN-MCQ-20 is an architect mapping, not PO words). No migration file is added by this spec-only PR.
