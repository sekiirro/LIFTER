# Implementation Plan: F20 Client Notes

CN-MCQ-26..29 are resolved by S51-PO-1 and the verified author-source audit. CN-MCQ-30 remains open only for a future data-model/scope change; the current F20 fallback is decided and implementable.

## Summary

Add independent plain-text notes to Client Details with a workspace/client composite scope and two authorization walls. Trainers (for any client in their workspace, regardless of assignment), Workspace Owners and Platform Owners may view and create within current authorized scope; only the note author with current active membership or the Platform Owner may edit; only the Platform Owner may hard-delete. Sales and Clients are denied. Creates are idempotent per client-generated key, edits are last save wins, audit is metadata only, and no version-history behavior is added.

## Technical context

- Next.js App Router, server-verified identity and existing application `authorize()`.
- Supabase Postgres with RLS enabled and forced; signed identity and active workspace membership are authoritative.
- Reuse F3 `public.staff_profiles`, `public.workspace_memberships`, `app_private.has_workspace_access()`, approved `coaching_work` capability, and F11 `public.clients`.
- Follow current hardened database access patterns and keep app/database decisions in parity. Do not introduce a new role or weaken RLS.
- Historical origin scan (round 3, run report): highest `20261108021002` across 91 fetched origin refs. This figure is NOT relied upon. Any future migration requires a fresh scan of all origin refs immediately before selecting a unique forward-only version above the then-highest version, again immediately before the commit, and again before push. ## Design

### Authorization and data

- Tenant entity proposal is in [data-model.md](data-model.md): a note row keyed to both `workspace_id` and `client_id`, with verified author, plain-text body, server creation timestamp, nullable `edited_at` and a client-generated `idempotency_key` unique with the workspace/client scope (FR-011).
- Read/create require a Trainer, Workspace Owner or Platform Owner with current authorization for the workspace. Trainers are not limited to assigned clients (CN-MCQ-04, S37-PO-6, S37-PO-7). PO follows the existing merged F3 platform-wide `app_private.has_workspace_access` rule, which grants Platform Owner access without a membership row; this is the current platform-wide PO rule and the later S47-PO-14 amendment resolves Principle I in constitution 1.13.0 is made (CN-MCQ-25; S40-PO-12 option A, architect mapping).
- Author edit checks the original `author_user_id`, current authorization in the workspace (active membership and a role still authorized) and current scope. PO edit is also scoped through the existing PO access helper.
- Delete checks PO role and workspace scope at the database boundary. Non-PO delete is refused even when actor authored the note.
- RLS is deny-by-default. No anonymous grants. Define tests for allowed role × action pairs, Sales/Client/anonymous denial, non-PO revoked membership denial, and foreign-workspace denial.
- Body: all leading and trailing whitespace is removed, the result must be 1 to 5,000 Unicode code points, and the trimmed text is stored; interior formatting is preserved. A body blank after trimming is rejected (CN-MCQ-02, CN-MCQ-14; S37-PO-16). A body containing U+0000 is rejected at both walls with no row persisted, using the existing generic save-error state (CN-MCQ-08 row 18); no new copy.
- Create idempotency (CN-MCQ-18; S39-PO-9; CN-MCQ-20; S40-PO-6; CN-MCQ-22; S40-R9; architect mapping/ruling, not PO words): the client generates one idempotency key per note create and re-sends the same key and the same body on every retry of that create. Body equality is checked after the FR-002 trim. The note row and the content-free create-idempotency record each enforce uniqueness of `(workspace_id, client_id, idempotency_key)`; a hardened database write boundary inserts the key record and the note atomically and refuses direct or concurrent duplicates. The key record survives a note hard delete and holds no body or note text; a required one-way fingerprint of the original trimmed body detects a body mismatch, including after the note was edited. A duplicate create that reuses the key with the same trimmed body returns the existing note row instead of inserting a second note while that note is live; the created note keeps exactly one create audit event under FR-010. A same-key create with a different trimmed body is rejected as a key/body mismatch while the note is live, with no second note, no body change and no create audit event. After a hard delete, a same-key retry returns a deleted/not-found outcome regardless of the retry body, taking precedence over the mismatch rule, and never recreates the note. If no content-free key record exists because the earlier retry never reached the server, the same-key retry follows the normal create path and creates the first note with its one create audit event; an existing key record is never used to create a new note (FR-007). The key is not an authorization factor and never substitutes for the verified actor or the workspace/client scope. The migration versions for this behavior are recorded in the technical context above.
- No version table/history. Edits are last save wins (CN-MCQ-11): the winner is the write the database commits last, and `edited_at` is set (CN-MCQ-03). `id`, `workspace_id`, `client_id`, `author_user_id` and `created_at` are immutable; a direct UPDATE changing any of them is refused.
- Audit: one metadata-only event per successful create, edit or hard delete (actor, workspace, client/note IDs, action, timestamp). Audit never stores note text, and no generic row-snapshot capture may store body content (CN-MCQ-07). Retention is the existing `public.audit_events` policy, inherited unchanged (CN-MCQ-13). The note mutation and its audit event share one database transaction (a failed audit write rolls the mutation back). Rejected or denied operations emit no successful note-mutation event (`specs/005-audit-log` US1 scenario 2).
- Ordering: `created_at` descending with `id` tie-break; edits do not reorder (CN-MCQ-01).
- Migration is described only: future additive/forward-only schema + indexes/constraints/policies or safe mutation functions, chosen after fresh all-origin-ref scan. No concrete version or SQL is authorized here.

### UI

- Surface: the authorized staff Client Details route with a minimal extensible horizontal tab container hosting only the functional Client Notes tab; no placeholder tabs or unrelated client panels. Keep it independent of Exercise Library and Workout Planner (S49-PO-7; S49-R21 mapping).
- Tab placement: horizontal tab alongside the existing client profile tabs (CN-MCQ-09). Text-only, no icon (CN-MCQ-10).
- Follow DESIGN.md §3–6, §11–12 and existing design tokens/components: Geist for English, IBM Plex Sans Arabic for Arabic; support EN LTR and AR RTL; existing client-profile mobile pattern is horizontally scrollable tabs.
- Timestamps use the viewer's local time zone (CN-MCQ-12) in the CN-MCQ-08 row 29 format.
- Strings: only the approved CN-MCQ-08 table in spec.md (rows 1–29), the approved CN-MCQ-16 table (rows 30–33) and the approved CN-MCQ-19 row 34 are used; no other copy is added. Mixed-direction text uses the existing `Bidi` component (README.md).
- Do not invent colors, layout details, responsive breakpoints or token values. The Client Notes UI reuses existing Design System components and their existing values (S38-R9): the DESIGN.md §6 tabs pattern; the existing textarea, button, dialog, toast and States components; existing tokens and breakpoints. It introduces no new breakpoint, touch-size, focus or token value. A value that exists neither in DESIGN.md nor in an existing component becomes a PO question only when implementation needs it, under the frontend design gate.
- Exit protection (DESIGN.md §5, Q54; spec.md FR-007): an editor with unsaved create or edit text shows a Stay/Discard warning on exit, using the CN-MCQ-16 strings (rows 30-33) and no Save Draft. Discard leaves the editor and discards only text that has not been submitted. A save already submitted is not cancelled: the server commits or refuses it, and a committed save keeps its row and its one audit event (CN-MCQ-17; S39-PO-8). Browser close/reload uses the browser's built-in warning (its text cannot be customized).
- In-flight warning body (CN-MCQ-19; S40-PO-3, option Variant 1 (Recommended)): when a create or edit save is already in flight, the warning body uses CN-MCQ-19 row 34, i18n key `clientNotes.exitWarning.bodyInFlight`, approved byte-exact: EN “Your note is being saved. Leaving now won't cancel the save.” / AR “ملاحظتك بتتحفظ. لو خرجت دلوقتي، الحفظ مش هيتلغي.”. It states that leaving cannot cancel the save already sent. Rows 30-33 are unchanged: row 31 (body) applies only to text that has not been submitted, while rows 30, 32 and 33 (title, Stay, Discard) also label the in-flight warning. While a save is in flight the note field is read-only, so only row 34 applies in that state and no combined warning state exists (CN-MCQ-21; S40-PO-6 option A). If the save outcome is unknown (no response), retain the text, keep the field read-only, show the existing save-error state (CN-MCQ-08 row 18) with the existing Retry action (row 17), never indicate success, and reuse the original create key and body on a create Retry; no duplicate create starts until the outcome is resolved (DESIGN.md Q51; CN-MCQ-21). While the save outcome is unknown, exit protection uses the approved CN-MCQ-16 title, Stay and Discard rows 30, 32 and 33 with the approved generic save-error body CN-MCQ-08 row 18; rows 34 and 31 are not reused for that state, leaving cancels nothing, and the unresolved create keeps its key for Retry (CN-MCQ-23; S40-PO-10 option A, architect mapping; no new copy).
- Unresolved-create recovery state (CN-MCQ-24; S40-PO-12 option A, architect mapping; constitution Principle VII): the editor keeps the note text, the client-generated idempotency key and the original submission body in that tab's browser `sessionStorage` when storage is available and the write succeeds (page-memory fallback below) until the server result is known, then clears it. When `sessionStorage` is available, the record is written before the create request is dispatched, so a same-tab reload while the request is in flight retains the key and original body and a later create cannot duplicate the note. If that pre-dispatch write fails (for example `QuotaExceededError`), the failure is treated as unavailable storage: the create request still proceeds, the state is held in page memory only for the current page, and the same-tab reload guarantee does not apply, so the duplicate-prevention guarantee does not apply across that reload and a later create can duplicate the note; no new copy is added. When written, it survives a same-tab reload only; a new tab, another device or a closed tab has no such state, so no reload or duplicate-prevention promise is made after a tab close. No server-side pending note body is stored; only the content-free create-idempotency record (key, scope, body fingerprint) exists. Clearing happens only when the attempt is resolved (the note is created or returned, the first note is created when no key record exists, the key's note is deleted/not-found, or the key's outcome is known); a definite refusal of the original create request clears the record only when no retry of that create was ever sent, and when a retry could have committed the key is reconciled with the server first. The reconciliation outcomes are the existing note, deleted/not-found, or the normal create path creating the first note when no content-free key record exists; an existing key record is never used to create a new note. Only a confirming outcome clears the record, so a later create cannot duplicate the note. A refusal of a Retry that does not resolve the attempt keeps the state, and an explicit Discard in the unknown-result state does not clear it. The record is bound to the originating browsing context with a per-tab identifier that survives a same-tab reload but is not inherited by an opener-created tab; a copied record is ignored and removed and cannot overwrite or resolve the originating tab's record. The record is bound to the signed-in actor and cleared on sign-out or an account switch, so another actor cannot read or retry it. The state is never written to logs or audit. If browser `sessionStorage` is unavailable or a pre-dispatch write to it fails (for example `QuotaExceededError`), the state is held in page memory only for the current page, the create request still proceeds, the same-tab reload guarantee does not apply, and the duplicate-prevention guarantee does not apply across a reload. An unresolved edit's retained text and Retry state are current-page only and do not survive navigation or reload (CN-MCQ-24 applies to creates; no new copy).

## Risks and mitigations

- **Cross-workspace exposure**: composite client/workspace integrity, `(workspace_id, id)` unique keys on the note and the create-idempotency record (constitution Principle I), two authorization walls and direct RLS negative coverage.
- **Role drift**: reuse the existing role matrix and assert app/database parity.
- **Attribution**: original author and creation timestamp are kept; edits set `edited_at` only.
- **Duplicate note on retry**: a client-generated idempotency key plus note-side and key-record unique constraints on `(workspace_id, client_id, idempotency_key)`, written atomically by a hardened boundary, return the existing note on a duplicate create; body equality is checked after trimming; a same-key different-body retry is a mismatch refusal while the note is live; a retry after a hard delete returns deleted/not-found regardless of the retry body and never recreates the note; a retry after an edit compares against the original submission fingerprint, not the edited body; a reconciliation retry with no key record follows the normal create path and creates the first note with its one audit event; tests cover retry without an observable result, duplicate-key reuse, mismatch, retry after delete (including a different body), retry after edit, the no-record create path, direct/concurrent writes and the same key in another workspace/client scope (CN-MCQ-18, CN-MCQ-20, CN-MCQ-22; FR-007, FR-011; S40-PO-6; S40-R9).
- **Unapproved interaction/copy**: UI copy is only the approved CN-MCQ-08 table (rows 1-29), CN-MCQ-16 table (rows 30-33) and CN-MCQ-19 row 34; no other string is implemented or guessed; design values come only from the reused Design System components (S38-R9); no icon is used.
- **Overpromised exit outcome**: the exit-protection wording claims only what is decided: unsubmitted text is discarded, and a submitted save is never cancelled but takes the server result (committed or refused) with its audit event (CN-MCQ-17; S39-PO-8). The note field is read-only while a save is in flight, so no combined pending/unsubmitted warning state is promised (CN-MCQ-21; S40-PO-6). An unknown save outcome retains the text and offers the existing Retry and save-error states without falsely indicating success (DESIGN.md Q51; CN-MCQ-21).
- **Device-local recovery state**: an unresolved create's text, key and original body live only in that tab's browser `sessionStorage` until the resolution, with same-tab reload only and no server-side pending body (CN-MCQ-24; S40-PO-12). The spec states the tab-close, new-tab, storage-unavailable and failed-write limits instead of promising a broader recovery or duplicate prevention; the state is never logged or audited (constitution Principle VII).
- **Audit/content duplication**: audit payload is metadata only (CN-MCQ-07); a generic row-snapshot audit must not store body text. Retention is inherited from `public.audit_events` (CN-MCQ-13); the existing period stays open as DP-02.
