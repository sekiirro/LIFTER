## Technical choices and rationale

- **Points representation**: exact signed base-10 numeric values store +1, −0.5 and PO-configured feedback/transformation weights without an unapproved point-scale limit. Never use binary floating-point for point totals.
- **Ledger and F19**: separate append-only KPI ledger entries for non-F19 changes; never mutate F19. Store deterministic source key and actor/reason attribution so replay is safe.
- **Month math**: Africa/Cairo date boundary follows existing finance/month behavior in F10/F12 and the recorded collection-month convention. Store period key as the Cairo calendar month, with event/effective time and recorded time separately.
- **Compensation currency**: F9 supports EGP only for Egypt and EGP/USD/SAR for International; no exchange rate is assumed. Basic Salary's currency/period remains pending P7-MCQ-02.
- **Snapshots**: immutable close records retain calculation version, source watermark/IDs, totals and staff attribution. A separate authorization-safe read projection serves each role.
- **Sales data minimization**: never grant Sales a base ledger/table read. Expose a row only if caller is Sales, row staff_id equals authenticated staff, period is Cairo month-end finalized, and selection has no detail columns. Deny via every read route and export.
- **Dedup/concurrency**: unique deterministic keys for F19 award, plan penalty, successful-submission follow-up penalty, refund reversal, and PO operation receipt. Lock/serialize at workspace-period/staff key, recheck role after wait, and bind retry to canonical argument hash.
- **Retention**: retain employee attribution and aggregate KPI event facts needed for historical totals; avoid client name/phone/username/answers in KPI facts. A client linkage used for idempotency must be pseudonymized/removed when F26 says the client data expires; audit events remain a distinct retention system.
- **Forms**: statuses specified by PO-16 are workforce projections over existing F15/F23 records, not replacements for source form status/history. Preserve Late as an append-only transition even if the current follow-up state becomes Followed Up.
- **Telegram feasibility (post-launch documentation only)**: Read only the post-launch section of `C:/Users/NEW LAP/.lifter/runs/s70-hy4-p7telegram/telegram.md`. Its official-source audit concludes PARTIAL: Bot API can provide inbound message timestamps, connection state and bot-authored replies for connected Business/Chat-Automation bots ([Message](https://core.telegram.org/bots/api/types/message.md), [Update](https://core.telegram.org/bots/api/types/update.md), [Business Bots](https://core.telegram.org/bots/features#business-bots)), but human-Trainer reply timestamps and human attribution are UNVERIFIED; ordinary bots cannot observe human-to-human chats ([Privacy Mode](https://core.telegram.org/bots/features#privacy-mode)). Telegram's [Business chatbot terms](https://telegram.org/tos/bot-developers#5-4-telegram-business) and [data retention terms](https://telegram.org/tos/bot-developers#4-2-data-storage-and-retention) impose data-minimization/retention obligations.
