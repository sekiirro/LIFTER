# Data Model - P7 Workforce Management

Logical model only; this is not an approved physical schema or migration. F10/F12/F13/F15/F19/F23/F26 remain owners of their source facts. P7 retains its own non-PII facts needed to preserve staff accounting.

## Invariants

1. Tenant-owned P7 records include workspace_id; cross-workspace references are prohibited.
2. Source facts remain immutable. Point correction, reversal, reassignment and monthly-quality changes append records.
3. P7 earned facts are durable, authoritative accounting rows. Each stores staff, workspace, exact amount, trigger/effective Cairo month, rule version and opaque source key. They have no FK to client-scoped rows and no client PII. Snapshots never recompute from purgeable F19/F10 client sources.
4. Points use exact numeric scale 2 values; API wire format is canonical decimal strings; JavaScript floating-point math is prohibited. Quality weights have no more than two decimal places.
5. Each logical effect has a deterministic source key and canonical argument hash. Same-key/same-args replay returns the same result; changed-argument replay fails.
6. Monthly quality revisions are append-only; exactly one latest effective revision per Trainer/month/category contributes. Older revisions remain history but are not summed.
7. Salary is one monthly entitlement per person, not per workspace. Platform PO owns it across that employee's workspace memberships. Market currency is PO-selected from existing allowed currencies. Point/KPI reports remain workspace-scoped.
8. Payroll is an externally paid assertion, not a payout instruction. At most one approval per employee/month, uniquely bound to a reviewed immutable payroll snapshot version, exact amount and currency.
9. Sensitive P7 financial/KPI detail is stored in PO-only P7 records. audit_events.details carries only an opaque reference for these actions; unrelated WO audit access is preserved.
10. **S70-R101**: Every manual monetary input uses the employee's salary currency effective for that input month and rejects a mismatch. Inputs retain their captured currency after later salary changes. A monthly snapshot uses the salary record effective for that month and rejects the snapshot if its active salary and input rows mix currencies; no FX conversion is performed.

## Net point calculation

NetPoints(workspace, staff, month) = Earned + Transformation/Feedback - Penalties + PO Adjustments.

Persisted entries use signed values and are summed once. Negative totals are valid. Penalty categories include plan delay (-1) and check-in delay (-0.5); any completed acquisition refund has one Sales point reversal. Earned facts include F19 Trainer activation (+1) and eligible F10 Sales acquisition (+1). Exact decimal strings cross API boundaries.

## Trigger time and period

Initial point periods use the Africa/Cairo month when the trigger happens; record trigger/effective time separately from ingestion/recorded time. Trainer award: client activation. Sales award: approval plus confirmed first payment. Check-in penalty: 24-hour deadline passes without follow-up. Plan penalty: persisted F15 D-03 deadline passes. Quality entries: PO-selected month. A late correction for a closed month is effective in current open month, linked to original month. Closed snapshots and Sales totals never change.

## Concurrency and idempotency

Every point producer and finalizer acquires one shared workspace+month advisory fence after existing source locks. Document one lock order that follows existing source transaction locks (including F12/F13 client/subscription/obligation/payment ordering) before the P7 period fence. This covers first events for staff with no prior period row, multiple staff, refund, reattribution and close. Enforce unique event keys independently of request idempotency keys. Changed canonical replay arguments fail. Stale PO edits and stale payroll snapshot approval reject without mutation; authorization is rechecked after waiting.

## Retention and audit

Retained earned facts, adjustment rows, snapshots and source-unit maps contain no client FK or PII. Client-linked check-in follow-up/questionnaire rows participate in the narrow F26 purge allowlist/unlink path. F26 tied-record purge pauses while an open P7 follow-up dispute or full-refund staff-fault review exists, then restarts the 30-day clock upon resolution. Staff totals and attribution survive because P7 retains non-PII facts; audit_events is never the KPI source. P7 financial/KPI audit payloads carry opaque reference only; detailed evidence is PO-only.

Strike events and corrections are retained staff history and contain no client FK or PII. The source key is opaque and is not a client identifier. Strike generation consumes the already-persisted F15 D-03 deadline and the first successful initial plan pair; it does not recompute the deadline. F26 client purge does not remove strike history. Strike corrections are append-only, PO-only, opaque in audit, and independent from P7 point corrections.

## Security projections

- PO: full authorized workspace detail and person-level compensation/payroll administration.
- WO: no P7 payroll/KPI detail; preserve unrelated existing audit permissions.
- Trainer: narrow all-Trainer Check-ins history in own workspace; own compensation only; no KPI/payroll detail.
- Sales: own compensation; only own finalized monthly point total after month-end and finalization. No live/formula/detail, including via raw tables, Realtime, counts, notifications, exports, cache or replay.
