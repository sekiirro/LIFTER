# F14 Data Model

This is a logical model for implementation planning. It specifies no SQL, migration syntax, or physical schema. Names below are conceptual and subordinate to the approved F14 specification and plan-approval items.

## Entities

| Entity | Scope and lifecycle | Required invariants |
|---|---|---|
| Workspace brand draft | One editable draft per workspace; revision increases on each accepted edit | Workspace-bound; editable only by `manage_branding` with explicit authorized scope; each save uses compare-and-set against the submitted revision. |
| Brand draft fields | Required name in one locale; optional second locale with fallback; brand color; optional logo/banner references and bilingual banner alt text | Color is `#RRGGBB`; semantic tokens are not configurable. Banner is image-only with PO-confirmed bilingual alt-text fallback; no banner text/CTA/link/pricing/contact. |
| Brand asset | Workspace-qualified content hash, asset role (logo/banner), validated format, dimensions, byte size, immutable validated object reference | Hash is not a credential; no cross-workspace deduplication. Only structurally validated, metadata-stripped PNG/WebP enters the validated state. |
| Upload operation | Durable state machine associated with workspace, role, target draft revision, staging object and eventual validated asset | Private staging → server validation → immutable validated object → revision-checked draft attachment. Interrupted upload and failed attachment are reconcilable; cleanup is reference-safe. |
| Published brand version | Immutable snapshot of current branding with workspace-scoped sequence number, author/time, fields and asset references | Changed publish atomically snapshots, advances current pointer and writes one detached audit event. Stale publish rejects. Unchanged publish is a no-op. Only the latest snapshot is retained long-term; a replaced snapshot is eligible for GC when unreferenced. No historical restore/rollback capability. |
| Current publication reference | Workspace-scoped pointer to current published version or no-publication default | Updates only with an atomic successful publication; each request resolves authorized workspace and version server-side. |
| Branding audit event | Permanent append-only record for publication, independent of version/asset retention | Exactly one `branding.published` event per changed successful publication; detached sequence metadata and changed field names only. No FK dependency on deletable version/assets and no object IDs, bytes, authored text, tokens or URLs. Extend the latest F11 audit trigger body and preserve every existing mapping. |
| Render handle | Cryptographically unguessable opaque short-lived capability minted by extended `registration_link_open(token)` and stored only as a hash, bound to registration link, workspace and exact published version | Bounded per-link active-handle count and issuance rate, expiry and cleanup; exact caps are specified before implementation. Possession alone is insufficient without visitor token and restricted proxy credential. No selectable version/object identifier. Image calls never set `opened_at` or extend grace. |
| Branding service credential registry | Private credential ID, identity kind (`branding_proxy`/`branding_validator`), enabled state, issuance/disable audit metadata | Contains no bearer JWT. Every privileged RPC/policy checks the signed credential ID against enabled registry state. Rotation enables replacement, deploys it, then disables old ID; emergency disable applies immediately. |
| Validator receipt | Server-only proof bound to upload operation, source staging object, validated object/hash, validation outcome and validator credential ID | Created only by `branding_validator`; owner JWT cannot fabricate or directly promote validated bytes. Receipt contains no image bytes or bearer token. |
| Deletion claim | Transactional, leased claim that marks an otherwise unreferenced object as deleting before Storage byte deletion | Every operation that can create a draft/version/upload reference checks and rejects or serializes against a deleting claim. Finalization follows verified Storage deletion; retry is safe and references can never race into a deleting asset. |
| Surface brand projection | Published tokens and permitted identity fields for Registration, Staff Dashboard, and Client Portal only when P4 exists | No shared actor/workspace cache; discard late workspace-switch responses; neutral defaults without scope. Client Portal contract does not add portal features. |

## Relationships and retention

- Every draft, version, asset, upload operation, and current-publication reference is bound to exactly one workspace. Composite relationships and workspace-prefixed Storage paths prevent cross-workspace attachment. Every render handle binds one link and one immutable published version; every image resolution is also bound to one allowed role/slot and derives the exact bucket/object path server-side.
- Draft and published snapshots may reference validated objects. Active upload references protect staging and validated objects during attachment/reconciliation.
- At publish time, the previous current snapshot is no longer retained long-term; its asset references become GC-eligible once no longer referenced by the new current publication, a draft, or an active upload. GC claims deletion transactionally and every reference-creating operation must respect the claim; deletion is retryable, bounded, and rechecks references. Permanent audit events remain and do not point to collected version rows or object bytes/URLs.
- A render handle is not a retention reference. If publication advances before an old page requests an image, the old handle cannot retrieve the prior object: the proxy either creates a fresh authorized resolution or fails generically. It never serves bytes from a deleted version.
- Capacity calculations count up to two assets for the current publication, draft/staging overhead, workspace volume, and proxy no-store egress against verified allowances and the 70% exit trigger.

## Authorization and storage boundary

- App wall: `authorize(actor, 'manage_branding', workspace)`; deny by default, explicit workspace scope, PO global authority (not contingent on workspace membership), WO active membership in own workspace only.
- Database wall: `has_workspace_access()` / capability helper in `SECURITY DEFINER` functions with `search_path=''`, plus forced RLS and bucket-qualified `storage.objects` policies.
- Anonymous users cannot list/read Storage directly. Cross-workspace access and mutation of published objects are denied. Public image bytes are available only through the token-validating proxy, never through client-visible signed URLs.
- `branding_proxy` and `branding_validator` are restricted `NOLOGIN NOBYPASSRLS` database roles, without privileged memberships or unrelated table access. Their expiring JWTs are issued externally; Workers contain neither project JWT signing key. A verified signed credential ID must be enabled in the private registry.
- Only `branding_proxy` executes `registration_brand_asset_resolve(token, render_handle, slot)` and `app_private.branding_storage_read_allowed(...)`; only the exact validated-bucket download operation is allowed by `branding_proxy_object_read`. The helper repeats live F10 and render binding checks. Only `branding_validator` creates validation receipts and promotes validated immutable bytes. Owner stage/attach/publish operations use user JWTs and current `manage_branding` authority.
- New definer functions use `SECURITY DEFINER SET search_path=''`, fully qualified references, explicit owners and grants. Revoke execute from `PUBLIC`, `anon`, `authenticated`, and `service_role` by default, then grant only named execution roles. Prefer a restricted no-login function owner with explicit RLS predicates over postgres-owned omnipotent functions.
- The existing Worker also holds a service-role key for the PO-approved D-19 manual recovery route. F14's GC function grants, if approved, apply service-role only to the bounded audited-cron operation; this does not mean service-role is confined to cron across the application. Any F14 use remains explicitly scoped, audited and subject to PO/architect review.

## Upload state model

The exact enum is intentionally not fixed. The required durable transitions are: staging accepted; validation in progress; validation rejected or validated; immutable validated object created; draft attachment succeeded or attachment failed/stale; reconciliation pending/completed; cleanup eligible/deleted. Transitions must be idempotent and enough evidence must remain to reconcile interruption without logging credentials or image bytes.
