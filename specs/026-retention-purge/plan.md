# Implementation Plan: F26 Retention Purge Entry Point (DP-08)

This artifact is spec-only. It plans a future implementation lane; it does not authorize code, SQL, migrations, scheduler activation, or task ticks. The four implementation-facing questions Q1–Q4 are resolved by S70-PO-10 (all recommended options); every slice now has concrete state values, object tables and test names, and no slice is blocked on an open question.

## Summary

Extend the existing purge entry point so that it implements the S70-PO-5 clocks: 30 days from account closure/deletion for client, payment, refund and invoice data, and 30 days from creation for audit events, with a deletion hold for records tied to an open refund/dispute and a full 30-day restart at resolution. The scheduler stays disabled, the backup gates stay open, and every behavior is covered by RED-first tests and mutation evidence. No user-visible copy is added.

## Design

### Apply-mode mutation design

This is the T012 non-audit apply design under architect mapping S70-R76 (MCQ-026-2 = A). It is design-only: T012/T014 remain unimplemented pending architect approval of this section. T012 will never touch `public.audit_events`; that table is KEEP-unchanged in T012 and remains T014-only. Eligibility and the full 30-day clock/hold checks happen before these mutations. A stable `run_id` is unique per apply, and all selected client mutations plus the counts-only evidence commit atomically. A committed replay with the same ID returns the existing counts without changing rows or appending evidence; a failed transaction rolls back and can be retried with the same ID.

The matrix's DELETE rows are the complete recursive Stack E FK closure from `public.clients` after excluding the four Q4 financial evidence tables above. The closure includes direct/deeper dependents listed in each row; multi-parent rows are deleted only after every client-scoped child that references them. No auth user deletion occurs here: Auth purge ordering remains the DP-06 path already recorded above. No extra identifier, per-client evidence, or reversible lookup is written.

#### FK ordering and ledger reconciliation

First select only eligible client IDs (30 days elapsed, no open refund hold) and acquire the stable run record. In one transaction, retain the four Q4 evidence tables, sever their FK links to the rows being deleted, then delete all other client descendants deepest-first in reverse FK topological order, including form/plan/progress/nutrition/leaderboard projections, operation/idempotency rows, renewals/freezes/upgrades, registration facts, `subscription_installments`, and finally `subscriptions` and `clients`. Preserve intra-ledger payment predecessor/reversal references and refund allocation/cancellation references among retained evidence. FK constraints that point from retained evidence to deleted non-evidence parents are replaced with equivalent non-client integrity checks before the deletion migration is applied; the retained ledger is not left with dangling enforced FKs. The full FK graph and each affected constraint must be captured in the implementation migration/test before execution.

For reconciliation, `amount_minor`, `commission_minor`, `currency`, `collected_on`, `effective_on`, and `recorded_at` on payment/refund/allocation evidence are never rewritten. `refund_operations.client_id` alone becomes NULL. Existing amount/currency/date checks, payment revision/self-reference checks, refund allocation sums, and source-collection validation remain active against retained evidence. Subscription price/schedule rows are not retained as client data; any reconciliation needed for the retained posted ledger is derived from the immutable ledger facts, not reconstructed from a client anchor.

#### Trigger handling: narrow apply-only exemption

No trigger is disabled, no `session_replication_role` change is used, and no general-purpose bypass flag is added. The only exemption is a transaction-local run context set inside one postgres-owned `SECURITY DEFINER SET search_path = ''` internal apply function, reached only after the authenticated wrapper's S70-R61 `auth.uid() IS NOT NULL AND app_private.is_platform_owner()` check. Each affected guard function keeps its default-deny behavior and permits only its table's specific DELETE or approved evidence UPDATE when `current_user = 'postgres'`, the context run ID matches the active locked run row, and the table/operation is in a hard-coded allowlist. The context is cleared before return; wrapper ACL remains authenticated-only and internal apply remains postgres-only. No caller-controlled run ID alone can satisfy the guard.

The Stack E catalog found guards that conflict with these intended mutations. Shared `app_private.forbid_delete()` blocks DELETE/TRUNCATE on `app_private.account_deletion_intents` (`20261215010000_f11_account_deletion.sql:76`), `app_private.client_signup_operations` (dynamic trigger install at `20261031121000_client_accounts_model.sql:323`), public subscription/ledger tables (`20261101120000_registration_approval_model.sql:366-383`), F13 freeze/refund/renewal descendants (`20261103122000_f13_freeze.sql:145-147`; `20261103123000_f13_refund_ledger.sql:227-229`; `20261103126000_f13_renewal.sql:98-100`), and later manual-adjustment/productivity tables (`20261111221000_f13_manual_date_adjustment.sql:29-33`; `20261111222000_f13_trainer_productivity_points.sql:25-29`). Their paired `audit_events_immutable()` guards block updates and/or deletes on the same immutable tables; named trigger installations include payment events at `20261101120000_registration_approval_model.sql:381-383`, and F13 descendants at the three migrations just cited. Table-specific guards also block eligible deletes on `client_inbox_notices` (`20261118100100_f22_client_notice_inbox.sql:45`), username history (`20261203000000_f24_client_leaderboard.sql:239`), F15 assignment facts (`20261112020600_f15_approval_selection_assignment_consumer.sql:55`; `20261112031500_f15_po12_decisions.sql:40`), progress measurement corrections (`20261118200100_f23_progress_measurements.sql:51-55`), corrections (`20261112021100_f15_immutable_answer_corrections.sql:44-47`), legal holds/retention windows (`20261112020200_f15_s14_privacy.sql:107,141`), consent receipts (`20261112020000_f15_terms_consent.sql:59`), plan delivery operations (`20261114150000_f19_continuity_delivery_projection.sql:353`), subscription reattachments (`20261114150000_f19_continuity_delivery_projection.sql:21-23`), and F19 override operations (`20261118010100_f19_platform_owner_override.sql:30`). #### Run replay and evidence row

The apply ledger is keyed by stable `run_id` with a unique constraint and stores aggregate counts only: eligible clients, deleted rows by table, retained payment/refund/allocation/cancellation rows pseudonymized, held clients, and skipped-inside-window clients. It stores no client IDs, account identifiers, row IDs, email/phone/name, request payloads, or per-client reason. A matching completed run ID returns that aggregate row. A conflicting run ID bound to different immutable request parameters fails closed. The counts row is written in the same transaction as the mutations, so no partial evidence can claim a successful purge.

### Clock and eligibility model

- Introduce pure clock predicates (no I/O, no wall-clock read inside the predicate) for: closure/deletion clock for client/payment/refund/invoice rows; creation clock for audit events; and hold/restart for records tied to an open refund/dispute.
- A row is eligible only when the full 30 days have elapsed AND no hold is in force. The 30-day value and both clock starts come only from S70-PO-1 item 3, S70-PO-3, S70-PO-4 and S70-PO-5; they are not configurable by argument, flag, or environment variable in this feature.
- The hold restart uses the resolution time of the refund as the new clock start; elapsed time before resolution is not carried over. Per S70-PO-10 Q1 and architect mapping S70-R47, the only OPEN states are `pending`/`retry` in `app_private.refund_auth_lockouts.status` (`20261103120000_refund_auth_lockout_hook.sql:16`) and the sole RESOLVED state is `succeeded`. `public.subscriptions.status` (account activity, FR-002) and generic `public.jobs.status` are not hold predicates; no persisted dispute object exists, so only refund holds are enforceable until one is introduced (S70-R47).
- Per S70-PO-10 Q4, the concrete "invoice data" objects are `public.payment_events` (`20261101120000_registration_approval_model.sql:94-125`), `public.refund_operations`, `public.refund_allocation_events`, `public.subscription_obligation_cancellations` (all `20261103123000_f13_refund_ledger.sql:2-57`); no new table.
- Per S70-PO-10 Q2, immutable legally required evidence (ledger/refund/audit rows) is pseudonymized/anonymized so it no longer identifies the client and other in-scope rows are physically deleted. Per S70-PO-10 Q3, the audit mutation runs only through one narrow audited SECURITY DEFINER purge function, the sole actor exempt from the `public.audit_events` immutability triggers (`20261027150000_audit_log.sql:29-41`); grants reviewed, removal recorded.

### Entry point and modes

- Extend the existing postgres-only entry point rather than adding a second scheduler or a new automatic invocation. The entry point supports a dry-run mode that computes candidates, holds and reasons without mutation, and an apply mode that mutates only eligible rows.
- A stable run identifier makes replay idempotent: a second apply with the same identifier performs no additional deletion and appends no duplicate evidence. The identifier is not an authorization factor.
- Evidence is counts-and-decisions only: candidate counts, eligible/held/inside-window counts, hold reasons, the cited decision sources, and "PO states Egyptian legal advice was obtained". No PII, tokens, secrets, raw IP, `ip_key`, note or body text, and no lawyer name/date/file/citation.
- Authorization is enforced at the application boundary and at the database boundary under D-10 (Platform Owner only). Per architect mapping S70-R61, the database boundary is one authenticated-callable SECURITY DEFINER wrapper with `search_path=''`: it rejects null `auth.uid()` or false `app_private.is_platform_owner()` with SQLSTATE `42501`, then calls the existing postgres-only internal purge. EXECUTE is granted to `authenticated` only and revoked from PUBLIC, `anon`, and `service_role`; the internal purge stays postgres-only. This explicit narrow PO check does not widen tenant access. Deny-by-default RLS stays in force.
- The DP-06 operational order is preserved before any Auth-user purge. This feature does not shorten or reorder it.

## Risks and mitigations

- **Deleting inside the window** — pure clock predicates with 29/30-day boundary tests and an explicit "no override flag" assertion; every deletion path goes through eligibility.
- **Indefinite or premature hold** — Q1 status enumeration is decided by S70-PO-10 and scoped by architect mapping S70-R47 to the refund lockout outbox; hold tests assert both no-carry-over and restart from resolution using the concrete OPEN/RESOLVED values and exclude subscription-status and generic-job states.
- **Ledger/audit contradiction** — Q2 and Q3 resolved by S70-PO-10 (pseudonymize evidence, one audited SECURITY DEFINER path); Constitution VII and F13 preservation language cited; no mechanism invented.
- **Unauthorized purge** — D-10 Platform-Owner-only at both walls, deny-by-default RLS, mutation evidence that kills each guard, no service-role fallback.
- **Accidental scheduler activation** — no activation call anywhere in the feature; scheduler-disabled test and OP-01 citation; exact-head CI gates.
- **False backup closure** — FR-006 and SC-007; no artifact claims BR-01/BR-02/BR-04/FN-03 satisfied.
- **Invented scope/copy** — Q4 resolved by S70-PO-10 to existing payment/receipt/refund objects; no user-visible strings; legal basis recorded only as the S70-PO-4 quoted string.
