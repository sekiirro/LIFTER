**AD-F11-1: Decided (PO, 2026-10-28): option (i); C1–C4 binding.** PO selected direct Auth writes inside one database transaction. C1–C4 are binding conditions; options (ii) and 3b remain rejected alternatives with evidence retained in research.md. No implementation or hosted proof is claimed. ND-F11-1..10 are Decided (PO, 2026-10-28); verbatim decisions and explicit open sub-decisions are in [spec.md](../spec.md#po-decision-register-and-open-sub-decisions).

## Public transport and admission

GET `/register/[token]` keeps F10's dynamic/no-store open behavior and minimal workspace-name/validity projection. Add a POST Server Action on the **same exact single-segment route**, with framework origin/CSRF protection, server-side payload validation and no state-changing GET signup. Do not put passwords/tokens/PII in query strings. Browser sends token only as the necessary route/action credential, a random per-submission request secret, and required name/email/phone/password (no Telegram) permitted by `signup_field_contract()`. Bound action values are still secrets; never serialize the token in visible success/error props or metadata. Reject caller workspace, offer/version, auth-user ID, role, grant, timestamp and terms overrides.

`authorizePublicClientSignup()` is the app wall: validates token/request-secret shape, same-origin submission, allowed fields/visitor policy and durable per-link and per-IP admission through the bounded admission RPC before expensive hashing. It does not call staff `requireActor()` (which redirects) or invent a client capability. The database wall independently hashes the token, resolves/locks its row, derives workspace/snapshot, checks time, admission/request binding, canonical ownership and all constraints. Direct callers of the public RPC must pass those DB checks too. No trust in caller scope, app precheck success or service-role bypass.

Protected staff surfaces still require existing `authorize()` and `has_workspace_access()`. Clients/Auth-only users have no staff role/membership; this unit grants none. An architect must review the bounded definer path as the public analogue of F10, with no broad anon RLS policy.

## Proposed bounded RPC shapes

- `client_signup_admit(token text, request_secret text, ip_key bytea, link_key bytea, issued_at timestamptz, nonce uuid, attestation bytea) → {status:'admitted',admission_ticket:uuid}|{status:'invalid'|'unavailable'}`: durable per-link and per-IP attempt transaction; unknown/invalid tokens do not disclose scope. The DB verifies attestation/freshness/nonce and token-to-link_key binding, then atomically counts under advisory link-key then ip-key locks, checks ND-F11-5, and records minimal evidence. The admission ticket is a one-use credential bound to the link and hashed request secret; it is not an Auth ID or workspace disclosure. No Auth reservation is created by this public call.
- `client_signup(token text, request_secret text, admission_ticket uuid, fields jsonb) → SignupResult`: option (i) bounded transactional signup; minimum 8-character password including number and symbol (maximum/symbol definition ND-F11-1a decided: maximum 72 UTF-8 bytes; symbol is any printable non-letter/non-digit/non-whitespace character), Supabase Auth email normalization, E.164 phone and mandatory shape/limit checks apply to direct calls as well as app calls. A public caller cannot forge successful admission by setting a JSON flag. Admission tickets (separate from attempt logs) must bind link + request-secret hash and be consumed exactly once by the write operation. Redeem before entering an inner write subtransaction; catch business failures and commit redemption while rolling back every inner signup effect; infrastructure failures roll back redemption too. Force deferred checks inside the inner unit. A new failed-write retry requires fresh durably counted admission. An exact concurrent request waits and returns generic invalid if the first committed.

RPC shape is the approved option (i) technical contract under binding conditions C1–C4; it is not an implementation. Infrastructure exceptions/provider/constraint details are adapted server-side and never passed through.

## Public SignupResult and privacy equality

Business outcomes render HTTP 200, with one constant-shape body containing only a status and translated generic text. Infrastructure failures MUST use a generic unavailable payload with HTTP 200 from the same-route Server Action (PO decision 2026-10-28: Server Action transport, unavailable returned as payload with HTTP 200), still with privacy headers and no provider details. Field-validation feedback is permitted only for the submitter's allowed input, never account lookup results.

| Internal class                                                                                                                                                                                                            | Public result                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unknown/malformed/expired/consumed link, wrong replay secret, forged binding                                                                                                                                              | `{status:'invalid'}` plus the same F10 generic invalid message; no reason code, validity date or workspace ID                                                                       |
| Email-only/phone-only/both collision, same/foreign workspace, active/pending/staff collisions and archived collision (generic D-08/admin review; state/review design deferred on ND-F5-1; identical D-08 always required) | `{status:'duplicate'}` plus **“This email is already registered. Contact support.”**, equivalent Arabic translation; no field discriminator, account ID, workspace or provider code |
| Confirmed initial committed signup                                                                                                                                                                                        | `{status:'complete'}` plus generic completion; no Auth/client ID, token, profile or financial data                                                                                  |
| DB unreachable / C1 guard failure / admission-attestation infra failure / unexpected exception after rollback                                                                                                             | `{status:'unavailable'}` plus generic translated retry text; no SQL/provider exception                                                                                              |
| Signed-in visitor at submission, including a session appearing after GET                                                                                                                                                  | `{status:'sign_out_required'}` plus generic bilingual manual sign-out text; no link or identity disclosure, nothing admitted or consumed                                            |
| Allowed form validation error                                                                                                                                                                                             | `{status:'invalid_input'}` with safe field feedback from approved field/password seam, no submitted values echoed                                                                   |

Invalid link checks precede uniqueness, including for requests with colliding inputs. Duplicate classes must have identical status/body/headers and UI wording; avoid identity-specific timing branches and run the repeatable SC-011 local timing-differential regression procedure in `spec.md`; it is not a latency SLA. Enforce BOTH 5/link/15 minutes AND 30/IP/hour; either exhausted limit returns generic non-disclosing feedback, never consumption. ND-F11-5a decides every submission reaching admission counts (success or failure); fixed 15-minute link/1-hour IP windows aligned with expiry. Counts and attempt/failure evidence commit in durable admission independently of signup rollback. Attempt logs contain no IP/ip_key; HMAC counters expire at window end (automatic expiry; no usable counter beyond the window), subject to C1 privacy decision Decided (PO, 2026-10-28). Trusted IP and the expanded attestation RPC follow AD-F11-2 below. Do not import F10 issuance limits.

## Lock order and atomicity

**Lock order (verbatim contract):** `link row FOR UPDATE → validity with authoritative clock_timestamp() after lock → request/ticket redemption (pre-admitted in a separate transaction) → canonical uniqueness locks in sorted key order and DB constraints → Auth identity/claim writes → client insert → guarded consume with fresh authoritative time → receipt and audit → deferred checks → COMMIT`.

**Transaction boundary (verbatim contract):** `Client insert + guarded registration-link consumption + successful-change audit (including deferred checks) + Auth user/identity + canonical claims + committed receipt commit in one database transaction; any failure rolls all signup effects back. Durable admission is separate; one-use ticket redemption precedes the inner signup subtransaction and business failures commit redemption without signup effects; infrastructure failures roll back redemption and return unavailable.`

Admission uses advisory link-key then ip-key locks separately from signup row locks and commits minimal evidence before hashing; it is not a validity reservation. C1 guards both RPCs before any write, including ticket redemption. Consumed-link retries always return generic invalid; internal committed receipts prevent duplicate identities but never recover public success/account/session. No provider HTTP or saga exists in signup. C3 requires server anon/publishable-key signup RPC calls only, bcrypt `extensions.crypt(..., extensions.gen_salt('bf', <GoTrue cost>))`, and no plaintext in exceptions/RAISE/audit/logs/receipts/returns. C2 real sign-in and exhaustive GoTrue-set-column parity must pass locally; C4 blocks hosted deployment pending re-verification and PO approval.

Guarded consumption: UPDATE the exact derived workspace/link with `consumed_at IS NULL` and `fresh_authoritative_time < expires_at`, set consumed_at to that same fresh instant and require one `RETURNING id` row. Zero rows raises/rolls back. Sample again after expensive hash/constraints; do not use transaction-start `now()` after a lock wait. Signup is strict, no grace, equality invalid. F10 open/grace behavior and contract remain unchanged: a post-expiry grace open may render valid but signup returns generic invalid. ND-F11-4a decides to preserve this mismatch and revisit with ND-F10-4. Future guard extension must agree with the consume timestamp and preserve all F10 protections.

## Headers, middleware and token handling

Every registration GET/POST response, including invalid, duplicate, field error, rate exhaustion, success, missing configuration, provider failure, framework error and cookie-refresh path, must carry `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Apply headers after response recreation, with route-level/framework error coverage; do not assume middleware headers survive all responses. Keep the current exact route regex public for POST as well as GET; nested/lookalike paths do not become public. Denied register-subtree variants must also receive privacy headers without copying their path into redirects.

Never use token-bearing `redirect`, login `next`, Return-To, Location, exception URL, analytics route name, console output, trace span, breadcrumb, audit detail or metadata. ND-F11-6b requires a generic completion page without a signup session; client signs in after approval. Any navigation must be token-free. No raw token/hash/password/email/phone/request secret in logs, request dumps, server caches or telemetry. Do not log full RPC arguments/provider bodies or public URLs. Disable/redact platform access capture of `/register/*` and request bodies, including error/WAF layers, before real use. Local tests do not certify host configuration. Scrub synthetic test traces too; no screenshot of credential-bearing addresses as evidence. No third-party analytics/assets may receive the token via referrer.

Signed-in visitor behavior is owned only by `signup_authenticated_visitor_policy()`; prompt manual sign-out before registering; no automatic sign-out, linking, merge, staff conversion, extra membership or token redirect. Create pending-approval and deny client capabilities through both walls until admin approval. Workspace PO/WO approve in F12 (ND-F11-6a); generic completion creates no session, client signs in after approval (ND-F11-6b); no interim client view or approval UI. Completion policy is owned by `signup_completion_policy()`; initial generic completion must never imply approval/activation/plan access; no replay establishes a session.

## Audit and retention contract

Structured events cover attempts, success, failures, link consumption and cleanup (purge). Success/consumption events commit with signup; attempts/failures have separate operational records AND append-only audit_events in admission/evidence transactions. No secrets, passwords, tokens/hashes or provider diagnostics; event names and payload allow-list are technical design. Signup-attempt logs without IP/ip_key retained 30 days; window-lived HMAC counters separate, purge mechanism local technical design; all other audit retention undecided (NEEDS SOURCE CONFIRMATION), ND-F5-1/B4 unchanged. Archived review mechanism/reviewer remains ND-F11-9a; archived-state/review design deferred until ND-F5-1 closure; identical D-08 always required defines absent state (ND-F11-9b). D-16 unchanged.

## AD-F11-2 — architect decision: trusted IP and admission

PO decision 2026-10-28: per-IP admission means per full IPv4 address (including mapped IPv4) and per IPv6 /64 network. Attestations accept issued_at up to 5 seconds ahead of DB clock_timestamp(), with an inclusive maximum age of 60 seconds. Nonces expire at issued_at + 60 seconds (up to 65 seconds after first acceptance); cleanup uses strict expiry so replay remains rejected at both inclusive edges. Timing constants have one private owner.

Technical architect decision, not PO policy approval. The C1 privacy proposal is **Decided (PO, 2026-10-28)**; Constitution unchanged. The C1 privacy decision is separate from AD-F11-1 option (i) and its binding C1–C4 conditions.

- U5 implements and tests a pure trusted-IP extractor: trust only `CF-Connecting-IP`, ignore `X-Forwarded-For` and all other IP headers, fail closed as unavailable when production IP is absent, and gate the explicit override to non-production. U6 wires the helper into the server action and owns the `build:edge` production-output proof.
- U5 implements and tests pure HMAC `ip_key`/`link_key` and attestation builders at their module boundary. Secrets remain server-only; raw IP stays within the server-action boundary. U6 wires these builders into the action and proves the test override is absent from `build:edge` output.
- The anon-callable admission RPC cannot trust a supplied ip_key. Send the attestation using the normative byte-level encoding and HMAC rules in `plan.md`, with constant-time MAC comparison. DB verifies SIGNUP_ATTEST_KEY held in Supabase Vault (local), readable only by the SECURITY DEFINER functions’ owner, freshness ≤ 60 s, future-issued timestamps at most 5 s ahead of DB clock_timestamp() (PO decision 2026-10-28) and single-use nonce. Missing/invalid attestation or replay → generic `invalid`, no counter credit or ticket (no oracle). Attestation infrastructure failure → `unavailable`. DB independently verifies token-to-link_key binding and enforces per-link limits regardless of caller ip_key; forged attribution cannot bypass it.
- Counter storage: `app_private.signup_rate_counters(scope ∈ {link, ip}, key bytea, window_start, count, expires_at)`, no workspace/link FK, forced RLS, no grants. Advisory xact locks in fixed order: link key, then ip key, inside the separate admission transaction that commits before signup. Enforce both 5/link/15 min and 30/IP/hour across links/workspaces. ND-F11-5a decides every submission reaching admission counts (success or failure); fixed 15-minute link/1-hour IP windows aligned with expiry, behind `client_signup_limits()`.
- Counter rows expire at window end (automatic expiry; no usable counter beyond the window); purge opportunistically on each admission and by the local purge job. Their retention is not 30 days. Keep private nonce/ticket security state separate from logs, forced RLS/no grants; nonce replay protection spans the freshness bound and ticket one-use integrity survives counter/log purge.
- `app_private.client_signup_attempts` stores outcome class, timestamp, and link_id/workspace_id ONLY when the link resolved (both NULL otherwise; same-workspace composite relation when present). No IP, ip_key, token, token hash, email/phone/name, or credentials. Retain 30 days (ND-F11-7). Operational failure records are written here; ND-F11-10 additionally requires separate append-only audit_events in admission/evidence transactions independently of signup rollback. For a failure discovered after the initial admission committed, use a separate admission/evidence transaction after rollback; do not claim to amend an already committed transaction. Success/consumption evidence remains atomic with signup.

## Infrastructure-failure contract (I1)

Only infrastructure failures produce `{status:'unavailable'}`: DB unreachable, C1 Auth-compat guard failure, admission-attestation infrastructure failure (including absent trusted IP in production), or unexpected exception after rollback. `unavailable` payload with HTTP 200 from the same-route Server Action (PO decision 2026-10-28: Server Action transport, unavailable returned as payload with HTTP 200), `Cache-Control: no-store`, `Referrer-Policy: no-referrer`; generic English “Please try again later.” / Arabic “يرجى المحاولة مرة أخرى لاحقًا.” only, with no cause. Nothing is consumed on unavailable, including the link or admission ticket; roll back redemption on this path. Previously committed admission accounting remains durable. Auth-compat guard failure is specifically fail-closed before any DB write: no attempt/audit row or consumption; evidence is a structured server-side event with only `code` and `timestamp`, fixed code `AUTH_COMPAT_GUARD_FAILED`, and no PII, IP, token or hash.

Never derive unavailable from link or identity state: unknown/malformed/expired/consumed links, invalid attestation and exhausted limits stay `invalid`; valid-link identity collisions stay D-08 `duplicate`. Unresolved policy blocks implementation/configuration rather than creating a link/identity unavailable branch. F10 GET `/register/[token]` open contract, including `{status:'invalid'}`, is unchanged. UI retains the form for a later retry and never claims completion. Enumerate link/identity branches in tests and prove none selects unavailable.

## U8 round 2: binding decisions and enforcement

The PO sub-decisions ND-F11-1a/4a/5a/6a/6b/9a/9b and C1 privacy are **Decided (PO, 2026-10-28)**; see the [decision register](../spec.md#po-decision-register-and-open-sub-decisions). ND-F11-9a/9b decide deferral of archived-state/review design until ND-F5-1, not deferral of privacy: before and after that definition, archived collisions return the identical generic D-08 payload, HTTP status and headers, with no measurable timing branch beyond the existing duplicate path. No account-existence disclosure or automatic admin-review queue is introduced.

Pending-approval clients have **zero client access** through app `authorize()`, DB RLS (`has_workspace_access()` and client policies), direct PostgREST/RPC or Storage. Signup creates no session, but a pending client who later signs in and obtains a JWT is still denied every client-scoped read/write. Absence of a signup session is not an authorization control. Workspace PO/WO approval ships in F12; F11 only creates pending-approval clients and shows generic completion, then the client signs in after approval. Test app denials with an accepting backend mock, RLS independently of grants, direct PostgREST/RPC calls using a real pending client's JWT, and Storage reads/writes; no policy may admit pending clients.

**C1-audit split:** `app_private.client_signup_attempts` is the operational attempt log, purged after 30 days (ND-F11-7). Separately append `audit_events` rows for attempt/failure/success/consumption/cleanup (ND-F11-10). Both evidence payloads allow only outcome class, timestamp and link_id/workspace_id when resolved (both absent/NULL otherwise); no PII, raw IP, ip_key, token, hash, credential or provider payload. Admission writes attempt audit in its transaction; signup success and consumption audit commit in the atomic signup transaction. A caught business failure writes failure audit outside the rolled-back inner signup unit; a failure discovered after a full rollback uses a new evidence transaction. Unknown/unresolved-link attempt and failure audit events use `target_table='client_signup_attempts'` and `target_id` equal to the attempt row UUID. Purge deletes only eligible operational records and appends cleanup audit in the same purge transaction; cleanup uses `target_table='client_signup_attempts'` and a per-run generated purge-run UUID as `target_id`, with counts-only payload. `audit_events` has no FK from attempt targets to attempt rows and no cascade; purge NEVER deletes/updates `audit_events`. After purge, audit rows referencing purged attempts must still exist unchanged. Audit retention remains **NEEDS SOURCE CONFIRMATION - pending ND-F5-1**. Test purge removes old operational rows, preserves younger rows, appends cleanup audit and leaves every pre-existing audit row intact. Counters are separate window-lived mutable enforcement state, not attempt/audit logs.

**U1 key provisioning and verification:** provision both `SIGNUP_RATE_KEY` and `SIGNUP_ATTEST_KEY` in local Supabase Vault, readable only by the SECURITY DEFINER functions' owner; matching copies stay in server-only environment, never browser or logs. The DB recomputes `HMAC-SHA256(SIGNUP_RATE_KEY, token_hash)` and constant-time compares it with supplied link_key, independently of attestation verification with `SIGNUP_ATTEST_KEY`. Both keys must therefore be available to the DB verifier. No raw IP or ip_key may enter any log, audit, attempt record, exception/error or telemetry. Only window-lived HMAC-keyed rate-limit counters persist derived attribution.

Coordinated rotation: SIGNUP_RATE_KEY rotation resets IP/link counters because counter keys derive from the active key. Admission uses only the current single `ip_key`, with no old-key lookup. Accept up to one extra window of attempts per key (at most 1 hour for the IP window). Rotation is rare and manual: rotate the server environment and Vault value together; old-key counters expire naturally. Never log key values or identifiers derived from IPs. Counter expiry remains aligned to fixed windows (15 minutes/link, 1 hour/IP), and every submission reaching admission counts; invalid/replayed attestations receive no counter credit or ticket.

**I1 dependency:** U2 (T007/T008) owns the minimal `signup_admission_tickets` schema and internal guarded redemption primitive, including request-secret hash/link binding, one-use NULL-to-timestamp transition and business-failure/infrastructure rollback semantics. Only explicitly pre-admitted synthetic tickets are available to U3 tests. U5 (T019/T020) owns attested issuance, nonces, counters, operational purge and admission integration. The redemption primitive has no public issuer/grant and requires no U5 object at the U2/U3 exits. AD-F11-1 option (i) is PO-approved; C1–C4 are binding conditions.
