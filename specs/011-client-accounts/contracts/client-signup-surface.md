# Contract: F11 public signup and F4 linkage

Design only; AD-F11-1 and ND-F11-1..10 remain open. [Plan](../plan.md) owns policy seams; [model](../data-model.md) owns schema/grants. Never expose a general anonymous client CRUD API.

## Public transport and admission

GET `/register/[token]` keeps F10's dynamic/no-store open behavior and minimal workspace-name/validity projection. Add a POST Server Action on the **same exact single-segment route**, with framework origin/CSRF protection, server-side payload validation and no state-changing GET signup. Do not put passwords/tokens/PII in query strings. Browser sends token only as the necessary route/action credential, a random per-submission request secret, and fields permitted by `signup_field_contract()`. Bound action values are still secrets; never serialize the token in visible success/error props or metadata. Reject caller workspace, offer/version, auth-user ID, role, grant, timestamp and terms overrides.

`authorizePublicClientSignup()` is the app wall: validates token/request-secret shape, same-origin submission, allowed fields/visitor policy and durable per-token admission through the bounded admission RPC before expensive hashing/provider calls. It does not call staff `requireActor()` (which redirects) or invent a client capability. The database wall independently hashes the token, resolves/locks its row, derives workspace/snapshot, checks time, admission/request binding, canonical ownership and all constraints. Direct callers of the public RPC must pass those DB checks too. No trust in caller scope, app precheck success or service-role bypass.

Protected staff surfaces still require existing `authorize()` and `has_workspace_access()`. Clients/Auth-only users have no staff role/membership; this unit grants none. An architect must review the bounded definer path as the public analogue of F10, with no broad anon RLS policy.

## Proposed bounded RPC shapes

- `client_signup_admit(token text, request_secret text) → {status:'admitted',admission_ticket:uuid}|{status:'invalid'|'unavailable'}`: durable per-token attempt transaction; unknown/invalid tokens do not disclose scope. The DB atomically counts under link lock, checks ND-F11-5, and records minimal evidence. The admission ticket is a one-use credential bound to the link and hashed request secret; it is not an Auth ID or workspace disclosure. No Auth reservation is created by this public call.
- `client_signup(token text, request_secret text, admission_ticket uuid, fields jsonb) → SignupResult`: option (i) bounded transactional signup; mandatory shape/password/normalization/limit checks apply to direct calls as well as app calls. A public caller cannot forge successful admission by setting a JSON flag. Admission tickets/attempt rows must bind link + request-secret hash and be consumed exactly once by the write operation. Redeem before entering an inner write subtransaction; catch sanitized failures and commit redemption while rolling back every inner signup effect. Force deferred checks inside the inner unit. A new failed-write retry requires fresh durably counted admission. An exact concurrent request waits and returns generic invalid if the first committed.
- Option (ii): app POST calls service-role-only client_signup_reserve(token,request_secret,admission_ticket), which independently locks/revalidates/redeems admission, reserves one link-bound Auth UUID and returns operation_id/auth_user_id/fence solely server-side, then calls provider orchestration; `client_signup_finalize(operation_id uuid,fence bigint)` is service-role EXECUTE only and takes no arbitrary scope/Auth ID/PII override. It independently verifies the reserved identity's canonical data, permanent gate, link and fence. No browser-facing admin API or service key. Complete saga/cleanup contract: [research R4](../research.md#r4--ad-f11-1-option-ii-auth-admin-api-plus-compensation).

RPC shape is a proposed technical contract pending AD review, not an implementation. Infrastructure exceptions/provider/constraint details are adapted server-side and never passed through.

## Public SignupResult and privacy equality

Business outcomes render HTTP 200, with one constant-shape body containing only a status and translated generic text. Infrastructure failures may use a generic 503, still with privacy headers and no provider details. Field-validation feedback is permitted only for the submitter's allowed input, never account lookup results.

| Internal class                                                                                                                | Public result                                                                                                                                                                       |
| ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unknown/malformed/expired/consumed link, wrong replay secret, forged binding                                                  | `{status:'invalid'}` plus the same F10 generic invalid message; no reason code, validity date or workspace ID                                                                       |
| Email-only/phone-only/both collision, same/foreign workspace, staff/account-state collision when participating under ND-F11-9 | `{status:'duplicate'}` plus **“This email is already registered. Contact support.”**, equivalent Arabic translation; no field discriminator, account ID, workspace or provider code |
| Confirmed initial committed signup                                                                                            | `{status:'complete'}` plus generic completion; no Auth/client ID, token, profile or financial data                                                                                  |
| Unavailable/unsupported schema/unresolved policy/provider infrastructure fault                                                | `{status:'unavailable'}` plus generic translated retry text; no SQL/provider exception                                                                                              |
| Allowed form validation error                                                                                                 | `{status:'invalid_input'}` with safe field feedback from approved field/password seam, no submitted values echoed                                                                   |

Invalid link checks precede uniqueness, including for requests with colliding inputs. Duplicate classes must have identical status/body/headers and UI wording; avoid identity-specific timing branches and benchmark for obvious timing leakage without inventing a new latency SLA. ND-F11-5 alone controls exhaustion wording/counting; provisional unresolved mode fails closed to generic unavailable, not successful consumption. Shared IP alone never blocks signup. Do not import F10 issuance limits.

## Lock order and atomicity

**Lock order (verbatim contract):** `link row FOR UPDATE → validity with authoritative clock_timestamp() after lock → request/attempt row and per-token admission → canonical uniqueness locks in sorted key order and DB constraints → Auth identity/claim writes → client insert → guarded consume with fresh authoritative time → receipt and audit → deferred checks → COMMIT`.

**Transaction boundary (verbatim contract):** `Client insert + guarded registration-link consumption + successful-change audit (including deferred checks) commit in one database transaction; any failure rolls all three back. Option (i) includes Auth user/identity and canonical claims in that transaction. Option (ii) creates only a permanently gated Auth user beforehand; its finalize transaction includes client, claims, guarded consume, audit, committed receipt and gate release; compensation/reconciliation runs outside it and must never affect a committed client.`

Admission's separate durable transaction uses the link-first prefix and commits minimal attempt evidence before expensive work. There is no lock spanning HTTP. Finalization repeats every authoritative check after reacquiring the lock; admission is not a validity reservation. For option (ii), Auth identity creation occurs before finalize; the quoted Auth write step in finalize means verify gated reserved identity and update claims/gate, not create another identity. All cleanup transactions acquire link then operation locks; registry keys follow sorted order.

Every public consumed-link request returns generic invalid, including a matching-secret retry after lost success, as required by the spec. Internal receipt lookup prevents duplicate creation and unsafe compensation but never recovers a public success, credentials or account. Lost response never causes blind createUser/new UUID retry; no dedup retention window may make a consumed link reusable. A duplicate or invalid-input failure may retry with corrected fields under the same submission identity only if no conflicting committed receipt exists and fresh admission passes. Inputs cannot rebind a reserved Auth ID to a different person after an ambiguous API call; reconcile first.

Guarded consumption: UPDATE the exact derived workspace/link with `consumed_at IS NULL` and `registration_link_is_valid(expires_at,opened_at,consumed_at,fresh_authoritative_time)`, set consumed_at to that same fresh instant and require one `RETURNING id` row. Zero rows raises/rolls back. Sample again after expensive hash/constraints; do not use transaction-start `now()` after a lock wait. Preserve strict expiry OR strict pre-expiry-first-open+30-minute grace, consumed dominant, equality invalid, no sliding/reopening extension. ND-F11-4 is confirmation only, not permission for alternate grace. Future guard extension must agree with the consume timestamp and preserve all F10 protections.

## Headers, middleware and token handling

Every registration GET/POST response, including invalid, duplicate, field error, rate exhaustion, success, missing configuration, provider failure, framework error and cookie-refresh path, must carry `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Apply headers after response recreation, with route-level/framework error coverage; do not assume middleware headers survive all responses. Keep the current exact route regex public for POST as well as GET; nested/lookalike paths do not become public. Denied register-subtree variants must also receive privacy headers without copying their path into redirects.

Never use token-bearing `redirect`, login `next`, Return-To, Location, exception URL, analytics route name, console output, trace span, breadcrumb, audit detail or metadata. A completion policy may eventually choose only an allowlisted token-free destination; provisional synthetic completion stays in place without a session. No raw token/hash/password/email/phone/request secret in logs, request dumps, server caches or telemetry. Do not log full RPC arguments/provider bodies or public URLs. Disable/redact platform access capture of `/register/*` and request bodies, including error/WAF layers, before real use. Local tests do not certify host configuration. Scrub synthetic test traces too; no screenshot of credential-bearing addresses as evidence. No third-party analytics/assets may receive the token via referrer.

Signed-in visitor behavior is owned only by `signup_authenticated_visitor_policy()`; no automatic sign-out, merge, staff conversion, extra membership or token redirect. Completion/session/interim state is owned only by `signup_completion_policy()`; initial generic completion must never imply approval/activation/plan access; no replay establishes a session.

## F4 recovery dependency

Unique Auth FK ensures at most one workspace. Pending Auth reservations/orphans return NULL; no client metadata or email-search endpoint is added.

Preserve `recovery_link_guard()`: authenticated caller, target exists through lookup, `has_workspace_access(ws,'generate_recovery_link')`, self/staff rejection and existing limits. Preserve `recovery_link_authorize()` preflight before provider work, app `authorize()`, then `recovery_link_record()` target-lock → actor-lock and repeated guard/audit. `lib/auth/recovery-link.ts` already uses server-only admin `getUserById`/`generateLink`; `lib/supabase/admin.ts` keeps service key server-only with no persisted session, refresh or URL detection. No F4 policy, rate, expiry, delivery, audit or ND-F4-5 decision is changed.
