# Feature Specification: F11 — Client accounts + signup

**Feature Branch**: `011-client-accounts`

**Created**: 2026-10-28

**Status**: Draft; ND-F11-1..10 Decided (PO, 2026-10-28); PO sub-decisions decided; archived-state/review and audit retention deferred on ND-F5-1; AD-F11-1 Decided (PO, 2026-10-28): option (i); C1–C4 binding remains. Specification/clarification artifacts only, not implementation approval.

**Input**: User description, corrected by architect review R1: F11 — Client accounts + signup. A prospective client who opens a valid F10 registration link (`/register/[token]`) can create a LIFTER client account. Client creation, guarded registration-link consumption (sets `consumed_at` once) and successful-change audit commit in one database transaction. Auth identity consistency is a binding outcome under FR-003, using the PO-approved AD-F11-1 option (i) direct transactional Auth writes subject to C1–C4. Invalid, expired, consumed or otherwise invalid links return only the generic invalid response. Email and phone are globally unique across accounts; duplicates return D-08's generic duplicate message without field/account/workspace disclosure. Bind the client to the issued workspace/offer/version snapshot. Apply app `authorize()` and DB RLS (`has_workspace_access()`), with audit via `audit_row_change()` extended from its latest body in `supabase/migrations/20261030120000_registration_links.sql`. Supply the client dependency for F4 recovery (ND-F4-5), without resolving that decision. Exclude F12 subscriptions/approval/ledger/commission/payments, F13 freeze/renewal/refunds and SMTP/email verification (D-19). Public content beyond the signup form remains ND-F10-4.

## Clarifications

PO decision 2026-10-28: per-IP admission means per full IPv4 address (including mapped IPv4) and per IPv6 /64 network. Attestations accept issued_at up to 5 seconds ahead of DB clock_timestamp(), with an inclusive maximum age of 60 seconds. Nonces expire at issued_at + 60 seconds (up to 65 seconds after first acceptance); cleanup uses strict expiry so replay remains rejected at both inclusive edges. Timing constants have one private owner.

## User Scenarios & Testing _(mandatory)_

Actors: prospective client holding a link, anonymous visitor, existing signed-in client/staff identity, and staff already authorized for client recovery. Link possession authorizes only bounded signup, never general workspace access or staff membership.

### User Story 1 - Create one account from the issued link (Priority: P1)

As a prospective client, I can submit the signup form from a valid link and receive one account bound to the issued workspace and terms.

**Why this priority**: Completes signup in Journey A and provides F4's missing client identity without implementing F12 approval or finance.

**Independent Test**: Use a synthetic valid link and unique identity; verify the account, snapshot association, consumed link and audit evidence, then inject failure into each persistence boundary.

**Acceptance Scenarios**:

1. **Given** a valid unconsumed link and valid unique signup data, **When** signup succeeds, **Then** one pending-approval client with no client access, one guarded set-once consumption and successful-change audit evidence commit in one database transaction, with exactly one associated Auth identity and the issued workspace/offer/version snapshot; success is reported only after commit (FR-001/003/004/005/010).
2. **Given** validation, Auth creation, client creation, consumption, deferred commit or audit failure, **When** the attempt completes, **Then** client creation, consumption and successful-change audit roll back together; a previously unconsumed link remains unconsumed, and no usable/sign-in-capable orphan Auth identity remains (FR-003/010/011; PO-approved option (i) subject to binding C1–C4).
3. **Given** an issued link whose offer later changes version or availability, **When** otherwise-valid signup succeeds, **Then** original terms remain bound and are not replaced or rejected merely because current terms changed (FR-005).
4. **Given** simultaneous submissions on one valid link, **When** both finish, **Then** at most one succeeds and the loser receives generic invalid after consumption, with no orphan account (FR-003/004).

### User Story 2 - Fail safely without disclosing identities (Priority: P1)

As a prospective client, I receive consistent responses for unusable links and identity collisions; failed submissions do not spend a valid signup opportunity.

**Why this priority**: D-08 and F10 protect identity and workspace privacy, including under races/retries.

**Independent Test**: Exercise invalid-link classes, exact time boundaries, duplicate email only, phone only, both fields and simultaneous cross-workspace collisions with synthetic data.

**Acceptance Scenarios**:

1. **Given** an unknown, malformed, consumed or otherwise invalid link, **When** opening/submitting it, **Then** generic invalid reveals no cause, workspace, account or duplicate result and creates nothing (FR-002/006). Signup at/after `expires_at` is generic invalid even when unchanged F10 grace-open renders valid.
2. **Given** a valid link and existing email, phone or both, **When** submitting, **Then** every collision displays exactly D-08's English message, "This email is already registered. Contact support.", or equivalent Arabic translation, with no field-specific code or account/workspace confirmation; no account is created and the link stays unconsumed (FR-006/007).
3. **Given** different valid links and concurrent submissions sharing a unique identity field, **When** committed, **Then** only one account may own that field; losing attempts roll back and return the same generic duplicate result (FR-003/007).
4. **Given** a form opened before expiry and submit near the effective deadline, **When** guarded consumption checks authoritative time, **Then** stale page validity cannot authorize signup; authoritative consumption time must be strictly before `expires_at`, with equality invalid and no grace (FR-004).

### User Story 3 - Keep clients isolated and recoverable (Priority: P1)

As a client or authorized staff member, I can rely on account isolation and existing recovery controls.

**Why this priority**: Signup must not widen tenant access, staff permissions or recovery-secret exposure.

**Independent Test**: Use clients/staff in A/B, revoked memberships, anonymous and direct data access; verify both walls and exercise F4's client-target lookup with a newly created account.

**Acceptance Scenarios**:

1. **Given** anonymous or foreign-workspace callers, **When** reading/writing tables directly, forging workspace/offer/version or bypassing the app, **Then** independent authorization denies unauthorized access without foreign data/existence disclosure (FR-005/008/009).
2. **Given** a new client in A, **When** requesting B's resources or staff capabilities, **Then** access is denied; no staff membership or dual-role identity was created (FR-008/009).
3. **Given** a new client in A, **When** F4 recovery targets it, **Then** existing capability/scope checks admit only already-authorized own-workspace/platform actors and deny foreign/revoked/anonymous actors, preserving audit and show-once secret handling; ND-F4-5 and other F4 questions remain open (FR-012).

### User Story 4 - Complete a private bilingual form (Priority: P2)

As a prospective client, I can use Arabic or English, keyboard or mobile, without leaking the link.

**Why this priority**: Signup must preserve the approved Design System and F10 public-route privacy.

**Independent Test**: Review AR RTL/EN LTR, themes, mobile layout, labels, focus and pending/error/success feedback; capture headers, redirects, public payloads and logs for valid/invalid cases.

**Acceptance Scenarios**:

1. **Given** either locale/theme, **When** navigating by keyboard or correcting input, **Then** labels, focus, validation and pending feedback are accessible and translated without secret exposure (FR-011/013).
2. **Given** any registration/signup response, including errors, **When** inspected, **Then** no-referrer/no-store apply and logs, analytics, metadata and redirects contain no token/hash, credential or client PII (FR-009/011/014).
3. **Given** committed signup, **When** completion feedback appears, **Then** it neither implies approval/payment/activation nor redirects with the token; the client is pending-approval with no client access through either wall; generic completion creates no signup session; client signs in after approval (ND-F11-6b) (FR-014/015).

### Edge Cases

- Concurrent double signup, replay and lost-success-response retry: at most one account per link; consumed links return generic invalid even when the successful response was lost. No credential/account recovery from a consumed token.
- Expiry versus submit, including lock waits: authoritative time at guarded consumption determines validity, not browser time or a prevalidated page. Consumption at or after `expires_at` is invalid, with no signup grace. F10 open/grace behavior and contract remain unchanged: a link inside F10 post-expiry grace may render valid on open but signup returns generic invalid. ND-F11-4a decides to preserve this mismatch and revisit with ND-F10-4.
- Duplicate email versus phone versus both, same/foreign workspace and concurrent different-link attempts: identical D-08 response, no merge/transfer/verification code or partial signup. An invalid link cannot become an identity-enumeration surface.
- Stale offer version or later disablement: honor the still-valid issued snapshot. Broken/missing/foreign snapshot relations cannot be silently replaced; abort without consumption/disclosure.
- Anonymous table/RPC bypass, forged scope, existing signed-in staff/client and revoked memberships: signup never grants broad anonymous access or converts/merges existing identities. Signed-in visitors receive a prompt to sign out manually before registering; no automatic sign-out, linking or merge, and no token in redirects (ND-F11-8).
- Failure after Auth creation, audit failure, deferred rejection, network interruption/retry: client creation, guarded consumption and successful-change audit commit or roll back as one database unit; never leave a consumed link without a client, a client without its Auth identity or a usable/sign-in-capable orphan Auth identity after failed signup. Report success only after commit; lost-response retries create neither a second identity nor a second consumption. Auth consistency uses the selected AD-F11-1 option (i) subject to binding C1–C4.
- Malformed passwords/email/phone: no consumption; require name/email/phone/password, minimum 8 characters including a number and symbol, Supabase Auth email normalization and E.164 phone. ND-F11-1a sets maximum 72 UTF-8 bytes and defines symbol as any printable non-letter/non-digit/non-whitespace character; no extra country/input transformation rule is inferred.
- Token-bearing access/error logs, telemetry, login-next redirects, referrers/caches: scrub every capture point; no-referrer/no-store on invalid/errors too; no third-party content receives token-bearing referrers.
- Shared IP clients: enforce BOTH 5 attempts/link/15 minutes and 30/IP/hour; either exhausted limit returns a generic, non-disclosing response. Count attempts in a durable admission transaction independent of signup rollback. ND-F11-5a is decided: every submission reaching admission counts; fixed 15-minute link/1-hour IP windows aligned with expiry; AD-F11-2 is an architect decision; issuance limits ND-F10-3 are unchanged. Attempt logs contain no IP/ip_key; HMAC counters expire at window end (automatic expiry; no usable counter beyond the window), subject to C1 privacy decision Decided (PO, 2026-10-28).

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: Provide email/password client signup through a valid F10 `/register/[token]`, using Supabase Auth and one workspace-specific client record. Require name, email, phone and password; minimum 8 Unicode code points (without normalization), including a number and symbol, maximum 72 UTF-8 bytes, and rejection of NUL. Normalize email according to Supabase Auth rules and store phone in canonical E.164 form; phone input uses a country selector defaulting to +20 (Egypt) and a national-number field (PO decision 2026-10-28, ND-F11-2a); server validation composes canonical E.164. Require no Telegram field. Enforce password policy through one shared bilingual application validator for F11 signup and F4 recovery password setting; GoTrue `minimum_password_length = 8` is a backstop. AUTH-PW-01 (PO-approved 2026-10-28) applies to both paths; symbol is any printable non-letter/non-digit/non-whitespace character. Introduce no SMTP or email-verification gate.
- **FR-002**: Opening MUST NOT create/consume an account. Signup at/after expiry (including F10 post-expiry grace), unknown, malformed, consumed and otherwise invalid links MUST use inherited F10 generic invalid shape/wording with no cause, workspace or identity details; preserve normal HTTP 200 invalid-link business rendering. Only infrastructure failures (DB unreachable, C1 Auth-compat guard failure, admission-attestation infrastructure failure, unexpected exception after rollback) return distinct generic `unavailable`: `unavailable` payload with HTTP 200 from the same-route Server Action (PO decision 2026-10-28: Server Action transport, unavailable returned as payload with HTTP 200), no-store/no-referrer, bilingual try-again-later text, no cause, nothing consumed. Never derive unavailable from link/identity state; those remain invalid / D-08 duplicate. F10 open contract is unchanged.
- **FR-003**: Client creation, guarded valid-link consumption and successful-change audit evidence MUST commit **inside one database transaction**. Every validation/uniqueness/write/deferred/audit failure rolls back all three; report success only after confirmed commit. Auth identity consistency is a binding outcome: there MUST never be a consumed link without a client, a client without its Auth identity, or a usable/sign-in-capable orphan Auth identity left after a failed signup; retries after a lost response MUST NOT create a second identity. Use the PO-approved option (i) direct writes to `auth.users` and `auth.identities` inside this same database transaction, subject to binding C1–C4 in AD-F11-1.
- **FR-004**: Consumption MUST coordinate on the link row with guarded UPDATE RETURNING, require `consumed_at IS NULL`, check authoritative time at guarded consumption and permit only one NULL-to-value transition. Signup requires authoritative consumption time strictly before `expires_at`; no grace, equality invalid, consumed always invalid. F10 open/grace behavior and contract are unchanged; a post-expiry grace open may render valid while signup returns generic invalid. ND-F11-4a decides to preserve this mismatch and revisit with ND-F10-4. Concurrency/retry admits at most one account per link.
- **FR-005**: Derive client workspace, offer, version and terms only from the issued immutable snapshot and same-workspace relations. Reject caller overrides. New publication/disablement MUST NOT rewrite/invalidate issued terms. Preserve association for F12 without creating subscription, approval, payment or commission effects.
- **FR-006**: Every email/phone/both collision within/across workspaces MUST have identical D-08 outward payload/message: "This email is already registered. Contact support." (equivalent Arabic translation). No colliding-field code, account confirmation or workspace disclosure, verification-code flow, merge or transfer. Invalid links MUST NOT reveal duplicate diagnostics.
- **FR-007**: Enforce email and phone uniqueness globally across accounts at the database boundary, including concurrent different-link attempts, rather than prechecks alone. Preserve D-16 separate staff/client emails and no dual-role accounts. Duplicate failures leave no new Auth/client record and no consumption. Use Supabase Auth email normalization and E.164 phone; DB-enforce uniqueness against active/pending identities. Archived collision MUST always return the identical generic D-08 payload/status/headers with no measurable timing branch beyond the existing duplicate path. ND-F11-9a/9b decide to defer archived-state and admin-review design until ND-F5-1; disclosure protection is never blocked.
- **FR-008**: Every tenant client row MUST have `workspace_id` and composite same-workspace relations. App `authorize()` and independent DB RLS via `has_workspace_access()` MUST deny unauthorized access on every new protected surface. Pending-approval clients MUST be denied every client-scoped read/write by app authorize(), DB RLS (has_workspace_access()/client policies), direct PostgREST/RPC and Storage, including with a JWT from later sign-in; no signup session is created. No staff role/membership or foreign access is granted. Keep the capability matrix unchanged and require foreign-workspace negative coverage for every new tenant table/surface.
- **FR-009**: Public signup MUST authorize only the bounded link operation, never general anonymous client/identity/link/snapshot reads/writes. Direct database access MUST independently reject forged/unauthorized scope. Browser privilege or broad service-role bypass cannot substitute for the two walls. Technical planning must reconcile public admission with existing staff-oriented helpers without adding staff capabilities or weakening RLS.
- **FR-010**: Provide append-only, tenant-scoped non-PII audit evidence correlating successful client creation and link consumption. Extend `app_private.audit_row_change()` from its **latest complete body** in `supabase/migrations/20261030120000_registration_links.sql` in a future forward-only migration; preserve workspace, staff-role, membership, recovery, package, offer, registration-link and job mappings. Failed transactions leave no successful events and replay cannot duplicate them. No secrets or foreign colliding account details in audit. Record structured attempt, success, failure, link-consumption and cleanup (purge) events without secrets, passwords or tokens/hashes. Attempts/failures survive signup rollback as operational attempt records AND separate append-only audit_events in admission/evidence transactions. Purge deletes only old operational attempts, appends cleanup audit and preserves all existing audit_events. Event names, actor representation and payload allow-list are technical design. Retain signup-attempt logs without IP/ip_key for 30 days; purge mechanism is local technical design. Unknown/unresolved-link attempt and failure audit events target `client_signup_attempts` by attempt-row UUID; purge cleanup targets `client_signup_attempts` by a per-run purge UUID and carries counts only. `audit_events` has no FK to attempt rows and no cascade; purge leaves referencing audit rows present and unchanged. Exception: an Auth-compat guard failure is fail-closed and performs zero DB writes (no attempt row, audit row or consumption); its evidence is a structured server-side error event with fields `code` and `timestamp` only; code is fixed as `AUTH_COMPAT_GUARD_FAILED`, with no PII, IP, token or hash. All other audit retention remains undecided (NEEDS SOURCE CONFIRMATION); ND-F5-1/B4 unchanged.
- **FR-011**: Input/provider/constraint failures MUST have safe translated feedback without credentials, tokens/hashes, raw provider errors, PII or foreign details. Ordinary input failures preserve the link for correction; pending/error/success must not claim completion before commit. Enforce BOTH maximum 5 attempts per link/15 minutes AND 30 per IP/hour; either exhausted limit returns generic, non-disclosing feedback. Attempt accounting commits in a durable admission transaction independent of signup rollback. ND-F11-5a decides every submission reaching admission counts (success or failure), with fixed 15-minute link/1-hour IP windows aligned with expiry; trusted IP/admission follows AD-F11-2 (architect decision); C1 privacy decision is Decided (PO, 2026-10-28).
- **FR-012**: Supply a stable Auth-user/client/workspace association to F4's existing client-target recovery lookup, preserving capability/scope checks, audit and secret handling. Demonstrate newly created own-workspace targets and denied foreign/revoked/anonymous targets. F4 recovery password setting MUST use the shared password validator defined in FR-001. This AUTH-PW-01 behavior change was approved by PO (2026-10-28) and changes password validation only. Config and F4 call-site changes are implementation tasks only; do not edit F4 specs or `supabase/config.toml` in this documentation round. This supplies the dependency without resolving ND-F4-5 or any other F4 item.
- **FR-013**: Use the existing Design System: Arabic-first RTL/English LTR, dark/light, responsive keyboard-accessible form, labels, errors and pending feedback. Render only the fields and apply the input/password policies defined in FR-001; do not add unapproved intake/health/profile collection.
- **FR-014**: Every public registration/signup response MUST retain `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; never shared/server-cache secrets or signup results. Raw tokens/hashes, token-bearing paths, passwords and client PII MUST never enter logs, analytics, exception dumps, metadata or redirect/login-next URLs. Host access capture must omit/redact token paths. Add no public package/financial/commission disclosure; ND-F10-4 stays open beyond the form.
- **FR-015**: Successful signup MUST create only the account and issued-link association/consumption/audit effects, with generic completion feedback. No registration approval, subscription activation, financial events or plan access. Create the client pending-approval; both walls deny client capabilities until admin approval. ND-F11-6a assigns approval to the workspace PO/WO in F12; generic completion creates no signup session; client signs in after approval (ND-F11-6b) (no access either way). Do not invent an approval UI.

- **FR-016**: Signed-in client/staff visitors MUST receive a manual sign-out prompt before registration. No automatic sign-out, account linking, merge, staff conversion or extra membership; no token in redirects or login-next URLs (ND-F11-8).
- **FR-017 (AUTH-SIGNUP-01)**: Disable Supabase public signup with `[auth] enable_signup = false` in `supabase/config.toml`. Anonymous `signUp` MUST be rejected. Admin-created staff, owner and trainer accounts and existing F4 password recovery MUST continue to work. Verify rejected anonymous signup plus the existing staff-creation and F4 recovery integration suites; config/test changes are U1 implementation work only.

### Key Entities _(include if feature involves data)_

- **Auth identity**: stable Supabase Auth user identity and protected email/password credentials; no dual staff/client role and no password copies in client/audit records.
- **Client account**: one workspace-scoped account linked to Auth, globally unique email/phone and the issued snapshot; required name, pending-approval state and no client access until admin approval; workspace PO/WO approval ships in F12; generic completion creates no session; sign in after approval (ND-F11-6a/6b).
- **Registration link**: existing F10 hashed, expiring, single-use credential with immutable snapshot, first-open and set-once consumed markers; raw token is not stored.
- **Issued offer/version snapshot**: historical workspace/offer/version/terms binding retained for F12; current catalog changes do not replace it.
- **Audit event**: append-only safe successful-change evidence with workspace/target correlation; structured attempts/failures live in durable admission evidence; event names/payload allow-list are technical design. Signup-attempt logs have 30-day retention; other retention undecided.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Every successful synthetic signup yields exactly one client with its Auth identity, bound to issued terms; client creation, guarded link consumption and successful-change audit commit in one database transaction, and success is reported only after commit. Injected validation/uniqueness/write/deferred/audit failures roll back all three DB effects, leaving zero consumed links without clients, clients without Auth identities or usable/sign-in-capable orphan Auth identities after failed signup.
- **SC-002**: Concurrent same-link, replay and lost-response cases yield at most one signup per link, no second Auth identity on retry and zero consumed links without clients, clients without Auth identities or usable/sign-in-capable orphan Auth identities after failed signup; concurrent different-link email/phone collisions each leave at most one owner of the unique field.
- **SC-003**: All invalid-link classes yield the same generic invalid outcome; all email-only/phone-only/combined collisions on valid links yield identical D-08 outcomes, zero field/workspace disclosure and zero consumed losing links.
- **SC-004**: Every signup consumption requires authoritative time strictly before `expires_at`, including after waits/hashing; equality and all post-expiry submissions are generic invalid. F10 open/grace is unchanged: a valid-looking grace open cannot authorize signup. ND-F11-4a preserves this mismatch; revisit with ND-F10-4.
- **SC-005**: Anonymous/client/staff by own/foreign/revoked-scope cases yield zero unauthorized reads/writes or staff grants; recovery allows only its existing authorized targets.
- **SC-006**: Every committed signup has safe audit evidence, with zero false success events on failed/replayed attempts. Captured logs/redirects/public payloads have zero credentials, token/hash echoes or unauthorized identity details; every public response has the required privacy/cache headers.
- **SC-007**: AR/EN mobile/desktop signup, invalid, duplicate and correction journeys pass keyboard/accessibility review with understandable completion/error feedback and zero unapproved public/financial actions. Approved field/password/normalization and pending-approval denial are covered; ND-F11-1a and ND-F11-6a/6b are decided acceptance requirements. Shared-validator tests cover F11 signup and F4 recovery password setting with bilingual messages, min 8 characters, a digit, a printable non-letter/non-digit/non-whitespace symbol, and max 72 UTF-8 bytes.

- **SC-008**: Under ND-F11-5a’s decided every-submission-reaching-admission semantics and fixed windows aligned with expiry, independently enforce both maximum 5/link/15 min and 30/IP/hour, including concurrent cross-link/workspace attempts. The next counted attempt at either ceiling is generic invalid with zero signup/consumption; neither limiter is bypassable.
- **SC-009**: Local purge removes every signup-attempt log older than 30 days, zero younger logs and zero unrelated audit/client/identity/receipt records. Separately verify counter expiry at window end (automatic expiry; no usable counter beyond the window). Audit rows referencing purged attempt IDs remain present and unchanged; cleanup audit targets `client_signup_attempts` by a per-run UUID and contains counts only. No FK or cascade connects audit targets to attempt rows. No other audit retention is inferred (NEEDS SOURCE CONFIRMATION).
- **SC-010**: Every signed-in client/staff fixture sees a manual sign-out prompt; zero automatic sign-out/linking/merge/membership changes and zero token-bearing redirect/next values (FR-016).
- **SC-011**: Before and after ND-F5-1 defines archived state, every archived-identity collision returns the identical generic D-08 payload bytes, HTTP status and headers, with no measurable timing branch beyond the existing duplicate path; zero automatic registration/reactivation/merge or account-existence disclosure. Archived-state/admin-review design remains deferred on ND-F5-1 (ND-F11-9a/9b). Test against the local stack with 20 warm-up requests, then at least 200 interleaved trials per condition in randomized order: ordinary duplicate and archived-identity collision fixture (use a synthetic stand-in path until archived state exists). Compare the timing samples with a two-sample Kolmogorov-Smirnov or Mann-Whitney test; pass when p >= 0.01 and the absolute median difference is < 5 ms, and assert identical payload bytes/status/headers. Record raw timings in the evidence file. This is a regression detector, not a guarantee, and sets no latency SLA.
- **SC-012**: Attempt, success, failure, link-consumption and cleanup scenarios each emit required structured evidence at their specified transaction boundaries; rollback/replay emits zero false success/consumption events. Scans find zero secrets in audit and zero IP/ip_key/token/token hash/email/phone/name in attempt logs (ND-F11-10). Auth-compat guard failure is the explicit zero-write exception: no attempt row, audit row or consumption; evidence is structured server-side event fields `code` and `timestamp` only, with fixed code `AUTH_COMPAT_GUARD_FAILED` and no PII/IP/token/hash.

## Assumptions

- D-19 supersedes older SMTP wording. Email/password is approved; SMTP, email verification and email-reset rollout are excluded. No new policy defaults are chosen.
- The binding atomic DB unit is client creation, guarded link consumption and successful-change audit; Auth identity consistency uses the PO-approved option (i) direct transactional writes in AD-F11-1. Technical planning must demonstrate both under the local Supabase Auth stack and the two walls; inability is a blocker, not permission to weaken these guarantees or expose service-role credentials to the browser.
- Roadmap P1/Journey A include later approval/intake/finance; this unit stops at account creation. ND-F11-3 excludes Telegram and requires name/email/phone/password; signup creates pending-approval, with the workspace PO/WO approval action reserved to F12 (ND-F11-6a).
- ND-F4/F5/F8/F9/F10 items and production gates, including retention/B4, remain unchanged. No real client data or deployment is authorized.

**AD-F11-1 — Decided (PO, 2026-10-28): option (i); C1–C4 binding**: Use option (i), direct writes to `auth.users` and `auth.identities` inside the same database transaction as client creation, guarded link consumption and successful-change audit. C1–C4 in `plan.md` are binding conditions. Options (ii) and 3b are rejected alternatives; their evidence remains in `research.md`. This records design selection, not implementation approval.

## Infrastructure-failure contract (I1)

Only infrastructure failures produce `{status:'unavailable'}`: DB unreachable, C1 Auth-compat guard failure, admission-attestation infrastructure failure (including absent trusted IP in production), or unexpected exception after rollback. `unavailable` payload with HTTP 200 from the same-route Server Action (PO decision 2026-10-28: Server Action transport, unavailable returned as payload with HTTP 200), `Cache-Control: no-store`, `Referrer-Policy: no-referrer`; generic English “Please try again later.” / Arabic “يرجى المحاولة مرة أخرى لاحقًا.” only, with no cause. Nothing is consumed on unavailable, including the link or admission ticket; roll back redemption on this path. Previously committed admission accounting remains durable. For an Auth-compat guard failure specifically, fail closed before any DB write: create no attempt/audit row and consume nothing; emit only structured server-side event with only `code` and `timestamp`, fixed code `AUTH_COMPAT_GUARD_FAILED`, and no PII, IP, token or hash.

Never derive unavailable from link or identity state: unknown/malformed/expired/consumed links, invalid attestation and exhausted limits stay `invalid`; valid-link identity collisions stay D-08 `duplicate`. Unresolved policy blocks implementation/configuration rather than creating a link/identity unavailable branch. F10 GET `/register/[token]` open contract, including `{status:'invalid'}`, is unchanged. UI retains the form for a later retry and never claims completion. Enumerate link/identity branches in tests and prove none selects unavailable.

## U8 round 2: binding decisions and enforcement

The PO sub-decisions ND-F11-1a/4a/5a/6a/6b/9a/9b and C1 privacy are **Decided (PO, 2026-10-28)**; see the [decision register](spec.md#po-decision-register-and-open-sub-decisions). ND-F11-9a/9b decide deferral of archived-state/review design until ND-F5-1, not deferral of privacy: before and after that definition, archived collisions return the identical generic D-08 payload, HTTP status and headers, with no measurable timing branch beyond the existing duplicate path. No account-existence disclosure or automatic admin-review queue is introduced.

Pending-approval clients have **zero client access** through app `authorize()`, DB RLS (`has_workspace_access()` and client policies), direct PostgREST/RPC or Storage. Signup creates no session, but a pending client who later signs in and obtains a JWT is still denied every client-scoped read/write. Absence of a signup session is not an authorization control. Workspace PO/WO approval ships in F12; F11 only creates pending-approval clients and shows generic completion, then the client signs in after approval. Test app denials with an accepting backend mock, RLS independently of grants, direct PostgREST/RPC calls using a real pending client's JWT, and Storage reads/writes; no policy may admit pending clients.

**C1-audit split:** `app_private.client_signup_attempts` is the operational attempt log, purged after 30 days (ND-F11-7). Separately append `audit_events` rows for attempt/failure/success/consumption/cleanup (ND-F11-10). Both evidence payloads allow only outcome class, timestamp and link_id/workspace_id when resolved (both absent/NULL otherwise); no PII, raw IP, ip_key, token, hash, credential or provider payload. Admission writes attempt audit in its transaction; signup success and consumption audit commit in the atomic signup transaction. A caught business failure writes failure audit outside the rolled-back inner signup unit; a failure discovered after a full rollback uses a new evidence transaction. Unknown/unresolved-link attempt and failure audit events use `target_table='client_signup_attempts'` and `target_id` equal to the attempt row UUID. Purge deletes only eligible operational records and appends cleanup audit in the same purge transaction; cleanup uses `target_table='client_signup_attempts'` and a per-run generated purge-run UUID as `target_id`, with counts-only payload. `audit_events` has no FK from attempt targets to attempt rows and no cascade; purge NEVER deletes/updates `audit_events`. After purge, audit rows referencing purged attempts must still exist unchanged. Audit retention remains **NEEDS SOURCE CONFIRMATION - pending ND-F5-1**. Test purge removes old operational rows, preserves younger rows, appends cleanup audit and leaves every pre-existing audit row intact. Counters are separate window-lived mutable enforcement state, not attempt/audit logs.

**U1 key provisioning and verification:** provision both `SIGNUP_RATE_KEY` and `SIGNUP_ATTEST_KEY` in local Supabase Vault, readable only by the SECURITY DEFINER functions' owner; matching copies stay in server-only environment, never browser or logs. The DB recomputes `HMAC-SHA256(SIGNUP_RATE_KEY, token_hash)` and constant-time compares it with supplied link_key, independently of attestation verification with `SIGNUP_ATTEST_KEY`. Both keys must therefore be available to the DB verifier. No raw IP or ip_key may enter any log, audit, attempt record, exception/error or telemetry. Only window-lived HMAC-keyed rate-limit counters persist derived attribution.

Coordinated rotation: SIGNUP_RATE_KEY rotation resets IP/link counters because counter keys derive from the active key. Admission uses only the current single `ip_key`, with no old-key lookup. Accept up to one extra window of attempts per key (at most 1 hour for the IP window). Rotation is rare and manual: rotate the server environment and Vault value together; old-key counters expire naturally. Never log key values or identifiers derived from IPs. Counter expiry remains aligned to fixed windows (15 minutes/link, 1 hour/IP), and every submission reaching admission counts; invalid/replayed attestations receive no counter credit or ticket.

**I1 dependency:** U2 (T007/T008) owns the minimal `signup_admission_tickets` schema and internal guarded redemption primitive, including request-secret hash/link binding, one-use NULL-to-timestamp transition and business-failure/infrastructure rollback semantics. Only explicitly pre-admitted synthetic tickets are available to U3 tests. U5 (T019/T020) owns attested issuance, nonces, counters, operational purge and admission integration. The redemption primitive has no public issuer/grant and requires no U5 object at the U2/U3 exits. AD-F11-1 option (i) is PO-approved; C1–C4 are binding conditions.
