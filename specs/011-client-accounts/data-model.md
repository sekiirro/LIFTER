Current publication/availability changes do not invalidate or rewrite an issued association. No F12 effects.

Index workspace/id for scoped existence and Auth user for F4 lookup (unique indexes already cover both). ## Global identity security index: app_private.account_identifier_claims

This is a global identity constraint registry, not tenant-owned client content. It includes existing staff/Auth identities, including platform staff with no workspace. It must not invent a fake workspace for them. Columns: `auth_user_id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE RESTRICT`, `email_key text UNIQUE`, `phone_key text UNIQUE`, `created_at timestamptz NOT NULL` server time. Nullable identifier fields permit existing identities without phone/email, subject to ND-F11-9; client creation requires both. No PII from this table is publicly selectable.

Client UNIQUE columns enforce global client/client collisions independently. Claims UNIQUE keys enforce collisions against other account identities. DB triggers/functions synchronize claims for **all** Auth email/phone mutations and client-contact mutations, and enforce staff/client mutual exclusion on both classification directions. Client contact phone need not be an Auth phone-login identity: a NULL Auth phone must not erase the client's existing phone claim. A non-NULL Auth phone must agree with the same user's canonical phone claim or be rejected; no silent overwrite/release. Source-authority and identifier release semantics come only from ND-F11-2/9.

Future migration must backfill known identities using the approved canonicalizer, compare registry/client/Auth consistency, and fail on unresolved collisions or missing policy. Do not merge users, choose a winner, change old migrations/seeds, or claim Auth's current email index is sufficient. Concurrent staff creation/identifier change must contend on the same canonical keys. Registry writes use sorted advisory key locks as an ordering aid and UNIQUE as enforcement. All paths must use the same order; deadlocks/serialization aborts are safely retried with the same request identity. ND-F11-7/9 block release/pseudonymization design; no automatic deletion is authorized.

## Private signup operation and attempt records

`app_private.client_signup_operations`: committed receipt only; tenant-owned, mandatory `workspace_id`, composite link FK and UNIQUE link; UUID operation ID with UNIQUE `(workspace_id,id)`, `auth_user_id uuid UNIQUE REFERENCES auth.users(id) ON DELETE RESTRICT`, hashed high-entropy request secret, server timestamps and composite committed-client FK. Insert atomically with Auth/client/consume/audit. Never store password, raw token, email/phone or raw request secret. Immutable after insert; no reservation, lease, fence or cleanup state. At most one committed Auth identity per link; receipts never recover public success/session.

`app_private.signup_admission_tickets`: private security state separate from logs; generated UUID ticket PK, hashed request secret, link_key binding, resolved link/workspace binding when present, admitted_at and guarded redeemed_at NULL-to-timestamp. No raw IP/ip_key/token/hash/identity fields. Redemption occurs outside the inner signup subtransaction; business failures retain redemption, infrastructure failures roll it back. Force deferred checks inside the inner unit. Ambiguous transport abort requires authoritative receipt checking and fresh admission. Log/counter purge cannot reopen used tickets.

`app_private.signup_admission_nonces`: private single-use nonce state with freshness-bound expiry/replay protection; no identity/IP/token fields. Forced RLS, no grants. Verify before counter credit/ticket issuance.

`app_private.client_signup_attempts`: event ID, outcome class, timestamp; nullable link_id/workspace_id ONLY when resolved (both NULL otherwise, composite same-workspace relation when present). No IP, ip_key, token, token hash, email/phone/name, request-secret hash, ticket state or provider body. Operational records use admission/evidence transactions independently of signup rollback; retain 30 days, narrow purge of older operational logs only. Separate append-only audit_events cover attempt/failure/success/consumption/cleanup, with outcome class/timestamp and optional resolved link/workspace IDs only; purge appends cleanup audit and never touches existing audit rows. Other audit retention is NEEDS SOURCE CONFIRMATION; ND-F5-1/B4 unchanged. See AD-F11-2 below for counters and attestation.

Receipt/request secrets are credentials: random at least 32 bytes, only hash persisted, never audited/logged/cached. They bind an internal operation, never grant client/profile access or recovery of completion. Every consumed-link replay is generic invalid, including a matching secret after response loss. Client refresh/retry retains the secret safely for that submission without persistent analytics/local-storage exposure. Expiry/retention must preserve link-bound at-most-one identity; technical dedup cannot expire into a second signup.

## RLS, grants and guards

Enable and FORCE RLS on all proposed tables. Revoke ALL table privileges from PUBLIC, anon, authenticated and service_role, including defaults. No anon table policy, general INSERT/UPDATE/DELETE/TRUNCATE grant or wildcard SELECT. Private tables have no end-user policies or API schema exposure. Postgres-owned narrow functions use empty `search_path`, fully qualified objects, validated arguments and revoked default EXECUTE. An elevated owner bypasses RLS: function checks are mandatory independent authorization, not a claim that FORCE RLS restrains that owner.

Exact end-user column grant inventory: **none** on clients or all private tables. Explicitly withhold workspace/id/Auth-ID/email/phone/link/version/timestamp columns, wildcard SELECT and all writes. F4 already uses guarded RPC/helper lookup; this unit adds no client-list reader or client self-read/write policy. No new SELECT policy or safe view is needed: forced RLS defaults deny. Any future protected reader requires existing app `authorize()` and a scoped RLS policy using `has_workspace_access()` plus separately reviewed column grants, not an implied entitlement here. Isolated RLS mutation probes may fixture-grant a safe column inside a rolled-back test transaction only.

Public callable `public.client_signup_admit(token text, request_secret text, ip_key bytea, link_key bytea, issued_at timestamptz, nonce uuid, attestation bytea)` and `public.client_signup(token text, request_secret text, admission_ticket uuid, fields jsonb)` receive EXECUTE only for anon/authenticated, never service_role; server signup calls use anon/publishable credentials only. No signup service-role grants or admin orchestration. Before any write, both RPCs invoke C1: latest `auth.schema_migrations` in the explicit locally captured GoTrue v2.197.0 allowlist and presence/types of every column written. Failure returns generic unavailable, no write or consumption. C3 uses `extensions.crypt(..., extensions.gen_salt('bf', <GoTrue cost>))` with captured local cost and no plaintext in exceptions/RAISE/audit/logs/receipts/returns. Do not insert generated Auth columns. C2 requires real sign-in and exhaustive reference-row parity; C4 blocks hosted deployment. No grants are applied in this design run.

clients: immutable identity/workspace/snapshot/created_at after insert; initially pending-approval. Both app authorization and DB RLS deny client capabilities until approval; workspace PO/WO approval ships in F12 (ND-F11-6a), no transition UI invented. Claims: guarded synchronization only, never arbitrary reassignment. Operations: immutable committed receipt/binding/secret; attempt logs immutable; separate ticket state permits only guarded redemption. Clients/claims/operations have BEFORE DELETE row and BEFORE TRUNCATE statement guards using F10's `forbid_delete()` pattern, even for privileged integrity probes. UPDATE rejection uses the existing immutable-trigger pattern except tightly guarded admission redemption and claim synchronization. Attempts need a narrowly authorized local 30-day purge path guarded against deleting younger records, with structured cleanup evidence and no general DELETE/TRUNCATE grant or weakened one-use/receipt integrity. Client FK RESTRICT forbids deleting a committed identity. Closure/pseudonymization remain future reviewed work, never bypass these guards casually.

Preserve F10 snapshot/schedule guards. Future consumed-marker guard extension changes only signup's NULL→value transition to use fresh authoritative time and client correspondence; it preserves set-once markers, no-op rejection, all immutable columns and first-open rules. No direct marker UPDATE grant. A client insert followed by zero-row guarded consume raises and rolls back, including any Auth writes.

## AD-F11-2 — architect decision: trusted IP and admission

Technical architect decision, not PO policy approval. The C1 privacy proposal is **Decided (PO, 2026-10-28)**; Constitution unchanged. This is separate from proposed Auth compatibility criterion C1. AD-F11-1 remains PENDING PO; option (i) is a recommendation and C1–C4 are proposed evaluation criteria.

- U5 implements and tests a pure trusted-IP extractor: trust only `CF-Connecting-IP`, ignore `X-Forwarded-For` and all other IP headers, fail closed as unavailable when production IP is absent, and gate the explicit override to non-production. U6 wires the helper into the server action and owns the `build:edge` production-output proof.
- U5 implements and tests pure HMAC `ip_key`/`link_key` and attestation builders at their module boundary. Secrets remain server-only; raw IP stays within the server-action boundary. U6 wires these builders into the action and proves the test override is absent from `build:edge` output.
- The anon-callable admission RPC cannot trust a supplied ip_key. Send `attestation = HMAC(SIGNUP_ATTEST_KEY, ip_key ‖ link_key ‖ issued_at ‖ nonce)` with shared unambiguous canonical encoding. DB verifies SIGNUP_ATTEST_KEY held in Supabase Vault (local), readable only by the SECURITY DEFINER functions’ owner, freshness ≤ 60 s, no future-issued timestamp and single-use nonce. Missing/invalid attestation or replay → generic `invalid`, no counter credit or ticket (no oracle). Attestation infrastructure failure → `unavailable`. DB independently verifies token-to-link_key binding and enforces per-link limits regardless of caller ip_key; forged attribution cannot bypass it.
- Counter storage: `app_private.signup_rate_counters(scope ∈ {link, ip}, key bytea, window_start, count, expires_at)`, no workspace/link FK, forced RLS, no grants. Advisory xact locks in fixed order: link key, then ip key, inside the separate admission transaction that commits before signup. Enforce both 5/link/15 min and 30/IP/hour across links/workspaces. ND-F11-5a decides every submission reaching admission counts (success or failure); fixed 15-minute link/1-hour IP windows aligned with expiry, behind `client_signup_limits()`.
- Counter rows expire at window end (automatic expiry; no usable counter beyond the window); purge opportunistically on each admission and by the local purge job. Their retention is not 30 days. Keep private nonce/ticket security state separate from logs, forced RLS/no grants; nonce replay protection spans the freshness bound and ticket one-use integrity survives counter/log purge.
- `app_private.client_signup_attempts` stores outcome class, timestamp, and link_id/workspace_id ONLY when the link resolved (both NULL otherwise; same-workspace composite relation when present). No IP, ip_key, token, token hash, email/phone/name, or credentials. Retain 30 days (ND-F11-7). Operational failure records are written here; ND-F11-10 additionally requires separate append-only audit_events in admission/evidence transactions independently of signup rollback. For a failure discovered after the initial admission committed, use a separate admission/evidence transaction after rollback; do not claim to amend an already committed transaction. Success/consumption evidence remains atomic with signup.

## Infrastructure-failure contract (I1)

Only infrastructure failures produce `{status:'unavailable'}`: DB unreachable, C1 Auth-compat guard failure, admission-attestation infrastructure failure (including absent trusted IP in production), or unexpected exception after rollback. HTTP 503, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`; generic English “Please try again later.” / Arabic “يرجى المحاولة مرة أخرى لاحقًا.” only, with no cause. Nothing is consumed on unavailable, including the link or admission ticket; roll back redemption on this path. Previously committed admission accounting remains durable. Auth-compat guard failure is specifically fail-closed before any DB write: no attempt/audit row or consumption; evidence is a structured server-side event with only `code` and `timestamp`, fixed code `AUTH_COMPAT_GUARD_FAILED`, and no PII, IP, token or hash.

Never derive unavailable from link or identity state: unknown/malformed/expired/consumed links, invalid attestation and exhausted limits stay `invalid`; valid-link identity collisions stay D-08 `duplicate`. Unresolved policy blocks implementation/configuration rather than creating a link/identity unavailable branch. F10 GET `/register/[token]` open contract, including `{status:'invalid'}`, is unchanged. UI retains the form for a later retry and never claims completion. Enumerate link/identity branches in tests and prove none selects unavailable.

## U8 round 2: binding decisions and enforcement

The PO sub-decisions ND-F11-1a/4a/5a/6a/6b/9a/9b and C1 privacy are **Decided (PO, 2026-10-28)**; see the [decision register](spec.md#po-decision-register-and-open-sub-decisions). ND-F11-9a/9b decide deferral of archived-state/review design until ND-F5-1, not deferral of privacy: before and after that definition, archived collisions return the identical generic D-08 payload, HTTP status and headers, with no measurable timing branch beyond the existing duplicate path. No account-existence disclosure or automatic admin-review queue is introduced.

Pending-approval clients have **zero client access** through app `authorize()`, DB RLS (`has_workspace_access()` and client policies), direct PostgREST/RPC or Storage. Signup creates no session, but a pending client who later signs in and obtains a JWT is still denied every client-scoped read/write. Absence of a signup session is not an authorization control. Workspace PO/WO approval ships in F12; F11 only creates pending-approval clients and shows generic completion, then the client signs in after approval. Test app denials with an accepting backend mock, RLS independently of grants, direct PostgREST/RPC calls using a real pending client's JWT, and Storage reads/writes; no policy may admit pending clients.

**C1-audit split:** `app_private.client_signup_attempts` is the operational attempt log, purged after 30 days (ND-F11-7). Separately append `audit_events` rows for attempt/failure/success/consumption/cleanup (ND-F11-10). Both evidence payloads allow only outcome class, timestamp and link_id/workspace_id when resolved (both absent/NULL otherwise); no PII, raw IP, ip_key, token, hash, credential or provider payload. Admission writes attempt audit in its transaction; signup success and consumption audit commit in the atomic signup transaction. A caught business failure writes failure audit outside the rolled-back inner signup unit; a failure discovered after a full rollback uses a new evidence transaction. Unknown/unresolved-link attempt and failure audit events use `target_table='client_signup_attempts'` and `target_id` equal to the attempt row UUID. Purge deletes only eligible operational records and appends cleanup audit in the same purge transaction; cleanup uses `target_table='client_signup_attempts'` and a per-run generated purge-run UUID as `target_id`, with counts-only payload. `audit_events` has no FK from attempt targets to attempt rows and no cascade; purge NEVER deletes/updates `audit_events`. After purge, audit rows referencing purged attempts must still exist unchanged. Audit retention remains **NEEDS SOURCE CONFIRMATION - pending ND-F5-1**. Test purge removes old operational rows, preserves younger rows, appends cleanup audit and leaves every pre-existing audit row intact. Counters are separate window-lived mutable enforcement state, not attempt/audit logs.

**U1 key provisioning and verification:** provision both `SIGNUP_RATE_KEY` and `SIGNUP_ATTEST_KEY` in local Supabase Vault, readable only by the SECURITY DEFINER functions' owner; matching copies stay in server-only environment, never browser or logs. The DB derives link_key from the canonical token_hash with `SIGNUP_RATE_KEY` using the `lifter.f11.link.v1` domain tag and length-prefixed input defined above, then constant-time compares it with supplied link_key, independently of attestation verification with `SIGNUP_ATTEST_KEY`. Both keys must therefore be available to the DB verifier. No raw IP or ip_key may enter any log, audit, attempt record, exception/error or telemetry. Only window-lived HMAC-keyed rate-limit counters persist derived attribution.

Coordinated rotation: SIGNUP_RATE_KEY rotation resets IP/link counters because counter keys derive from the active key. Admission uses only the current single `ip_key`, with no old-key lookup. Accept up to one extra window of attempts per key (at most 1 hour for the IP window). Rotation is rare and manual: rotate the server environment and Vault value together; old-key counters expire naturally. Never log key values or identifiers derived from IPs. Counter expiry remains aligned to fixed windows (15 minutes/link, 1 hour/IP), and every submission reaching admission counts; invalid/replayed attestations receive no counter credit or ticket.

**I1 dependency:** U2 (T007/T008) owns the minimal `signup_admission_tickets` schema and internal guarded redemption primitive, including request-secret hash/link binding, one-use NULL-to-timestamp transition and business-failure/infrastructure rollback semantics. Only explicitly pre-admitted synthetic tickets are available to U3 tests. U5 (T019/T020) owns attested issuance, nonces, counters, operational purge and admission integration. The redemption primitive has no public issuer/grant and requires no U5 object at the U2/U3 exits. AD-F11-1 remains **PENDING PO**; option (i) is the recommendation and Auth criteria C1–C4 remain proposed.
