# Feature Specification: F19 Shared Plan Core

**Feature Branch**: `speckit-019-plan-core`
**Phase**: Specify → Clarify → Plan → Tasks → Analyze (documentation only)
**Status**: Spec-only proposal encoding approved PO decisions; implementation is not authorized by this change.

## Purpose and scope

F19 defines the shared lifecycle, delivery, activation, and client projection contract used by F17 Workout Planner and F18 Nutrition Planner. F19 owns stable plan identity, private drafts, immutable published revisions, delivery records, initial-subscription activation, productivity-unit attribution, authorization boundaries, and the shared client/delivery contract. F17 and F18 own their respective content schemas. F16 owns catalog identities, version references, and live exercise-video resolution. F12/F13 own subscription and renewal facts. P7 consumes productivity-unit records.

Workout-only and nutrition-only subscription types are out of scope for launch (A1). Real-time co-editing is out of scope (A3). This unit writes no implementation, migration, application code, or test code.

## User scenarios

1. **Edit and publish:** Staff edits one stable plan. Autosave and Save as Draft update its private draft. Ready & Publish appends an immutable revision; it does not create another Plan ID.
2. **Create or copy:** Only explicit Create New Plan creates a new root. It may start blank, from a template, or from an authorized existing plan. Copying reproduces planner-entry/content values, not ownership or history.
3. **Deliver and activate:** Ready & Publish for a client with an eligible subscription is the delivery operation. Workout and nutrition deliveries may occur on different days. The initial subscription activates once both kinds have a committed delivery; that same transaction creates a productivity unit only for an eligible new client who has no existing unit. Later deliveries and revisions cannot reactivate or add units.
4. **Override:** A Platform Owner may Override Activate an eligible initial subscription before, between, or after plan deliveries. The operation immediately activates and creates a unit only for an eligible new client with no existing unit, without creating a delivery. Later plan deliveries do not add another unit.
5. **Client access:** The client projection contains every delivered plan for that client and exposes the latest published revision of each. Undelivered plans and private drafts are never disclosed. Expiry blocks normal platform content and presents the approved renewal page body.

## Functional requirements

- **F19-FR-001 - Stable plan lifecycle (baseline B).** A plan has one stable Plan ID, one private mutable autosaved draft, and append-only immutable published revisions. Draft saves and publish retries do not create roots. Only explicit Create New Plan creates a root. Save as Draft and Ready & Publish are distinct actions; draft content is never client-visible. Every Ready & Publish appends one revision and records one delivery for its target subscription. Later revisions remain under the same Plan ID and do not create another root or reactivate the subscription.
- **F19-FR-002 - Plan ownership, subscription selection, and delivery (A5, Q1, MCQ-12/16/17; S43-PO-4 item 1; S45-PO-2 MCQ-17).** Each plan root carries `workspace_id` and `client_id`; delivery rows reference the client's single continuous subscription. Ready & Publish is one action: each successful published revision atomically appends that revision and one `plan_deliveries` row; there is no separate Deliver action. The pending F13-FR-037 requirement defines the continuous-subscription invariant (see Pending F13 requirement references). Before F19 delivery is enabled, the F13 renewal-continuity change and a safe, audited, dry-run-first, idempotent cleanup that corrects only invalid overlapping legacy records must be completed. Those overlapping legacy F13 predecessor/successor records are mock/test-only data; no production reconciliation or subscription-selection rule is specified. Until a client's legacy overlap is safely corrected and its single continuous subscription is verified, Ready & Publish fails closed with generic `not_permitted` and writes nothing. A client with more than one active subscription projection also receives the same generic refusal. For a resolved single continuous subscription, the initial F13 `awaiting_activation` subscription is an eligible F19 delivery target so the approved two-delivery activation can occur. Otherwise the subscription whose F13 entitlement projection is `active` or `frozen` (F13 FR-028; `app_private.f13_project_entitlement`) is eligible; expired, refunded, or cancelled subscriptions are not. Ready & Publish binds automatically to the client's eligible continuous subscription; there is no chooser. If no eligible subscription exists or the invariant is violated, fail closed with generic `not_permitted` and write nothing. F19's refusal is defense in depth.
- **F19-FR-003 - All delivered plans visible (A5).** A client may have any number of distinct plans. The authorized client projection returns every plan with a committed `plan_deliveries` row for that client, including multiple plans of the same kind. It must not omit plans because they lack a special "first delivery" record. Drafts without a delivery are not disclosed. Because publishing without an eligible subscription is refused, no published revision can be undelivered. If any cache is introduced for client plan views, its key includes the authenticated user, the plan identity, the plan version and the workspace; two plans with the same published version for the same user and workspace never share a cached result; a test and mutations (drop plan identity from the key -> test fails; drop plan version from the key -> test fails) are required. Video is never stored in a cached projection: F16 FR-034 forbids a Video resolution cache, and every authorized view resolves Video from the current authorized library value (F16 FR-034, F16 T051 PARTIAL, S46-R1).
- **F19-FR-004 — Initial automatic activation (A1, Q2/Q3).** For an `initial` subscription, the first committed workout delivery and first committed nutrition delivery for that same workspace, client, and subscription satisfy the activation condition, even when they occur on different days. The delivery completing the pair and activation commit in one atomic transaction. In that transaction, create a productivity-unit row only for an eligible new client who has no existing unit; returning clients and clients who already have a unit may activate without another unit. The first delivery remains committed if the other kind is delivered later. The activation is unique per `(workspace_id, subscription_id)`. Later deliveries or revisions never reactivate or add units. Workout-only and nutrition-only subscription types are deferred and excluded.
- **F19-FR-005 — Renewal modifies the continuous subscription (S43-PO-5 items 1, 3, 4, 7, 8, 10).** Renewal extends the existing subscription expiry by the full purchased duration; an expired renewal starts today. Frozen subscriptions must be unfrozen before renewal, and freezing extends expiry by frozen days. Renewal records full revenue, creates no subscription row, and awards no additional unit. Renewal-then-upgrade preserves separately purchased renewal duration and payments; upgrade credit is only the original package full payment. Expired subscriptions cannot upgrade; renew into the desired package. (pending F13-FR-037; S43-PO-5; architect mapping (S43-R6)).
- **F19-FR-006 — Platform Owner override (A2, Q4=A, Q6=B, Q9; S43-PO-4 item 5).** Only a Platform Owner may invoke Override Activate, and only for an initial subscription. It is allowed for any otherwise eligible initial subscription, including an unapproved or unpaid one. It is refused for cancelled or refunded subscriptions and for deactivated clients, returning the existing generic `not_permitted` result. After current authorization, resolve a matching operation receipt before evaluating whether a new override is refused because the subscription is already active. An exact authorized retry returns its original receipt; an active subscription with no matching receipt returns the existing generic `not_permitted` result and writes or changes nothing. Override immediately records activation in one transaction, even with zero plan deliveries. It awards the client's one production unit only if none was previously awarded. It records no fabricated plan-delivery row. Subsequent plan deliveries cannot activate again or award another unit. Override is not available for renewal subscriptions.
- **F19-FR-007 - Productivity-unit recipient (Q5=A, Q10=No, MCQ-14; S43-PO-5 item 7).** Award one production unit per new client only, once per client, on first activation (automatic or PO Override). Returning clients never count as new. Upgrade, renewal, and re-publication never award additional units. Automatic activation credits the trainer assigned at the activation transaction serialization point. If none is assigned, credit the Trainer who published the completing delivery; if that publisher is not a Trainer, refuse the completing Ready & Publish with no writes. Override with no assignment requires selection of an active trainer in that workspace. Selection records only the unit recipient and never creates or changes an assignment. See pending F13-FR-040 (plans) and pending F13-FR-041 (points), plus pending F13-FR-037 (subscription continuity). (S43-PO-5; architect mapping (S43-R8)).
- **F19-FR-008 — Copy semantics (A4, Q7=A).** Copying an existing plan uses its latest published revision; copying a template uses its immutable template version. Copy actual planner-entry values, including sets, reps, RIR, rest, Notes, and nutrition content, rather than current library defaults. Create independent destination values. Do not copy source ownership, authorship, audit history, client/subscription association, delivery or activation facts. Do not copy exercise Video: F16 resolves Video live for the authorized workspace. F17/F18 define domain-specific content fields.
- **F19-FR-009 — Editing permissions (A3, Q8=A).** A Trainer, Workspace Owner, or Platform Owner with current authorization in the plan’s workspace may edit any client plan in that workspace, including one associated with another trainer. Sales may not edit. No role receives cross-workspace plan access. The system provides no real-time co-editing experience.
- **F19-FR-010 — Compare-and-swap writes (A3, Q8=A).** Draft writes compare the expected draft version; publish compares the expected current draft and published revision/version. A stale write returns `stale_version` without partial mutation. Exact idempotency-key replay returns the original committed result after current authorization is rechecked; changed arguments under the same key return `key_conflict`. Concurrent operations cannot overwrite a newer draft or append duplicate revisions/deliveries.
- **F19-FR-011 — Expired client access (A6, Q11).** On subscription expiry, normal platform content, including plan content, is blocked and the client sees an informational subscription-status page. It has no buttons, CTAs, renewal actions, or contact actions. The page is informational only: the approved title and body are shown byte-for-byte below. F19 defines the plan-content denial boundary and projection; P4 owns the wider access enforcement and expiry surface.
- **F19-FR-012 - Trainer deletion and retained history (A7, MCQ-13).** Trainer deletion must not cascade-delete plans, revisions, deliveries, activations, productivity records, or audit history. Author references use `ON DELETE RESTRICT` or equivalent and retain the deleted trainer non-login account ID under F11 deletion policy; no tombstone rewrite is used. F11 PR #73 remains pending, not a merged fact.
- **F19-FR-013 — Audit, tenant isolation, and persistence.** All plan, revision, delivery, activation, and unit operations are workspace-scoped, authorization-checked after relevant lock waits, idempotent, auditable, and concurrency-safe. Client self-reads derive the client from authenticated identity and never accept a caller-selected client/workspace as authority. Persistence and concurrency evidence requires real-database integration tests; static or mocked tests do not establish persistence.
- **F19-FR-014 — Forward-only activation model.** New activation writes use sources `plan_deliveries` and `po_override` only. Historical `activation_source='renewal'` rows remain valid and unchanged; the write-path guard rejects that source on new writes. Renewal and upgrade write immutable lifecycle and ledger events for period changes and revenue, and no new activation row. A continuous subscription activates once. Do not reinterpret historical rows. (Architect rulings S43-R8 and S43-R9 Sol-8; pending F13-FR-037).
- **F19-FR-015 — Plan publishing and points (S43-PO-4 items 5–6).** Both new and existing eligible clients may receive unlimited plan revisions and publications, subject to normal permissions. Upgrade and renewal never require a new plan or create a successor subscription (pending F13-FR-037/040/041). Publishing never awards additional trainer production points; the single new-client unit is governed by F19-FR-007 (S43-PO-5 item 7; architect mapping (S43-R8)).

## Measurable success criteria and acceptance scenarios

- **SC-001 — Stable private lifecycle (baseline B).** For every successful draft save, the Plan ID remains unchanged; zero client projections contain the draft; each successful publish appends one immutable revision. **Given** Plan P with revision R, **When** authorized staff edit and save, **Then** P remains P and the draft is private. **When** Ready & Publish succeeds, **Then** one new immutable revision is appended under P and the draft becomes the published content.
- **SC-002 — Explicit creation only (baseline B).** Across 100 retries of autosave, Save as Draft, and Ready & Publish with the same operation key, exactly zero additional roots are created; an explicit Create New Plan creates exactly one root. **Given** an existing plan, **When** any edit/save/publish operation is retried, **Then** its root count is unchanged. **When** Create New Plan succeeds, **Then** exactly one new Plan ID exists.
- **SC-003 - Delivery is Ready & Publish (Q1=A, MCQ-12/16/17; S43-PO-4 item 1; S45-PO-2 MCQ-17).** Each successful Ready & Publish for an eligible subscription publishes exactly one immutable revision and records exactly one delivery row. **Given** an authorized editor and the client's verified single continuous eligible subscription after the F13 continuity prerequisite and safe cleanup, **When** Ready & Publish commits, **Then** revision and delivery commit together and bind automatically without a chooser. **Given** overlapping mock/test legacy records not yet safely corrected, more than one active subscription projection, no eligible subscription, or an unexpected continuity violation, **When** Ready & Publish is attempted, **Then** it returns generic `not_permitted` and writes nothing.
- **SC-004 - First deliveries activate initial subscription once (A1; S43-PO-4 item 5).** One first-kind delivery leaves activation absent; after workout and nutrition deliveries for the same initial subscription commit, exactly one activation exists and the client has at most one production unit. **Given** an eligible new client with no prior unit, **When** both first plan kinds are delivered, **Then** activation and one unit commit atomically. **Given** a returning client or a client who already has a unit, **When** both first plan kinds are delivered, **Then** activation commits without creating another unit.
- **SC-005 - Retry, concurrency, and rollback (baseline B; S43-PO-4 item 5).** In 100 concurrent/replayed delivery attempts, no duplicate delivery, revision, activation, or client-level unit is created. A failed transaction leaves none of its writes. **Given** concurrent second-kind deliveries or an unknown result after commit, **When** the same operation key is retried, **Then** one receipt and at most one activation are returned and the client has at most one unit.
- **SC-006 — Later plans/revisions do not reactivate (A5).** For any number of later plan deliveries and revisions on an activated initial subscription, activation count and unit count remain one. **Given** an activated subscription, **When** a tenth distinct plan or a later revision is delivered, **Then** it is visible to the client and neither activation nor unit count increases.
- **SC-007 - All and only delivered plans project (A5, MCQ-12).** For a fixture with at least ten delivered plans of the same kind and one undelivered draft, every delivered plan appears and the draft is absent. **Given** delivered plans P1...P10 and draft P11, **When** the authorized client reads plans, **Then** P1...P10 appear with their latest published revisions and P11 and all draft data are absent. **Given** a cache introduced for client plan views, **When** two plans with the same published version for the same user and workspace are read, **Then** the cache key includes the authenticated user, the plan identity, the plan version and the workspace, the two plans never share a cached result, the required test fails when the mutation drops plan identity or plan version from the key, and Video is never stored in a cached projection because F16 FR-034 forbids a Video resolution cache (F16 FR-034, F16 T051 PARTIAL, S46-R1).
- **SC-008 - Override exactly once (A2, Q4=A, Q6=B, Q9, MCQ-15; S43-PO-4 item 5).** For an otherwise eligible initial subscription, Override records one activation; it awards a unit only when none exists for an eligible new client. Later delivery adds no unit. **Given** an eligible new client with no deliveries or prior unit, **When** a Platform Owner overrides, **Then** one activation and one unit commit without a delivery row. **Given** an already-active subscription with no matching authorized receipt, **When** Override is attempted, **Then** `not_permitted` is returned and no row or value changes. **Given** an exact authorized retry after a successful override, **When** its operation key is replayed, **Then** the original receipt is returned before active-state refusal.
- **SC-009 - Recipient and assignment separation (Q5=A, Q10=No, MCQ-14).** Automatic activation credits the assigned trainer or, if none exists, the completing delivery publisher when that actor is a Trainer. Otherwise the completing Ready & Publish is refused with no writes. Override with no assignment requires an active same-workspace trainer selection. Selection never creates an assignment. **Given** an eligible new client with no prior unit, no assignment, and a Trainer publisher completing delivery, **When** activation completes, **Then** that Trainer receives the unit. **Given** a non-Trainer publisher, **When** completing delivery is attempted, **Then** it is refused without delivery, activation, or unit. **Given** Override with no assigned trainer, **When** a valid trainer is selected for a client eligible for a unit, **Then** the unit names that trainer and assignment is unchanged.
- **SC-010 — Copy and role boundaries (A3/A4, Q7/Q8).** Copied values equal the source’s latest published revision or immutable template version for all domain content fields, including sets/reps/RIR/rest/Notes and nutrition content; Video, ownership, history, subscription, and delivery are not copied. Trainer, Workspace Owner, and Platform Owner can edit within workspace; Sales and cross-workspace actors cannot. **Given** a source whose planner values differ from current defaults, **When** it is copied, **Then** the destination preserves source values and has independent ownership/history and no copied Video value. **When** Sales or a foreign-workspace actor attempts edit/read, **Then** access is denied without revealing existence.
- **SC-011 — Expiry and trainer deletion (A6/A7, Q11).** After expiry, client plan content is denied and the approved body copy is byte-identical to the PO source. Trainer deletion leaves plan, revision, and audit record counts unchanged; author references restrict deletion and prevent cascade. **Given** an expired client, **When** the client requests a plan, **Then** content is denied and the informational page shows the approved title and body with no buttons, CTAs, renewal actions, or contact actions. **Given** a trainer referenced as an author, **When** the F11 deletion workflow executes, **Then** authored plans/revisions/history remain and no cascading delete occurs; author reference retains the non-login account ID under F11 policy; PR #73 is pending.
- **SC-012 - Automatic activation recipient (Q5=A, MCQ-14).** Automatic activation credits the assigned trainer at serialization, or otherwise the Trainer who publishes the completing delivery. A non-Trainer completing publisher cannot complete the operation. **Given** an eligible new client with no prior unit, no assignment, and one delivery kind committed, **When** a Trainer publishes the other kind, **Then** one delivery, activation, and unit commit atomically for that Trainer. **Given** the completing publisher is a Workspace Owner or Platform Owner and no trainer is assigned, **When** Ready & Publish is attempted, **Then** no delivery, activation, or unit is committed.
- **SC-013 — Unlimited eligible plans without points (S43-PO-4 items 5–6).** **Given** an eligible client, **When** staff publish any number of revisions/plans under normal permissions, **Then** all successful deliveries remain visible and publishing adds no unit. **Given** an upgrade or renewal, **When** it is recorded, **Then** no successor subscription or new plan is created, and no additional client-level unit is awarded. **Given** a returning client, **When** any plan, upgrade, or renewal is recorded, **Then** the client is not reclassified as new and no extra unit is awarded. (S43-PO-5 item 7; architect mapping (S43-R8); pending F13-FR-037/040/041).

- **SC-014 ? Legacy renewal activation compatibility (S43-R9 Sol-8). Given** an installed historical activation row with source `renewal`, **When** the forward schema update is applied, **Then** the row and source meaning remain valid and unchanged. **Given** a new activation write requesting source `renewal`, **When** the write-path guard runs, **Then** it is rejected; new writes accept only `plan_deliveries` or `po_override`.
