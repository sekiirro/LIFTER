# Plan Core Data Model

## P4 activation and first-delivery contract

F12 baseline: immutable id, workspace_id, subscription_id, activated_at and non-null `delivery_event_id`, with unique workspace/subscription and composite subscription relation. This table has no public writer or standalone activation action. P4 extends it forward with `workout_delivery_id` and `nutrition_delivery_id` relations to first-delivery records. Keep the legacy `delivery_event_id` column and NOT NULL constraint; for a new activation, set it to the generic source event of the successful first-delivery record that completes the both-delivered gate. The two typed FKs remain the authoritative links to both deliveries. Do not rewrite or backfill existing activation rows. Legacy readers continue reading the existing column unchanged; existing values retain their original meaning. New readers that need proof of both first deliveries use the typed relations and delivery records, never the legacy column alone. The P4 forward migration adds `first_plan_deliveries` with one durable row per `(workspace_id, subscription_id, plan_kind)` (`workout` or `nutrition`), binding `client_id`, `plan_id`, immutable `plan_version_id`, `delivery_event_id`, and `delivered_at`. Each row references the existing idempotency ledger operation; unique constraints on subscription/kind and delivery event prevent duplicate first delivery. A database-enforced kind-specific composite relation (composite foreign keys and/or equivalent CHECK constraints) MUST bind `plan_kind='workout'` only to a workout plan and its immutable version, and `plan_kind='nutrition'` only to a nutrition plan and its immutable version; cross-kind or mismatched-version references are rejected. The delivery writer also validates this mapping. P4's delivery RPC commits each kind independently and is retry-safe; it MUST NOT require paired publishing. When either delivery is the second successful first delivery, the same transaction that commits that delivery MUST verify exactly one successful workout row and one successful nutrition row for the same workspace/client/subscription, then insert `subscription_activations` and the single subscription productivity unit. If activation cannot complete in that transaction after the delivery is otherwise valid, the transaction MUST durably record an outbox/retry item before commit; a worker or retry path processes it idempotently under the same subscription serialization guard. Thus both delivery rows cannot be durable while activation has neither succeeded nor a durable retry. Exact replays return the original delivery result and activation status and may re-attempt the durable activation path, without duplicating delivery, activation or productivity credit. `activated_at` is recorded by the activation transaction after it verifies both successful first deliveries; it is not copied from either delivery timestamp. The activation row's two typed delivery FKs preserve both source-event relations; a unique workspace/subscription guard makes concurrent activation attempts return the existing activation. F12 internal due reader sees no rows until that integration.
