# Contract: F12 staff operations and client status

**Status**: Proposed, 2026-10-29. [Model](../data-model.md), [plan](../plan.md) final PO decision mapping and [handoffs](feature-handoffs.md) govern behavior and Architect refinements. Names are proposed public API contracts for implementation review, not existing functions.

## Transport and two walls

Staff reads and Server Actions live under `/registration-approvals`, `/registration-approvals/[clientId]`, separate `/payments` and `/payments/[subscriptionId]` pages gated by record_payment for PO/WO/Sales. Sales cannot enter the approval queue/review. IDs alone never authorize access. Actions verify session with `getUser()`, load current actor, call app `authorize()` for target workspace/capability and explicit role restrictions, validate the allow-listed shape and framework same-origin/CSRF protection, then call one RPC using the same user's session client. No service-role financial writer or redirect parameter containing client PII. Responses are dynamic/no-store; generic errors never return database/provider diagnostics.

Database operations independently verify auth.uid(), an existing workspace and capability/role/scope. No target existence, stale state, receipt or commission is disclosed before permission checks. Lock client → subscription → obligation/ledger, then current actor/membership authorization rows; repeat authorization after waits in fresh statements using current locked tuple values. Keep those locks through commit. Reject target spoofing even when a caller bypasses the action.

Capability map: approve/reject = `approve_registration` and PO/WO; reconsider = approval plus PO; collection = `record_payment` and PO/WO/Sales; correction = PO and existing `record_refund` capability, scoped to this correction operation only. Correction remains available on the preserved rows of a deleted client; collection and every new charge or obligation are refused for that client (S47-PO-12). Sales approval is removed in TS and DB matrices. Commission reads additionally require PO/WO. All public functions are postgres-owned SECURITY DEFINER with `search_path=''`, fully qualified references, and EXECUTE only authenticated; internal helpers revoke default EXECUTE from all application roles. Base tables remain ungranted and forced RLS.

## Common mutation request

- `workspace_id`, `client_id`, `request_key`: required canonical UUIDs. workspace must correspond to target; it is not a trusted tenancy assertion.
- Money: canonical unsigned decimal strings for expected collection amount; rate/price/schedule are never caller input. Reject numeric JSON money, sign/fraction/exponent/overflow, unknown keys and mismatched snapshot currency/amount.
- `collected_on`: valid finite ISO `YYYY-MM-DD` date, no future versus fresh Cairo today after waits; no signup lower bound. Responsible staff, recorded_at and audit actor derive from signed actor/DB time.
- Full payment confirmation must be explicit true for collection/approval/reconsideration; false/missing creates nothing.
- Ledger operations name expected installment seq, expected stream revision and previous event ID (null for initial root). Requests never say only “next unpaid.” The exact amount shown in the UI is read-only, but the expected value is still validated on the server.
- Operation-key canonical encoding v1 hashes operation, workspace/client, expected state, subscription/obligation/original event IDs, installment seq, expected revision/predecessor, expected amount/currency, collection date, confirmation and rejection code in fixed ordered typed fields. Absent optional fields are explicit null, UUID/date/money are normalized once. Actor is bound from session. Reject fields not defined for that operation.

## Public RPC inventory

Each mutation takes a single operation-specific typed JSON request and returns the common result union. JSON is validated independently by the DB; it is not an escape for arbitrary columns.

| RPC / action adapter                                 | Request beyond common IDs/key                                                                                                                                                  | Successful result / effects                                                                                                                                                                                                                               |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `registration_approve` / `approveRegistration`       | expected_state=pending-approval, expected_installment_seq=1, expected_amount_minor, currency, collected_on, payment_confirmed=true                                             | approved receipt; subscription+obligations+first collection+decision+approval fact+audit atomic                                                                                                                                                           |
| `registration_reject` / `rejectRegistration`         | expected_state=pending-approval, reason_code=`registration_rejected` only                                                                                                      | rejected receipt; decision/state/audit only                                                                                                                                                                                                               |
| `registration_reconsider` / `reconsiderRegistration` | expected_state=rejected, first-payment fields as approve                                                                                                                       | approved receipt with reconsider operation; same initial graph, PO only                                                                                                                                                                                   |
| `installment_collect` / `recordInstallment`          | subscription_id, obligation_id, expected_installment_seq, expected_revision, expected_previous_event_id, expected_amount_minor, currency, collected_on, payment_confirmed=true | collection receipt; full obligation only; activation required for seq>=2, all earlier obligations paid; early payment allowed; refused with `stale_state` for a client in the F11 deletion lifecycle (no new collection, charge or obligation; S47-PO-12) |
| `collection_correct` / `correctCollection`           | subscription_id, obligation_id, original_event_id, expected_installment_seq, expected_revision, expected_previous_event_id, correction_confirmed=true                          | reversal receipt; exact negative stored amount/commission, derived unpaid; no supplied amount/date/method/reason text; available on a deleted client's preserved unreversed collection (S47-PO-12)                                                        |

Reject uses only `registration_rejected`, no free text. Correction effective_on is the Cairo date of fresh correction recording; book in that correction month and retain original event/date/commission unchanged. Reconsideration is distinct from stale normal approval; no rejected→pending transition, link release or recovery change. On a deleted client's preserved rows the correction follows the same rules and creates no new collection, charge or obligation; a new collection for that client is refused (S47-PO-12).

## Result shapes

Successful mutation returns only `{status:'ok', receipt:{id, operation, workspace_id, client_id, subscription_id, obligation_id, event_id, installment_seq, revision, outcome, amount_minor, currency, collected_on, recorded_at}}`. Not-applicable fields are null. `recorded_at` is DB recording time inside the transaction; success is acknowledged only after commit and no exact commit timestamp is asserted. `amount_minor` is a signed decimal string (negative on correction); outcome is approved/rejected/collected/reversed. Commission/rate, names/email/phone, tokens, hashes, raw arguments and arbitrary metadata are absent. Common success payload is equally safe for Sales and owners. Owner commission is fetched separately.

The DB stores the successful receipt and returns it unchanged for an exact authorized replay; no “replayed” flag, fresh timestamp or changed amount. It does not reflect current state after later correction; readers do. Receipt uniqueness is actor/key across all operations. Reuse by another actor is a different key namespace but cannot bypass financial uniqueness. Mismatched target/operation/arguments for the same actor/key fails; key conflicts do not expose the old request. Concurrent distinct-key collection against the same expected revision yields one success and one stale result, not collection of another installment.

| Failure shape                                          | Meaning / precedence                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{status:'not_permitted'}`                             | unauthenticated/foreign/revoked/nonexistent or disallowed role; no target/receipt details                                                                                                                                                                                                                                                                                                                               |
| `{status:'invalid_input', fields:[allowedFieldCodes]}` | syntactic errors in allowed supplied fields only; no echoed values or existence information                                                                                                                                                                                                                                                                                                                             |
| `{status:'stale_state'}`                               | authorized target no longer has expected client state or ledger revision; the expected client state includes the F11 deletion lifecycle, so a `deletion_pending`, `release_pending`, released or deleted client is never in the expected actionable state; exact authorized replay is checked first; a collection for a client in the F11 deletion lifecycle is refused with this shape and creates nothing (S47-PO-12) |
| `{status:'key_conflict'}`                              | authorized actor reuses key with changed canonical intent; no prior receipt details                                                                                                                                                                                                                                                                                                                                     |
| `{status:'unavailable'}`                               | infrastructure/unexpected failure after rollback; generic translated retry text, no SQL/provider payload                                                                                                                                                                                                                                                                                                                |

Server Actions return these safe payloads using framework transport; do not add a target-existence HTTP distinction. Missing session uses the existing login flow with a safe token-free return path; direct RPC callers receive the denial/permission error normalized to not_permitted. Unauthorized targets cannot produce stale_state/key_conflict. Retain the exact request/key after uncertain outcomes; The decided UI retains the same canonical request/key, warns and permits safe retry without a duplicate payment. Never report success before commit or replace an uncertain key automatically.

## Narrow client status and automatic navigation

F12 creates `/account/status` in the separate client route group; this is the standalone Pending/Approved/Rejected page, not an intake page. Verify Auth through `getUser()` and the safe self-status association, never through staff role membership, caller IDs or an approval claim in JWT. Existing middleware already requires authentication for this path; keep it protected. On expired/missing Auth use the existing login flow with safe return path `/account/status`, no token/PII. Staff/non-client sessions get generic denial, not another client's status.

`client_self_status()` takes no arguments and returns only `{status:'ok',approval_state:'pending-approval'|'approved'|'rejected'}` or generic not_permitted/unavailable. Only this self-status is allowed while pending/rejected. Approved alone grants no plan/intake/Storage access. Internal `client_has_access(workspace_id,client_id)` directly checks the indexed signed association and approved state, avoiding recursive client RLS. No browser EXECUTE grant or staff capability is created for that private helper. Request memoization is request-local only; no shared/JWT cache of approval.

Technical recommendation AI-F12-4: pending pages perform visibility-aware bounded polling through the session-backed safe action, no Supabase Realtime/subscription/channel. Use one request in flight, a minimum 15-second interval, at most 12 automatic status attempts per mounted page (at most 4 per minute, nominal 3-minute window). Hidden/offline pages pause; focus/online may resume remaining budget without resetting it or issuing an immediate parallel request. Failures count toward budget; back off within it rather than retrying in a tight loop. Stop polling on approved/rejected, exhausted budget, lost Auth or unmount; cancel timers/ignore late results. Manual Refresh always remains available while authenticated, independently debounced with the same one-in-flight guard; it does not restart automatic budget. This bounds Free-tier HTTP/DB cost without claiming a latency SLA.

On an observed pending-to-approved transition, announce current status and request at most one redirect preflight. Revalidate Auth, current self association and approved state on the server, and resolve an allowlisted same-origin destination that actually exists and is authorized. Current fallback is `/`: `app/(app)/page.tsx` exists, accepts an authenticated role-null client via `requireActor()`, and exposes no plans. Do not use guessed `/intake`, `/dashboard`, workout or nutrition routes. Use router.replace once on successful preflight. No automatic redirect loop or arbitrary next URL. If navigation/preflight fails, keep the status page and visible manual-navigation fallback; no failure may remove Manual Refresh. A directly opened already-approved page can remain readable with its manual Continue link; automatic redirect is for a detected approval transition.

All three standalone states use reviewed bilingual copy; approved explicitly does not mean activated or plans available. There is no form selector/engine, fabricated plan CTA or P2 assignment success. Rejected shows the generic rejected state, no reason details/PII/recovery-policy invention. P2 may later add a real route through reviewed server allowlist/route contract; its absence does not block the existing `/` fallback. Existing root landing gets an authenticated client status link and only capability-appropriate staff Approvals/Payments links, not a navigation redesign.

## Flexible registration-link creation (F12-owned extension)

Existing F10 action path `app/(app)/registration-links/actions.ts`, `lib/registration-links/service.ts`, `validation.ts` and dialog/manager are extended in U1F. New v2 action input: `{workspaceId,packageVersionId,paymentTerms:null|{upfrontAmountMinor:string,totalPaymentCount:number,installments:{seq:number,amountMinor:string,dueOffsetDays:number}[]}}`. Null retains full-payment issuance, including Trainer generation. Non-null requires generation AND configure_installment_schedule at both walls before shape/target disclosure. Reject mixed old/new fields and actor/price/rate/currency/expiry overrides; retain the existing DB legacy issuer contract for old callers.

New proposed RPC `issue_flexible_registration_link(workspace_id,package_version_id,token_hash,upfront_amount_minor,total_payment_count,installments)` is authenticated-only, hardened SECURITY DEFINER/search_path empty and qualified throughout. Validate explicit upfront equals row 1, count equals array length, amount strings positive/bounded, contiguous sequence, existing increasing integer offsets and exact total against authoritative version. Delegate to existing `issue_registration_link` in the same transaction, inheriting offer locking, current-version checks, rate-limit policy, immutable snapshot and deferred audit/total checks. Recheck current capability/scope after waits in this wrapper before return/commit. No raw token returned by the DB; server constructs URL once only after commit as F10 does.

Editor default semantics: staff chooses positive upfront (no guessed value/percentage); default remainder is exact price minus upfront at offset 30, upfront at approval. Full-price upfront yields count 1/no zero remainder. Custom count/amounts/offsets are configured before issue, all positive and exact-total, no automatic equal split for additional rows. Count-includes-upfront labeling/removal behavior is an architect design refinement, not a new policy question. Preserve all historical row amounts/counts/offsets; no migration normalization or hidden reinterpretation of custom timing. Frontend Design Gate covers this changed issuing UI as well as approval/payment/status screens.

## Audit / event consistency

Client UPDATE trigger owns approved/rejected/reconsidered audit. Payment INSERT trigger owns collection/correction audit. Decision/receipt/approval-fact inserts do not duplicate these success events. All effects roll back on audit or deferred failure. Approval fact emission is exactly once for the initial successful approval, including PO reconsideration, and is governed by the [P2 contract](feature-handoffs.md). Denied operations leave no false success audit. F11 audit mappings remain intact.
